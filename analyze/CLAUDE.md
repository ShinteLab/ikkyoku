# analyze の CLAUDE.md

**確定した局面 → 評価値**（Phase 4）。⚠️ **ikkyoku は将棋 UI（USI クライアント）であって、
`engine` の利用者ではない。** クライアント本体は `core/usi/client`（ここに書かない）。
⚠️ **正式な SFEN を要求するのはここだけ。**

### 正式な SFEN を要求するのはエンジンだけ

**「どちらが手番か」が大きなファクタになるのは評価値を出すときだけ。** そこでは
先後と手番の整合した正式な SFEN が要る（手数は**手番と食い違っていなければ十分**）。

したがって反転は `engine` に渡す境界（Phase 4）で行う。**盤を 180 度回し、全駒の
先後を入れ替え、駒台の割り振りも入れ替え、手番の文字も一緒に入れ替える。**
`Position` から正規形を作って渡す形にし、**元の `Position` は画像の向きのまま置いておく**
（画面に出ているものと、エンジンに渡すものが別で構わない。**ユーザに見せるのは前者**）。

- 取り込みの向きも「手前が先手 / 手前が後手」の 2 択。既定は**手前が先手**（中継の原則）
- **UI の手番は対局の先手/後手**（画面の上下ではない）。後手目線なら「後手番」＝
  手前が指す番、という関係になる
- ⚠️ **回す場所は `adoptPosition`（訂正 → 解析の境界）にした**（2026-08-18）。
  「エンジンに渡す直前」まで引っ張ると、**解析タブの盤・手順・棋譜・評価値が
  全部ひっくり返ったまま**になる（指した手の USI も先後が逆になる）。
  境界を 1 つ手前に置けば、そこから先は普通の局面として扱える
- ⚠️ **上の「表示視点」のトグルを流用しないこと。** あちらは見え方の好みで、
  こちらは**画像がどちら向きだったか**という別の事実。同じ 1 つの値に 2 つの意味を
  持たせると、盤を裏から眺めただけで局面が回る（あるいはその逆）


**案 B（USI クライアント方式）に決めた理由と Step の切り方は `CLAUDE.md` の Phase 4。**

## 層の分け方

| 置き場所 | 持つもの |
|---|---|
| `core/usi` | **プロトコルの語彙。** `info` 行 / `bestmove` 行の読み取り（`protocol.go`）と手表記 |
| `core/usi/client` | **USI クライアント本体。** ハンドシェイク・`position`/`go`/`stop`・`os/exec` での起動 |
| `ikkyoku/usi` | **Step 1 の足場だけ。** 同一プロセスの `engine` を `io.Pipe` で繋ぐ |
| `ikkyoku/analyze` | **評価値の意味づけ。** 先手視点への符号変換・候補手の畳み込み・接続の持ち回り |

- **クライアントは `core` に置いた**（2026-08-08 決定）。`engine` に置くと、
  やねうら王を起動したいだけの UI が**探索エンジン一式を import する**ことになり、
  依存が裏返る。`core` なら `ikkyoku` からも `prokishi` からも引ける
- **`core/usi` の JS 側（`core/web`）には対応物を置いていない。** USI を話すのは
  デスクトップアプリの Go 側で、ブラウザは構造化された結果しか見ないため。
  **ブラウザから USI を扱う必要が出たら、そのときに JS 側も揃えること**
- `prokishi/server` も `prokishi/usi.Sender` で同じことをしている（実運用でエンジンを
  起動している）。**今は触らない**が、重複しているので統合の候補
- ⚠️ **`io.Pipe` で同一プロセスの `engine` を繋ぐ部分は core に置けない**
  （`core → engine` の依存になる。向きは `engine → core`）。だから
  `ikkyoku/usi` に残っている

## 決まっていること（**崩さないこと**。テストで固定してある）

- ⚠️ **「best を問い合わせる同期 API」に丸めない。** `GetBestMove(sfen) → 指し手` まで
  畳むと Phase 5 の中核が最初から取れない ——**MultiPV が出せない**・**`info` の逐次
  ストリームを捨てる**・**`stop` で途中まで読んだ結果を使う**操作が表現できない。
  USI がステートフルなのは面倒に見えるが、**その面倒さがそのまま欲しい機能**
- ⚠️ **打ち切ったときに、一度出した候補より貧しい最終結果を返さないこと**
  （2026-08-11 に直した。実際に「秒数が過ぎた瞬間に候補手が全部消える」が起きた）。
  **最終結果が読めないのが一番困る。** 崩れていたのは 3 か所で、**どれも独立**:

  | 症状 | 原因 |
  |---|---|
  | 候補手（読み筋）が消える | **読み筋の無い info で上書きしていた。** エンジンは終わり際に「評価値だけの info」を出すことがある（`stop` の直後が特にそう）。順位ごとに**最後の読み筋を覚えて引き継ぐ** |
  | 候補が丸ごと消える / 一部が落ちる | `progressLocked` が順位を**「1 から本数まで」で回していた**。順位 1 が届いていないと空になり、本数を超える順位は黙って落ちる。**実際にある順位を並べ替えて返す** |
  | **三番手だけが残る**（頻発） | **深さが変わるたびに候補を全消ししていた**（下記） |
  | **最善手の読み筋だけが 1 手に化ける**（2026-08-13） | ⚠️ **`lowerbound` / `upperbound` の速報を取り込んでいた**（下記） |

### ⚠️ `lowerbound` / `upperbound` の info は捨てる（2026-08-13）

**探索の途中で「この手はこれ以上（以下）だと分かった」という速報**で、
**評価値は確定値ではなく、読み筋も 1 手しか付かないのが普通。** 取り込むと
**画面の読み筋がその 1 手に化ける**（実測: `+237 ▲９七角` だけが出て、その先が
消えた。**候補の 2 番手は正しく読み筋が出ているので、余計に分かりにくい**）。

- ⚠️ **USI のやり取りには正しい読み筋が流れているので、ログを見ても原因が
  分からない。** 「最後は手順があるのに消える」という見え方になる
- ⚠️ **`lastPV`（読み筋の無い更新で消さない仕掛け）では救えない** —— あれは
  「読み筋が**無い**」ときの話で、**1 手だけの読み筋は「有る」**ので通ってしまう。
  **`add` の入口で捨てるしかない**
- **捨てても損は無い。** 確定値は同じ深さのすぐあとに必ず来る（来なければ 1 つ前の
  深さの答えが残る。将棋 UI の一般的な挙動でもある）
- ⚠️ **自作 `engine` では出ない**（`lowerbound` を書かない）ので、**外部エンジンを
  繋いで初めて出る**。テストは `accumulator` に直接食わせて固定してある

### ⚠️ MultiPV の info は順位の順にも深さの順にも並ばない（2026-08-11）

**実測で `multipv 2` → `multipv 1` → `multipv 3` の順に、しかも深さがばらついて
届く。** 以前は「深さが変わったら候補を全部捨てる」だったので、**そのたびに 1 本だけの
状態に戻り、最後に来た順位しか残らなかった**（「三番手の手だけが残る」）。

**深さで候補を捨てないこと。** 代わりに**順位ごとに上書き**し、捨てるのは
**その順位が既に持っている答えより浅い報告**だけにする。

- ⚠️ **全体の深さと比べて捨てないこと。** 順位ごとに進み方が違うので、ある順位の
  **最初の報告**が他より浅いことは普通にある。全体と比べると**その候補を丸ごと落とす**
  （直そうとして一度これを踏んだ）
- **順位が更新されないあいだは 1 つ前の深さの値が残る。** 候補が消えるよりはるかに
  ましで、将棋 UI の一般的な挙動でもある。どの深さの答えかは **`Line.Depth`** に出す
  （見出しの「深さ」は一番深いところ。**候補ごとに違ってよい**）
- ⚠️ **`Line.Depth` はイベントのペイロードにも載る。** `mainscreen.ts` の
  `AnalyzeLine` は手書きなので、**Go 側を変えたらそちらも直す**
- ⚠️ **候補手は配列（`Progress.Lines`）。** 今の自作 `engine` は MultiPV を持たないので
  1 本しか来ないが、**それを異常扱いしないこと**。1 本でも一覧の形で出す
- ⚠️ **評価値は先手視点に直して返す。** USI の評価値は**エンジンの手番側**から見た値なので、
  そのまま出すと**後手番のときだけ符号が逆に見える**。符号を決めるのは `analyze` の責務で、
  **表示側で符号をいじらないこと**。`Score.Label`（"+230" / "▲詰 5手"）も
  Go 側で組み立てる（書式が 2 か所に散る）
- ⚠️ **詰みの検出に推定が要る。** 自作 `engine` は `score mate` を返さず、
  `MateScore - ply` の生値を `score cp` として出す（`engine/TODO.md` の 2）。
  そのため `analyze` が `engineMateScore`（`1<<20`）を**写して**推定している。
  **`score mate` を返すエンジンではそちらを優先する**ので、向こうが直れば定数ごと消える
- ⚠️ **`usinewgame` を落とさない。** 実際に送る並びは
  `usi` → `setoption` → `isready` → **`usinewgame`** → `position` → `go infinite`
  （ShogiHome の実機と同じ）。送らないと**前の局面の探索結果を引きずったまま次を読む**
  エンジンがある。ikkyoku では**局面ごとに 1 回**になる（プロセスが 1 回の解析で
  終わるため）が、**それが正しい** —— 渡すのは履歴を持たない独立した局面で、
  前の解析と繋がっていない（設計原則1）
- ⚠️ **`go movetime` に頼らない。** 自作 `engine` は解釈しない（`engine/TODO.md` の 3）。
  **常に `go infinite` で投げ、打ち切りは ikkyoku 側の `stop` で行う。**
  外部エンジンでも「こちらが時間を握る」ほうが揃う
- ⚠️ **玉の欠けた局面は原則エンジンに渡さない**（`ensurePlayable`）。合法手生成が
  玉の位置を前提にしているエンジンがある。**訂正 UI 側でこれを禁止しないこと**——
  詰将棋のような「玉が 1 枚しかない局面」も確定できるのが訂正 UI の要件。
  止めるのは**渡す瞬間だけ**で、盤を見ることも訂正することも学習に送ることもできる
- ⚠️ **例外は「片側の玉だけが無い局面」×「同梱エンジン」**（2026-09-12。詰将棋）。
  `Session.kingless` が持っている。**実測**（`engine/search` を直接叩いて確認）:
  **攻方の玉が無くても落ちず、1 手詰を詰みスコアで見つける**（`G*5b` / 1048575 =
  `MateScore-1`。**攻方の玉を隅に置いた版と手もスコアも一致**した ——
  つまり**玉を仮置きする意味は無い**）。
  - ⚠️ **外部エンジンには渡さない。** 両玉を前提にしているエンジンがあり、落ちるか
    出鱈目を返す。**実物で測っていないので安全側に倒す**（断るときは「同梱エンジンなら
    読めます」と次の一手を出す）
  - ⚠️ **通すのは「片側だけが 0 枚」のときだけ。** 両方無い局面は攻める相手が居らず、
    玉が 2 枚ある局面は駒数がおかしい（どちらも詰将棋ではない）
  - ⚠️ **詰将棋で意味があるのは「詰みかどうか」だけ。** 慣習で玉方が余り駒を全部持つので、
    **評価値は常に玉方の大優勢に出る**。数字を詰将棋の難易度として読まないこと
  - **長手数は通常探索では届かない。** そこまでは `Session.Mate`（下記）

#### 外部エンジンで詰将棋を解かせるとどうなるか（**2026-09-12 に実測**）

**やねうら王（水匠5・Suisho5 NNUE）で測った。** ⚠️ **この結果は再測しなくてよい。**

| 渡した局面 | `go`（通常探索） | `go mate` |
|---|---|---|
| **攻方の玉なし**（詰将棋そのまま） | **無反応**（`bestmove` すら返らない） | **無反応**（`checkmate` も返らない） |
| 攻方の玉を隅（1九）に置いた版 | **10ms で `score mate 1` / `bestmove G*5b`** | 同じ（`score mate 1`） |

- ⚠️ **「落ちる」ではなく「黙って返ってこない」。** `readyok` までは普通に進み、
  `position` も受け取り、そのあと何も出さない。**手前で弾いていないと解析が固まる**
  （`ensurePlayable` を外してはいけない理由がこれ）
- **`go mate` は要らない。** 玉さえ揃っていれば**通常の `go` でも詰みを返す**ので、
  `core/usi/client` に `checkmate` の口を足しても、この形では得るものが無い
- ⚠️ **「解析のときだけ攻方の玉を隅に仮置きする」案は採らない。**
  1 手詰では実害が無いが、**長手数では解が変わる** —— 詰将棋では玉方が余り駒を
  全部持っているので、**玉方が攻方の玉に王手をかけて手番を稼げてしまう**
  （攻方は応じるしかなくなり、詰め手順が別物になる）。**別の問題を解いて
  「解けました」と出すのが一番たちが悪い**
- **正しく長手数を解くなら詰将棋専用エンジン**（攻方の玉なしを前提にしている）。
  **入れた**（2026-09-12。`Session.Mate`）

#### `Session.Mate`（詰み探索）— **2026-09-12**

`position` → `go mate <ms>` → info… → `checkmate`（`core/usi/client.Session.Mate`）。

- ⚠️ **`ensurePlayable` ではなく `ensureMateTarget` を通す。** 条件が違う ——
  詰将棋は**攻方の玉が無いのが普通**なので、要るのは**詰ませる相手（玉方の玉）**だけ
- ⚠️ **手順（`moves`）は渡さない。** 詰将棋は**その局面だけで完結する**問題で、
  そこへ至る手順は答えに関係しない（`Analyze` とはここも違う）
- ⚠️ **時間はエンジンに伝える**（`go mate <ms>`）。**時間切れも答えの 1 つ**
  （「詰みなし」ではない）なので、**エンジン自身に言わせる**
- ⚠️ **答えは 5 通り**（`MateKind`）。**「詰みなし」と「時間切れ」を同じ扱いに
  しないこと**（後者は秒数を伸ばせば変わる）。
  ⚠️ **`already`（既に詰んでいる）を `mate` と混ぜないこと**（2026-09-12 に実機で
  踏んだ）—— **手順の無い `checkmate`** が返る形で、木に足すものが無く、
  画面に出す言葉も違う。**捨てると返事を待ち続けて時間切れになる**
  （「エンジンが checkmate を返しません」と出た）
- ⚠️ **候補は `MultiPV` で並ぶ**（`MateResult.Progress`。解析の候補手と同じ形）。
  詰将棋では別解＝**余詰**なので、**1 本目だけ返して終わりにしない**。
  ⚠️ **KomoringHeights は `isready` の前に送らないと MultiPV が効かない**（実測）——
  **探索時の `setoption` では候補が 1 本のまま**なので、エンジンの登録の
  `Options` に入れて接続時に送ること（`app` の `engineKey` が詰将棋エンジンでだけ
  MultiPV を指紋に入れているのはこのため）
- **手順の日本語表記は `core/kifu.FormatMoves`**（読み筋と同じ作り方。
  ⚠️ エラーは握る —— 読めない手があっても USI の手順は返す）
- **実測**（KomoringHeights 1.1.0）: 攻方の玉なしの 1 手詰・5 手詰とも数十 ms で
  `checkmate`。⚠️ **同梱エンジンは `checkmate notimplemented`**（`MateEngine`
  インターフェースだけで実装が無い）—— **経路が通ることはそれで固定してある**
- **正式な SFEN を要求するのはここだけ。** 手番か駒台の先後が未決なら
  `position.Position.SFEN()` がエラーを返すので、解析は始められない
  （設計原則5。ここで先手に倒すと、決めていない手番でエンジンが読む）。
  **これは警告ではなくエラー**——決めてもらう以外に手が無い
- **履歴（`moves`）は渡さない**（設計原則1）。引き換えに千日手・連続王手はエンジンが
  判定できないが、それは仕様として受け入れる
- **打ち切っても評価値は出る**（設計原則3）。`Stop` は「やめる」ではなく「ここまでで良い」
- **接続は使い回す**（`analyze.Session`）。局面ごとに繋ぎ直すと、Step 2 では毎回
  プロセス起動と `isready` を待つことになる。通信が切れたら捨てて次で開き直す
- **どのエンジンが答えたかを見せる**（`Result.Engine` = `id name`）。繋ぎ先を
  差し替えられる以上、評価値だけ出して出所を伏せると比べようがない
- **評価値の絶対値は当てにしない。** 自作 `engine` の PST は手作り・未調整


## ⚠️ エンジンのプロセスは解析タブに居るあいだ生きる（**2026-08-12 に変えた**）

```
解析タブに入る ─┐
                ├→ 起動 → setoption → isready ─┬→ usinewgame → position → go → bestmove ─┐
                                                └──────────────────────────────────────────┘
解析タブを離れる / アプリの終了 → quit
```

⚠️ **以前は「1 回の解析のあいだだけ生きる」だった**（2026-08-08 決定）。
**連続モードと連続解析が入って持たなくなったので変えた** —— 1 手ごとに解析し直す
ので、`isready`（NNUE の評価関数の読み込み。数秒になりうる）を**手数ぶん**払うことに
なり、151 手の棋譜を通しで解析すると待ち時間の大半がそれになる。

**元の決定の理由（待機中の `USI_Hash` は GB 級）は消えていない。** 消えたのは
「解析していないあいだ生かしておく」ことへの答えで、**寿命をタブの境界に置くことで
答えた**（`AnalyzeService.Release`）。**アイドルタイマーは持たない** ——
目に見える操作を境界にするほうが読める、という元の方針は変えていない。

- ⚠️ **1 接続 1 探索なので直列化が要る**（`analyze.Session.runMu`）。**前の
  `bestmove` が返る前に次の `position` を送ると噛み合わなくなる。**
  「止めて即次」を繰り返す**連続モードと連続解析がまさにこれを踏む。**
  待ちは有界（`client` が `stop` のあと `BestmoveGrace` で見切る）で、
  **待っているあいだに世代が進んでいたらその解析はやめる**（積み上がるため）
- ⚠️ **`setoption` は `isready` の前にしか効かない。** 毎回起こしていた頃は
  設定を変えれば自動で反映されたが、**今は繋ぎ直さないと効かない。**
  判断は `AnalyzeService.engineKey`（**パス + options の指紋**）で、
  ⚠️ **options を指紋に含めること** —— エンジンは黙って古い値で動くので、
  落とすと**画面では気づけない**
- ⚠️ **エラーで終わったら接続を捨てる**（`analyze.Session.drop`）。通信が切れた
  ときはもちろん、「`stop` を送ったのに `bestmove` が返らない」ときも
  **そのまま使い回すと次の探索ごと噛み合わなくなる**。捨てても次で開き直すだけ
- ⚠️ **解析タブを離れたら手放す**（`AnalyzeService.Release`）。**走っている解析
  （連続解析を含む）も止まる。** そこまでの評価値は残る（設計原則3）
- **「接続を確認」は確かめたら閉じる**（ここは変えていない）。押すのは設定タブに
  居るときで、そこから解析に入るとは限らない。**解析していないのにプロセスを残さない**
- **「ずっと解析していたい」は時間無制限の解析 1 回**（考える秒数を「無制限」にする）
- ⚠️ **起動にかかった時間は画面に出すこと**（`Result.StartupMS`）。見えないと、
  遅いのが探索のせいなのか起動のせいなのか分からない。⚠️ **使い回したときは 0 で、
  それは「速かった」ではなく「払っていない」**（`Result.Reused`）。
  **0 を「起動 0.0 秒」と書かないこと** —— 意味が 2 通りになって読めなくなる。
  ⚠️ **そのときは何も書かない**（2026-08-15。以前は「接続を使い回し」と出していたが、
  **2 回目以降は毎回そうなる**ので、ただ常に出ている文字になっていた）。
  **区別そのものは捨てない** —— ツールチップには残す
- ⚠️ **`usinewgame` は解析ごとに送り続ける**（使い回すようになっても）。送らなければ
  隣り合う局面で置換表が効いて連続解析は速くなるが、**前の解析の影響を受けた評価値**に
  なる（設計原則1）。**使い回しで消したかったのは `isready` のほうで、ここではない**
- ⚠️ **プロセスの ctx は解析の ctx から切り離す**（`analyze.Session.dial` の
  `context.WithoutCancel`）。`client.Exec` は `exec.CommandContext` で起こすので、
  解析の ctx をそのまま渡すと**「停止」を押した瞬間にプロセスが死に、`stop` に対する
  bestmove を受け取れない**。しかも**使い回す今は、1 回目の「停止」で接続ごと失う。**
  片付けは `quit` → kill の順で行う

## 読み筋は日本語表記で出す（**2026-08-10**）

`Line.Text` が `"▲２二角成"` の並び、`Line.Moves` が `"8h2b+"` の並び。
**画面に出すのは `Text`、手を辿るのに使うのは `Moves`。**

⚠️ **変換には局面が要る。** USI の手文字列に駒種は書いていない（`"8h2b+"` のどこにも
「角」は無い）ので、**8h に何が居るかを盤から読む**しかない。さらに `７八銀右` の "右" は
「同じ駒が他からも行けたか」を見ないと決まらないので**盤全体**が要る。

- **変換は `core/kifu`**（`NewNotation` / `FormatMoves`）。ikkyoku には書かない
  ——将棋の**仕様**は core に一本化する、の一例。注意点は core の CLAUDE.md にまとめてある
- **組み立てるのは `analyze`**（`accumulator.moveText`）。解析した局面の SFEN を持って
  いるのがここだけなので。⚠️ **フロントに移さないこと** ——盤が要る変換なので、
  フロントには材料が無い
- ⚠️ **表記に失敗しても読み筋を捨てない**（読めなかった手はその USI が `Text` に入る）。
  評価値は正しく出ているのに、表記の都合で候補ごと消えるのが一番困る（設計原則3）
- ⚠️ **フロントで `text` が空のとき `moves` に落とさないこと。** Go 側は失敗した手も
  USI のまま `text` に入れて返すので、`text` が空なのは「読み筋そのものが無い」ときだけ。
  落とすと、古い Go と繋いだときに**静かに USI 表記へ戻る**（気づけない）
- USI 表記は読み筋のツールチップに残してある（エンジンの出力をそのまま確かめたいとき用）


### 解析は `position sfen <根> moves ...` で渡す

⚠️ **組み立て直した 1 つの SFEN を渡さないこと。** 千日手と連続王手は手順が無いと
エンジンに判定できない。`StudyService.analyzeTarget` が根と手順を分けて返し、
`analyze.Options.Moves` がそのまま `client.Session.Analyze` に載る
（`go infinite` は元から。打ち切りは ikkyoku 側の `stop`）。

- ⚠️ **評価値の符号を決めるのは「解析する局面の」手番**であって、根の手番ではない
  （`analyze` が `len(Moves)` の偶奇で反転する）。**根のままにすると、奇数手進めた
  ときだけ符号が逆に見える** —— 画面を見ても気づけない壊れ方
- ⚠️ **読み筋の日本語表記も、まず手順ぶん盤を進めてから名付ける**
  （`accumulator.played`）。根からいきなり読み筋を流すと**別の盤の上で名付ける**
  ことになり、駒種も「同」も全部おかしくなる（USI のほうは正しいままなので
  やはり画面では気づけない）
- ⚠️ **`AnalyzeState.SFEN` には「解析する局面」を入れる**（根ではない）。
  手を進めても根は変わらないので、根を入れると**フロントが「局面が変わった」に
  気づけず、前の手の評価値が今の盤の上に残る**
