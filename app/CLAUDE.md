# app の CLAUDE.md

**フロントに公開する Service**（設定・訂正・解析・棋譜・駒の字・学習送信・計測）。
⚠️ **wails3 を import しない** —— Wails の口（ダイアログ・イベント）は `FilePicker` /
`EventEmitter` として `_cmd` から差し込む。⚠️ **`PositionService`（訂正タブ）と
`StudyService`（解析タブ）は別の局面**で、繋がるのは `Adopt` の 1 か所だけ。

⚠️ **「受け渡しは `Adopt` の 1 か所だけ」は訂正タブとの受け渡しの話。**
入力の口が増えること自体は想定どおりで、棋譜は訂正タブを経由せず
`StudyService.LoadKifu` が直接根を入れ替える（**棋譜の局面は初期局面と手順で
一意に決まる**ので、直すものが無い）。

- ⚠️ **棋譜を読んでも `PositionService`（訂正タブ）は触らない。** 撮った局面を
  消してしまうと、貼り付けたのが誤りだったときに戻る先が無くなる
- **指し手は全て載せるが、見ているのは開始局面**（2026-08-18 に最終手から変えた）。
  ⚠️ **最終手に置かないこと** —— 棋譜を読むのは**この対局を初手から解析するため**で、
  **連続解析の始点は「今どこを見ているか」**（`batchFrom`）なので、最終手に置くと
  **押す前に必ず開始局面まで戻る操作が要る**。先まで見たいときは盤の右の手順リストか
  評価値グラフで飛べばよい（`GoTo`。**手順は 1 手も消えない**）
- ⚠️ **取り直し（`ReloadKifu`）でも見ている位置は動かない**（2026-08-19）。
  読み込んだ直後は開始局面なので、**そのまま押しても開始局面のまま**。
  ⚠️ **`ReloadKifu` 側を「最後まで進める」に変えて辻褄を合わせないこと** ——
  **どこを見ているかはユーザーが選んだ状態**で、取り直しは
  「URL の側を正にする」操作でしかない。中継の最新手を見たいときは
  十字キーの下か手順リストで移る
- ⚠️ **途中で止まっても成功として扱う**（設計原則3）。読めなくなった手より前は
  正しいので、そこまでの局面は解析できる。理由は `KifuLoad.Note` に出し、
  **フロントで「note が空でない＝エラー」にしないこと**
- **KIF の読み取りも指し手 → USI の変換も `core/kifu`**（`Parse` / `DecodeMoves` /
  `StartSFEN`）。**ikkyoku にもフロントにも書かない** —— 将棋の**仕様**は core に一本化する。
  ikkyoku 側（`position.FromKIF`）がやるのは「読めた手を 1 手ずつ `Study` に指させる」
  というアプリ側の組み立てだけで、**合法性の判定は `Study.Play`（＝ `legal`）が持つ**
  ので、壊れた棋譜はそこで止まる
- ⚠️ **変化（`変化：N手`）は `core/kifu.Parse` が未対応**なので本譜だけが載る。
  分岐ツリーが入るまではこのまま（木の形は core で決める）
- ⚠️ **盤面図（BOD）つきの KIF は未対応。** 途中局面から始まる棋譜は
  手合割から初期局面を決められないので読めない（対応するなら `core/kifu.Parse` 側）


#### URL から取る（`_cmd/ikkyoku/kifufetch.go` → `kicho/scrape`）

`StudyService.LoadKifuURL` が取ってきて、あとは貼り付けと同じ経路に合流する
（**読み込んだあとの処理を 2 つに分けない**）。実測で
`http://live.shogi.or.jp/oui/kifu/67/oui202607290101.kif`（王位戦）が
151 手そのまま載ることを確認済み。

- ⚠️ **取得はフロントではなく Go 側。** webview の `fetch` は CORS で弾かれるうえ、
  **中継の .kif は Shift_JIS** なので、どのみちブラウザ側では読めない
- ⚠️ **文字コードは中身から判別する**（UTF-8 として妥当ならそのまま、駄目なら Shift_JIS）。
  **UTF-8 決め打ちにしないこと** —— 対局者名が化けるだけでなく、
  **漢数字が壊れて指し手が 1 手も読めなくなる**。何として読んだかは画面に出す
- ⚠️ **http / https 以外は受けない。** `file://` を通すと URL 欄から手元のファイルを
  読めてしまう（ファイルの読み込みは口として別に作るもの）
- ⚠️ **HTML が返ってきたら、そこに書かれた .kif を辿る**（2026-09-04。
  `scrape.KifURLFromHTML`。それまでは「棋譜ではない」と断っていた）。
  **これが無いと、棚から解析タブへ送った中継棋譜を「再読み込み」で追えない** ——
  連盟の中継の `source_url` は**中継ページ（HTML）の URL** だから。
  ⚠️ **ページから対局内容を読み取るわけではない**（取り込むのは .kif の原本）
- ⚠️ **辿った先ではなく、指定された URL を覚えること**（kicho の `source_url` と
  同じ扱い）。中継ページの `KIF_FILE_NAME` が一次情報で、**.kif のパスは変わりうる**
- **上限 4MiB・タイムアウト 20 秒。** 棋譜 1 局は数十 KB なので、
  これで足りないのは相手が居ないときだけ
- ⚠️ **中身の解釈は `kicho/scrape` に寄せてある**（2026-09-04 に `ikkyoku/kifuweb` を
  畳んだ）。文字コードの判別（`DecodeKIF`）・上限つきの読み取り（`ReadLimited`）・
  HTML から .kif を辿る（`LooksLikeHTML` / `KifURLFromHTML`）はどれも向こうの実装。
  ikkyoku 側に残っているのは http/https の制限と HTTP の取得だけ
- ⚠️ **`kicho.Library` を経由していない。** あちらは棋譜データベースを開けていないと
  使えないが、**URL から棋譜を読むのは棚に依らない操作**（設計原則3）。
  **`KifuService` 経由に書き換えないこと** —— DB が壊れると貼った棋譜も読めなくなる

##### 再読み込み（`StudyService.ReloadKifu`）— **2026-08-13**

**同じ URL を読み直して、URL の側を正にする**（解析タブの**手順の見出し**の
**「手順」の真横にある更新アイコン**。2026-08-15 に「再読み込み」の文字ボタンから
変えた）。中継の .kif は 1 手進むたびに書き換わるので、**取り直せること
自体が「本譜は URL が更新し続ける」という一番よくある使い方の前提**
（`TODO.md` の「本譜のロック」）。

```
                      一致している範囲 │ 食い違ったところから先
今の手順   ７六歩 ３四歩 ２六歩 ８四歩 │ ５六歩（自分で指した）
URL の側   ７六歩 ３四歩 ２六歩 ８四歩 │ ６八銀 …
評価値     残す   残す   残す   残す   │ 捨てる
```

- ⚠️ **入力タブから読み直させないこと。** あちらは `LoadKifu` が根ごと入れ替える
  ので、**評価値が全部消える**（同じ URL を読んでも別の対局として扱われる）。
  取り直しの口を別に立てているのはそのため
- ⚠️ **解析結果はそのまま残す**（これがこの口の理由そのもの）。捨てるのは
  **食い違ったところから先だけ**で、根が違えば（＝別の対局）全部捨てる
- ⚠️ **食い違いが無ければ `evalStore.dropAfter` を呼ばないこと。** あれは世代
  （epoch）を進めるので、**走っている解析の途中経過まで捨てる** ——
  1 手進むたびに押す使い方では毎回それが起きる
- ⚠️ **見ている位置は動かさない**（2026-08-19。**取り直す前に選んでいた手が
  そのまま選択状態で残る**）。据え直しでは節点が 1 つも消えないので、
  行き先は必ず生きている。⚠️ **最後の手を見ていたときも進めないこと** ——
  以前は「伸びた先の最後まで進める」だったが、その判定は**深さ**
  （`Ply() >= len(MainLine())`）でしか見ておらず、**枝は本譜より深くなり得る**ぶん
  「最後の手」と誤判定して、**枝を見ている最中に取り直すと本譜の終わりへ
  飛ばされていた**（実測で踏んだ）。⚠️ **「深さではなく本譜の最終手か」で
  直す形にも戻さないこと** —— 中継の最新手へ移るのは 1 操作
  （十字キーの下・手順リスト）で、**勝手に飛ぶほうが取り返しがつかない**
- ⚠️ **今は「捨てる」で済んでいるが、それは分岐ツリーがまだ無いから。**
  木が入ったら**捨てるのではなく別の枝として残す**ことになる。
  **直す場所は `mergeReloadLocked` の 1 か所**にしてある
- ⚠️ **取れなかった / 読めなかったときは今の手順を壊さない**（組み立てが通って
  から入れ替える）。中継が落ちても検討は続けられる
- ⚠️ **ボタンを出す条件は `StudyState.SourceURL`**（URL から読んだときだけ埋まる）。
  **入力タブの URL 欄を見ないこと** —— 欄はいつでも打ち換えられるので、
  **今の手順がどこから来たか**とは別物。⚠️ **根を入れ替えたら捨てること**
  （撮った局面・貼り付け・新規対局には取り直す先が無い）
- ⚠️ **置き場所は「手順」の真横**（2026-08-15）。**取り直す相手はその手順**なので、
  見出しの隣に置いて位置で対象を示す（連続解析を手順の見出しの行へ移したのと同じ）。
  右へ寄るのは連続解析のボタンだけ（CSS の `margin-left: auto`。⚠️ **`.field-label`
  側に `margin-right: auto` を戻さないこと** —— 見出しの直後で空くと、間に
  アイコンが挟まらない）
- ⚠️ **アイコンだけなので、意味は `aria-label` と `title` が持つ。**
  ⚠️ **`title` を空にしないこと**（文字が無いぶん、何のボタンかはこれでしか読めない）
- ⚠️ **`display: flex` は `hidden` に勝つ。** 打ち消し（`.icon-btn[hidden]`）を
  落とすと、**撮った局面でも取り直しのアイコンが出る**（押しても取り直す先が無い）。
  `<shogi-board hidden>` で踏んだのと同じ話
- **取り直している最中はアイコンを回す。** 文字が無くなったぶん、
  **押した手応えがアイコンにしか出せない**（理由は下の行にも出るが、目はボタンを見ている）
- **差し替えが起きたら文字で出す**（`KifuLoad.Note`）。自分で指した手が消えるので、
  **黙って済ませない**

#### 新しく対局を始める（`position.NewGame` / `StudyService.NewGame`）— **2026-08-13**

**何もないところから初期局面を作る。** 入力タブの「新しく対局を始める」で、
**手合割 → 解析タブ**。棋譜と同じ扱いなのは、**初期局面が手合割で一意に決まる**から
（直すものが無いので訂正タブを通らない）。

```
入力タブ ──手合割──> StudyService.NewGame ──> position.NewGame ──> core/kifu.StartSFEN
                                                                        （初期局面はここだけ）
```

- ⚠️ **初期局面を ikkyoku に書かない。** 手合割 → 盤面は将棋の**仕様**なので
  `core/kifu.StartSFEN` の 1 か所だけが持つ。書き写すと、**棋譜から読んだ平手と
  新規で作った平手が食い違いうる**（しかも画面では気づけない）。
  **フロントにも書かない**
- ⚠️ **`FromFullSFEN` で読む**（`FromBoardSFEN` ではない）。持ち駒まで書いてある
  局面なので `HandsFixed` が立つ。**落とすと駒落ちの根が SFEN を組み上げられない**
- **駒落ちは今すぐ通る**（`core/kifu` が香落ち〜十枚落ちを持っている）。
  **UI の option を足すだけ**で、Go 側は 1 行も変えなくてよい。テストでも
  二枚落ちを固定してある。⚠️ **上手（後手）が初手**なので手番は後手番
  （`w` + 手数 1 は正当な局面。先手に倒さないこと）
- ⚠️ **詰将棋はここには来ない。** 初期局面が無い（人が並べる）ので**別の口**になり、
  行き先も**訂正タブ**（自由に置ける盤が要る）。**ここに空の盤を作る option を
  足さないこと** —— 確定した局面を解析タブへ渡す、というこの経路の意味が崩れる
- ⚠️ **知らない手合割を平手に倒さない**（`core/kifu.StartSFEN` もそうしている）
- ⚠️ **`PositionService`（訂正タブ）は触らない**（棋譜と同じ。撮った局面が
  戻り先として残る）。始め損ねても前の局面を壊さないことはテストで固定してある
- ⚠️ **「あなたの手番」は Go 側に渡していない。** 今それが決めているのは
  **視点（画面の向き）だけ**で、平手の初期局面はどちらを持っても同じ。
  **対局モード**（人が片側を持ち、エンジンがもう片側を指す）を入れる段になったら、
  この選択がそのまま「自分の側」になる —— **先回りして未使用の欄を作らない**
- **戻り値は `KifuLoad` を共有している**（フロントの描き方が同じ＝根を入れ替えて
  解析タブを開き、1 行の説明を出す）。**別の経路を作らないこと**

- **訂正タブに居ること自体が訂正モード。** トグルは廃した（`editor.ts` の
  `setEditing` は無い）。**モードを戻さないこと** —— タブが意味の境界になっている
- **受け渡しは `StudyService.Adopt` の 1 か所だけ。** 確定しているかの判定も
  そこがする（`position.Position.SFEN()` が組み上がるか）。⚠️ **フロントで同じ
  判定を書かない**（2 か所に散る）
- **解析タブ → 訂正タブへ戻れる。** 戻って直し、もう一度確定すればよい。そのとき
  **前の手順と解析結果は捨てる**（別の局面の話になるため）。捨てるのは `Adopt` が
  根ごと入れ替えることで担保しており、フロントの片付けに依存していない
- ⚠️ **撮っても解析タブは消さない**（2026-08-22 に変えた。それまでは撮れた時点で
  `StudyService.Clear` していた）。**撮ることと、解析している局面を捨てることは
  別の操作** —— **訂正した局面を suteme へ送るために撮る**使い方（学習データを
  育てるループ。「決定: 訂正した局面は学習にも回す」の節）では、撮るたびに
  検討が消えると**解析しながら盤を追加する**ことができない。棋譜を読んで解析して
  いる最中に 1 枚撮ったときも同じで、**あちらは訂正タブを通らない入口**なのに
  巻き添えで消えていた。
  - ⚠️ **捨てるのは「この局面を解析する」を押したとき**（`StudyService.Adopt` が
    根ごと入れ替える）。**そこが訂正タブと解析タブの唯一の継ぎ目**なので、
    撮った時点で先回りして消す必要が無い。**`showShot` に戻さないこと**
  - **走っている解析は止まる**（撮ると訂正タブへ移り、`selectTab` がエンジンを
    手放す）。⚠️ **そこまでの評価値は残る** —— タブを移ったときと同じ約束
  - ⚠️ **「古い評価値が今の 1 枚に対する評価に見える」は残る懸念だが、
    それは訂正タブの話ではない** —— 撮ったあと開くのは訂正タブで、解析タブには
    その局面の盤・SFEN・手順が出ている。**採るまでは別の局面**という元からの
    線引き（`PositionService` / `StudyService`）そのもの

## 棋譜データベース（棚）— **kicho をライブラリとして使う**（2026-09-04）

**`ikkyoku` は「ユーザ環境で動く将棋ソフト」**なので、棋譜のデータベース化も
ikkyoku から使えないと**ユーザが ikkyoku と kicho の 2 つを立ち上げる**ことになる。
そこで kicho の UI が持っていた機能（取得 / 登録 / 蔵書）を ikkyoku へ移した。

kicho の UI は将来「テスト用のモック」または
「ikkyoku 以外の将棋ソフトからの読み込み口」になる。

```
入力タブ ─ 貼り付け/URL ─┬─ 読み込む ────────────────→ 解析タブ（棚に入らない）
                        └─ 棚に登録する ─┐
入力タブ ─ 中継から取得 ─ カード ─ 保存 ──┤
                                        ↓
                                 kicho.Library ─→ store(SQLite)
                                        ↑
                        棋譜タブ（棚）─ 検索 ─「解析する」──→ 解析タブ
```

`kicho.Open(dbPath, logger)` は**dbPath が空でなければ kicho 側の `settings` を
見ない**し、HTTP サーバも作るだけで起動しない（`httpapi.Server.Stop` は未起動でも安全）。

⚠️ **移行の直後は kicho を 1 行も変えずに済ませたが、その形は維持できなかった**
（2026-09-07 に整理）。当時は `kicho.Library.Store()` で `*store.Store` を直接触っており、

- 実質の公開 API が `store` パッケージ全体になっていた
- **保存の組み立てが 2 か所に分かれていた** —— 取得元ごとの `source_url` の決め方、
  文字コードの既定、手数の数え方を ikkyoku と `kicho/_cmd/kicho` がそれぞれ持ち、
  片方だけ直せば黙って割れる状態だった（実際 kicho 側は読売の `source_url` を
  入れ忘れていた）

いまは **`Store()` は無く、蔵書の操作も取得元の知識も `kicho.Library` にある**。
ここに書くのは DTO の変換と入力チェックだけ。

### 崩してはいけない線引き

1. ⚠️ **棚は解析の前提条件にしない。** `kicho.Open` が失敗してもアプリは起動し、
   撮った 1 局面と貼った棋譜は解析できる（設計原則3）。**棋譜タブだけ**が理由を
   出して機能しない。判断は `KifuService.library()` の 1 か所で、
   **どのメソッドも同じ文言を返す**（読めないと設定タブへ辿り着けない）
2. ⚠️ **棚に入るのは KIF の原本だけ。** 検討ツリー（`position.Study`）も評価値も
   入れない（kicho の「原本を保持する。整形し直さない」原則そのもの）。
   Phase 5 の決定「検討ツリーは永続化を前提にしない」も生きている。
   ⚠️ **仮の一覧（`watches`）はこの例外ではない** —— あちらが残すのは
   「どのサイトのどの棋譜か」だけで、**KIF 本文を持たない**（後述）
3. ⚠️ **ikkyoku で伸ばした枝を KIF に書き戻さない。** 棚の KIF は
   **実際に現れた指し手**で、エンジンの読み筋や自分で指した手ではない
   （`TODO.md` の「本譜のロック」と同根）
4. ⚠️ **取得元の知識をこちらに書かない。** 取得元ごとの `source_url` の決め方、
   文字コードの既定、手数の数え方、「再読み込みで取り直せる URL か」の判断、
   **「仮の一覧に載せられる取得元か」**は
   **kicho 側**（`kicho.Fetched` / `Library.Save` / `Library.Watch` / `RefetchableURL`）。
   同じ変換を `kicho/_cmd/kicho/kifuservice.go` も持つので、こちらに書くと必ず割れる。
   足りないものが出たら **kicho の `Library` に足す**（`Store()` は無い）。
   直したら kicho 側で `.\check-consumers.ps1` を流すこと
5. ⚠️ **DTO は `app` にローカルに持つ**（`GameSummary` / `GameDetail` /
   `SearchQuery` / `SearchResult` / `WatchEntry`）。
   `store.Record` / `store.Watch` をそのままフロントへ出さないこと ——
   bindings に kicho の型が漏れると、向こうのスキーマ変更がフロントに直撃する
6. ⚠️ **ikkyoku は HTTP サーバを持たない**（`ServerService` は移していない）。
   kicho の UI の「棋譜 URL をコピー」「取得 URL をコピー」は**外部ツール
   （ShogiHome 等）へ渡すため**のもので、ikkyoku では渡す先が自分自身。
   **代わりに置いたのが「解析する」**。⚠️ **URL コピーを戻すなら、先に
   「ikkyoku がサーバを持つか」を決めること**
7. ⚠️ **エラーは文言比較で分岐しない。** kicho は**「画面と文言は使う側にある」
   という前提で sentinel を公開している**（`ErrNoInput` / `ErrEmptyKifu` /
   `ErrNotKifu` / `ErrUnsupportedSource` と `store.ErrNotFound` /
   `ErrSchemaTooNew`）。**種類だけ向こうから貰い、何をすればよいかはこちらが書く**
   （`describeKifuError` / `describeOpenError` の 2 か所）。
   ⚠️ **kicho の文言を書き写さないこと** —— `%w` で包んで足すだけにする。
   写すと向こうを直してもこちらだけ古い言い方で残る
   （実際 `SendToStudyGame` が「棋譜が空です」を手書きで持っていた）
8. ⚠️ **一覧の上限を「並んだ件数」として画面へ渡さないこと。**
   `Library.Search` が丸めるのは **Limit が 0 か上限超えのときだけ**で、
   呼び出し側が指定した `Limit` はそのまま効く。`MaxSearchRows`（500）を
   決め打ちで返すと、**1 件しか並べていないのに「500 件だけを表示しています」**と
   出る。返すのは `SearchResult.Shown`（＝実際に並んだ行数）で、
   **切ったときはそれが適用された上限そのもの**なので丸め方を写さずに済む

### kicho を抱えると付いてくるもの

`kicho.Library` を import した時点で、ikkyoku のバイナリには次が入る。

| 依存 | 何のため |
|---|---|
| `modernc.org/sqlite` | 棚（PureGo。cgo 不要） |
| `github.com/dop251/goja` | **読売のペイロード評価** |
| `golang.org/x/net/html` | 読売の対局ページから iframe を辿る |
| `golang.org/x/text` | Shift_JIS の判別 |

⚠️ **goja は第三者サイトの JavaScript を ikkyoku のプロセス内で実行する。**
読売の `_payload.js` は Nuxt の IIFE で、値が引数リストの変数として共有されているため
文字列パースでは解けず、JS として評価するしかない（理由は kicho の CLAUDE.md）。

- 盤面キャプチャ・エンジン・解析と**同じプロセス**で動くことは認識しておく
- kicho 側に `vm.Interrupt` による 10 秒のタイムアウトがある。**外さないこと**
- ikkyoku から呼ぶ経路は「中継から取得」（`KifuService.Fetch` / `Refresh`）だけ。
  貼り付け・URL 取り込みは goja を通らない

### 棚の呼び出しには必ず制限時間を付ける

⚠️ **`context.Background()` をそのまま `kicho.Library` へ渡さないこと。**
kicho の `store` は接続を 1 本に絞っているので、止まらないクエリが 1 つあると
**以後の棚の操作が全部待たされる**（画面からは「棚が反応しない」に見える）。

`KifuService` の `kifuDBContext()` / `kifuNetContext()` を通す
（DB は 10 秒、サイトへの取得は 60 秒）。

### DB の場所

**既定は `os.UserConfigDir()/ikkyoku/kicho.db`**（`Config.KifuDB` の 1 か所で解決）。
設定タブ「棋譜データベース」で任意のパスを指せるので、**kicho アプリの DB
（`%APPDATA%\kicho\kicho.db`）を共用**できる（開発時に確かめやすい）。

- ⚠️ **既定を kicho と同じにしないこと。** `store` の `SetMaxOpenConns(1)` は
  **プロセス内**の直列化でしかない。プロセスをまたぐ競合には kicho 側で
  WAL と `busy_timeout` を入れてある（2026-09-07）ので即 `database is locked` には
  ならないが、**共用を勧める状態ではない**。ユーザーが設定で指定したときだけにする
- ⚠️ **kicho と ikkyoku は別バイナリなので DB のスキーマ版が食い違いうる。**
  片方だけ更新した状態で同じ DB を指すと `store.ErrSchemaTooNew` で開けない
  （黙って開いて後段が `no such column` で落ちるより良い、という判断）。
  **実際に 2026-09-08 に v4 へ上がった**（仮の一覧 / `watches`）——
  `replace` で相対参照している以上、**ビルドし直せば揃う**
- ⚠️ **存在チェックをしない**（SQLite は無ければ作る）。まだ無い場所を先に書く
  順序が普通にある（エンジンのパスとはそこが違う）
- ⚠️ **変えたその場で開き直す**（`SettingsService.onKifuDBPath` → `KifuService.open`）。
  **`SettingsService` から DB を直に触らないこと**（棚を持っているのは `KifuService`）
- **開けているかは設定ではなく状態**なので `KifuService.Status` から取る
  （設定は「どこを開こうとしているか」、状態は「開けたか」）

### 二系統を残す（**貼り付け／URL の行き先**）

⚠️ **「棚に入れる」と「保存せず解析する」は別操作。** 入力タブの
「棋譜を貼り付ける」には**同じ入力欄に対して 2 つのボタン**がある。

| ボタン | 行き先 | 棚 |
|---|---|---|
| 読み込む / URL から読み込む | **解析タブ**（`StudyService.LoadKifu` / `LoadKifuURL`） | 入らない |
| 棚に登録する | **棚**（`KifuService.ImportKIF` / `ImportURL`） | 入る。**解析タブは触らない**。⚠️ **`ImportURL` は `Fetch` + `Save`**（2026-09-12）—— `kicho.Library.ImportURL` は何を渡しても `source` が `url` になるので、**連盟・読売の URL で中継としての ID を捨てる** |

- ⚠️ **入力欄を 2 つに増やさないこと。** 同じ入力の**行き先が 2 つある**だけで、
  欄を分けると「どちらに貼ったか」で挙動が変わる面になる
- ⚠️ **登録してもタブは移らない。** 登録は「あとで探せるようにする」操作で、
  今すぐ見るなら「解析する」。**代わりに棋譜タブの一覧は取り直す**
  （反映されていないと、登録できたのか分からない）

### 棋譜タブ（棚）

移植元は kicho の「棋譜一覧」タブ（`_cmd/kicho/frontend/src/App.tsx` の `LibraryTab`）。

- 行の操作は **「解析」（左端）/「削除」（右端）** で、**詳細は棋戦名のリンク**
  （2026-09-12 に「表示」ボタンを廃止）
- ⚠️ **タブを開くたびに棚を読み直すこと**（`selectTab` → `libraryUI.reveal()`）。
  同じ DB を kicho アプリからも触れるので、**初回だけ読む作りにすると
  向こうで足した棋譜が見えない**（共用にした意味が消える）
- ⚠️ **検索は打つたびに走らせない**（Enter か「検索」）。**3 文字未満は索引
  （FTS5 trigram）が効かず全件走査になる**ので、そのことを案内する。
  ⚠️ **案内は打っている途中に出さない**（2026-09-12）——
  **検索を走らせたときだけ、見出し（棋譜一覧の横）に出す。**
  検索欄の下に置いて 1 文字ごとに出し入れしていた頃は、**下の表が動いていた。**
  ⚠️ **文字数は `MinSearchLength`（＝ `store.MinTrigramLen`）を写すだけ** ——
  **判定そのものは Go 側**で、フロントを検索の条件に使わないこと
- ⚠️ **削除の確認は `window.confirm` ではなく `popup.ts`**（初期フォーカスは
  「やめる」。手順を消すときと同じ）
- **詳細はモーダル**（2026-09-12。それまでは一覧の下に開いていた）。
  ⚠️ **KIF の本文は画面に出さない** —— 150 手を流すと詳細だけで画面が埋まる。
  持ち出す口は**「KIF をコピー」だけ**で、渡すのは**原本のまま**（整形し直さない。
  棚の中身と食い違わせない）。⚠️ **クリップボードは Wails ランタイム**
  （`navigator.clipboard` はカスタムスキーム配信の webview では当てにできない）

### 中継から取得（入力タブのカード）

移植元は kicho の「取得」タブ。読売（竜王戦）のスクレイピングと
日本将棋連盟の棋譜中継（.kif の直取得）の 2 つで、**取り方は違うが
カードに積む・更新する・保存する、の扱いは同じ**（判別も取得も Go 側）。

- ⚠️ **取得は 1 件だけ持つ設計にしない。** 同じ日に 2 局以上進むこと（並行対局、
  複数局を交互に追う）があるので、取得のたびにカードを 1 枚積む（新しいものが先頭）
- ⚠️ **同じ棋譜を取り直したらカードを増やさない。** key（`{取得元}:{棋譜 ID}`）が
  一致するカードは**位置と「保存済み」を保って中身だけ差し替える**
  （`mergeCard`）。⚠️ **取得元も key に含めること** —— 棋譜 ID の形が取得元ごとに
  違う（読売は 24 桁の ID、連盟は中継のパス）
- ⚠️ **保存は画面の内容をそのまま書き込む**（サイトへ取り直しには行かない）。
  そのため**保存済みで手数が変わったら「保存し直す」よう促すこと** ——
  黙っていると「更新＝保存」だと誤解される
- ⚠️ **「閉じる」で消えるのは画面のカードと仮の一覧だけ。棚の棋譜は消えない。**
  棋譜タブの「削除」と見た目が同じ赤いボタンなので、**文言で分ける**
- ⚠️ **日本将棋連盟の中継はここで扱うこと。** 上の「棋譜を貼り付ける」の URL 欄から
  入れると `source_id` が毎回 UUID になり、取り込むたびに別の棋譜として増える

### 中継そのものを覚えておく（仮の一覧 / `watches`）— **2026-09-08**

**2 日制の対局では翌日また中継の URL を貼り直すことになる。** それを避けるため、
取得カードを棚の DB（`watches`）に残して**再起動後に並べ直す**。
kicho 側の実装で、ikkyoku は `Library.Watches / Watch / Unwatch / UnwatchAll` を呼ぶだけ。

⚠️ **残すのは「サイト」であって棋譜ではない。**

| 持つもの | 持たないもの |
|---|---|
| `source` / `source_id` / `source_url` | **KIF 本文** |
| 一覧で見分けるためのメタ（棋戦名・対局者・開始日時・手数・終局種別） | 手合割・場所・文字コード |

メタは**表示用の写しであって原本ではない**（原本は取り直せば取れる）。
⚠️ **棋譜そのものを残すのは「この内容を保存」（棚）の役目で、役割を混ぜないこと。**

```
取得 / 更新 ──> mergeCard（画面）──remember──> KifuService.Watch ──> 棚の watches
起動 ────────> KifuService.Watches ──> cardFromWatch（本文は空）
```

- ⚠️ **復元ではサイトへ取りに行かない。** 起動のたびに追跡ぶんの通信が走ると
  待たされるうえ、**中継を追っていない日でも毎回外へ出ることになる。**
  中身はカードの「**更新**」で取り直す（復元直後なら「**取り直して解析**」が
  1 回で済ませる）。⚠️ **まとめて回す口は置かない**（2026-09-12 に「すべて更新」を
  外した）—— **カードは 2〜3 枚が普通**なので 1 枚ずつでよく、**サイトへ順に
  投げる制御を抱える理由が無い**
- ⚠️ **復元しただけのカードでも「解析する」は押せる**（2026-09-09。
  ラベルは**「取り直して解析」**に変わり、押すと
  **先に `Refresh` してから送る**）。⚠️ **以前は押せなくしていたが、
  その理由は「送っても必ず失敗する」（`SendToStudyGame` の `ErrEmptyKifu`）
  だけだった** —— 取り直してから送れば消える理由なので、
  人に「更新 → 解析」と 2 回押させない
  - ⚠️ **「この内容を保存」は今までどおり押せないまま**（`isRestored` ＝ 本文が空）。
    **保存は画面の内容をそのまま書き込む操作**なので（上の「保存は画面の
    内容をそのまま書き込む」）、**ここで取り直しに行くとその約束が崩れる**
  - ⚠️ **本文があるカードでは取り直しに行かないこと。** 送るのは
    「いま画面に出ているこの内容」で、最新手を追うのは「更新」か
    解析タブの「再読み込み」の役目
  - ⚠️ **取り直しているあいだはボタンにそう出す**（「取り直しています…」）。
    外へ取りに行くので数秒かかる —— **「解析する」と同じラベルにしないこと**
    （押したところで通信が始まるとは読めない）
  - ⚠️ **取れなかったときは解析へ進まないし、理由を書き直さないこと**。
    取得の失敗を「送れなかった」で上書きすると、
    **取得と送りのどちらで失敗したのかが分からなくなる**
  - ⚠️ **これは kicho に無い分岐**（あちらに「解析する」は無い）
  - ⚠️ **取り直しの本体は `fetchInto` の 1 か所**（「更新」も「取り直して解析」も
    ここを通る）。**busy の出し入れは押した側が持つ** ——
    `fetchInto` が自分で解くと、**取り直しを終えた瞬間に
    解析を待たずボタンが押せるようになる**
- ⚠️ **判定に別のフラグを持たせないこと。** 本文の有無で見れば、更新して中身が
  入った瞬間に自動で外れる（フラグだと復元扱いのまま残る道ができる）
- ⚠️ **載せられるのはライブ中継（読売・連盟）だけ。** 貼り付け・URL 取り込みは
  取得元での一意な ID を持たず `source_id` が毎回 UUID なので、復元しても
  「更新」が必ず失敗するカードになる。**判断は kicho**（`ErrUnsupportedSource`）で、
  **ここに取得元ごとの分岐を書かないこと**
- ⚠️ **載せ損ねても取得結果は画面に残すこと。** 今日の作業は続けられるので
  失敗にはせず、**「仮の一覧に無し」の札**を出して「再起動すると消える」ことだけ伝える
  （黙っていると「昨日のカードが無い」の理由が分からない）
- 一覧から外れるのは次の 2 つ。**どちらも棚の棋譜（`games`）には触らない。**

  | 操作 | 動き |
  |---|---|
  | カードの「閉じる」 | `Unwatch`。⚠️ **外さずに閉じると再起動で戻ってくる** |
  | 終局済みの棋譜を「保存」 | `Library.Save` が自動で `Unwatch` |

  ⚠️ **「クリア」（`UnwatchAll`）は画面から外した**（2026-09-12）。
  **1 枚ずつ「閉じる」で足りる**（カードは 2〜3 枚）うえ、
  **「閉じる」は赤くて問い合わせがあるのに、全部消すクリアは問い合わせ無し**
  という不揃いな操作だった。⚠️ **`KifuService.UnwatchAll` は残してある**ので、
  戻すなら**「閉じる」と同じ作法（問い合わせ）にすること。**

- ⚠️ **終局していないときは保存しても外さない**（2 日制なら 1 日目の封じ手時点で
  保存しても翌日また同じカードで追う）。**分岐を持っているのは kicho の `Save`** で、
  フロントは `rec.finished` を見て札を落とすだけ。**こちらで判断し直さないこと**
- ⚠️ **既に無いものを外すのは失敗にしない**（`KifuService.Unwatch` が
  `store.ErrNotFound` を飲む）。終局後の保存では kicho が先に外しているので、
  エラーにすると**カードが閉じられなくなる**
- ⚠️ **棚を開き直したとき（設定タブ）に復元し直していない。** 復元はメタだけで
  カードを作り直すので、**今日取ったカードの本文（KIF）を捨てることになる。**
  閉じれば新しい棚からも外れる（無ければ何も起きない）ので実害は無い
- ⚠️ **`GameDetail` を返す形にしないこと**（`WatchEntry` を別に持っている）。
  本文の欄に空文字を詰めて返すと、**「棋譜が取れている」ように見える**

### ⚠️ 解析タブの「再読み込み」に渡せる URL は取得元による

棚（または取得カード）から解析タブへ送るとき、**取得元の URL も一緒に渡す**と
解析タブの「再読み込み」で中継の最新手を追える。**が、全部の取得元では渡せない。**

| 取得元 | `source_url` | 取り直せるか |
|---|---|---|
| `shogilive` | 中継ページ（HTML） | **○**（`KifURLFromHTML` で .kif を辿る） |
| `url` | 指定された .kif | **○** |
| `yomiuri` | 棋譜ビューアのページ | ⚠️ **×**。Nuxt のページで .kif が無い（KIF は `_payload.js` から組み立てている）。**取り直す口は取得カードの「更新」** |
| `paste` | 空 | —（取り直す先が無い） |

⚠️ **判断は kicho の `RefetchableURL` の 1 か所。フロントにも ikkyoku にも
書かないこと**（取得元ごとの知識は向こうが持つ。上の「取得元の知識をこちらに
書かない」）。
取り直せない URL を渡すと**再読み込みのアイコンが出るのに押すと必ず失敗する**、
という画面からは理由の分からない壊れ方になる。


### 取り込みの向き（**入っている**。2026-08-18）

中継は「先手が手前」が原則だが、**ゲーム画面では自分（後手）が手前のことがある。**
その画面を認識すると、後手の駒が正立して見えるので `suteme` は「先手の駒」と分類し、
盤の上下も逆のまま返す。

⚠️ **これは手番や駒台の未決と違って、黙って間違う。** 出てくる盤面は自己矛盾が無いので
**警告も出ないし信頼度も落ちない**（「決まっていない」と言えるものですらない）。
訂正 UI でも直せない（右クリックの先後反転を 40 枚やっても盤の上下は直らない）。
**だから目線はトグルとして要る。**

入口は**訂正タブの「手前: 先手」ボタン**（**盤のすぐ下**。`#edit-view-row`。
押すたびに先手 ⇄ 後手が入れ替わる）。

⚠️ **解析タブの「手前: 先手」（表示視点）と字面が同じだが、別物。**
あちらは**盤の絵を裏から見るだけ**（SFEN は 1 文字も変わらない）、こちらは
**撮った画像がどちら向きだったかという事実**（押すと解析へ渡す局面が回る）。
**それでも位置で書くほうがよい** —— 「目線」だと**盤が反転すると思われる**
（この盤は 1 マスも動かない）。**どちらなのかはツールチップが言う。**

⚠️ **手番・手数と同じ行に並べないこと**（2026-08-18 に出した）。**盤面から
決まらないもの**という点では手番・手数と同類だが、**言っている事実が違う**
（どちら側から写したか / どちらが指す番か）。同じ見た目のボタンが隣り合っていると
**同じものの選択肢に見える**うえ、⚠️ **訂正タブの表示視点（「手前: 先手」）とも
紛らわしかった** —— そちらは**ボタンごと外した**（「表示視点」の節）。
⚠️ **盤のすぐ下に置くこと** —— 言っているのは「この盤がどちら向きか」なので、
盤から離すと何に対する設定なのか分からなくなる。

```
訂正タブ（撮ったとおり）──┬─ 盤・駒台・LabelSFEN … **回らない**（学習ラベルは画素と一致）
                          └─ 目線 = 後手 ──> adoptPosition ──> Rotate180 ──> 解析タブ
```

- ⚠️ **盤は 1 マスも動かない。** 効くのは**解析へ渡すときに回すかどうか**だけで、
  回すのは `PositionService.adoptPosition` の 1 か所（`position.Rotate180`）。
  **訂正タブの盤・駒台・`LabelSFEN`（suteme へ送るラベル）は撮った向きのまま**
- ⚠️ **手番とは独立**（「手番がどちらか」「目線がどちらか」の 2 つの事実）。
  **画面に出す手番は対局としての先後**で、目線を切り替えても**変わらない**
  （後手番 × 後手目線なら手前から指す・先手番 × 後手目線なら奥から指す）。
  ⚠️ **`Position` が持っているのは「見た目の手番」**（盤と揃えてある）なので、
  **目線を切り替えたら中の手番のほうを入れ替える**（`SetViewpoint`）。
  翻訳は `positionservice.go` の中だけ（`asSeenTurn` / `gameTurn`）。**散らさないこと**
- ⚠️ **駒台の角の ▲/△ は `EditState.SeenTurn`（見た目の手番）で光らせる。**
  ▲ は**上向きに写っている側**に付いているので、後手目線では `Turn` と逆になる。
  **`Turn` を渡さないこと** —— 後手目線のときだけ光る側が入れ替わる
- ⚠️ **訂正タブの駒台の見出しは「手前の駒台」「奥の駒台」**（2026-08-18。
  以前は「先手」「後手」）。後手目線では手前に写っているのが後手なので、
  そこに「先手の駒台」と書いてあると**画面が嘘をつく**。**位置なら目線に
  関わらず必ず正しい**（手番マークのツールチップも同じ言い方に揃えてある）。
  ⚠️ **表示視点を反転したら言い直すこと**（`showHandLabels`）—— 駒台ごと
  入れ替わるので、**位置で説明しているのに位置と食い違う**
- ⚠️ **盤の駒の名前（「先手の歩」）は見たとおりのまま。** 訂正タブは
  **撮った画像を直す面**で、学習ラベルもこの向き。
  ⚠️ **そのぶん ▲ が光っているのに「後手番」を選んでいる、が普通に起きる**ので、
  手番マークのツールチップでは**先後を言わず**「この側が指します（後手番）」と出す
- ⚠️ **黙って回さない。** 画面の局面とエンジンが読む局面が上下逆になるので、
  **後手目線のときだけ SFEN の後ろに「（解析へは反転して送信）」と添える**
  （`#sfen-note`。全文＝`EditState.AnalyzeSFEN` は `title` に出す）。
  ⚠️ **行を増やさないこと**（2026-08-18 に「解析へ」の行から変えた）——
  後手目線のときだけ行が増えると、**出たり消えたりするたびに下のボタンが上下に
  ずれて押しづらい**。⚠️ **目線のボタンの横にも出さないこと**（同じ理由で
  ボタンそのものがずれる）
- **目線は撮り直しても残る**（`Load` で捨てない）。同じ中継・同じゲーム画面を
  続けて撮るのが普通なので、1 枚ごとに選び直させない
- ⚠️ **表示視点（`flip`）を流用していない。** あちらは見え方の好みで、
  こちらは**画像がどちら向きだったか**という事実（上の A/B の表）


## エンジンの登録（設定タブ）— **複数登録できる**（2026-08-11）

**繋ぎ先は設定の問題**にしてある（`ikkyoku.Config` の `engines`）。
**1 つに絞らない** —— 登録は一覧で、`enabled` を付けたものが**解析のときに同時に走る**。

```json
{ "engines": [
    { "id": "engine-1", "name": "やねうら王", "path": "D:/shogi/YaneuraOu.exe",
      "options": { "USI_Hash": "1024", "Threads": "4", "EvalDir": "eval" }, "enabled": true },
    { "id": "builtin", "enabled": true }
  ] }
```

- **なぜ複数か。** どのエンジンが正しいかは局面によって違うので、**評価が食い違う
  ところを並べて読めること**自体が「別の選択も一つの局として辿る」という構想に効く。
  同じ exe を **option 違いで 2 つ登録**して比べるのも正当な使い方（だから鍵はパスではなく `id`）
- ⚠️ **`engines` が空なら同梱エンジン 1 つ**として扱う（`Config.EngineList`）。
  設定ファイルを作っていない状態でも解析できる、という既定の挙動を変えないため。
  **「空だったら同梱」を呼び出し側に書かないこと**（判断が 2 か所に散る）
- ⚠️ **旧形式（`engine: { path, options }`）は読み込み時に `engines` へ移す**
  （`migrateEngines`。移したら旧欄は捨て、次の保存でファイルからも消える）。
  **移行を落とすと、設定してあった外部エンジンが黙って同梱に戻る**（画面には何も出ない）
- ⚠️ **「外部エンジンを使う」の真偽値は持たない。** **パスが空なら同梱、入っていれば外部。**
  2 つ持つと「パスが入っているのに無効」という食い違いが起きる
- **`enabled` を外しても登録は消えない。** エンジンを入れ替えて比べる作業では、
  外したものをまた戻すことが多い。**全部削除すると同梱エンジン 1 つに戻る**
  （解析できない状態に落とし込まない）
- **並べ替えられる**（各行の ▲▼。`SettingsService.MoveEngine`。2026-08-12）。
  **一覧の順序は表示の順序そのもの** —— 解析タブのエンジンごとの結果も、
  評価値グラフの折れ線も、勝率バーが最初に出すエンジンもこの順で決まるので、
  **よく見るものを上に置けること**は要る。
  - ⚠️ **順序は「優先度」ではない。** 上が正しいという意味も、先に走るという意味も
    無い（**解析は全部同時に走る**）
  - ⚠️ **「解析に使う」を外した登録も含めた一覧の中で動かす。** 走るものだけを
    詰めて数えると、**チェックを外した瞬間に見えている順番と食い違う**
  - ⚠️ **端で回り込ませない**（一番上を上げたら一番下へ飛ぶ、では驚く）。
    端の行はボタンを**押せなくする** —— 押しても何も起きないと、壊れているのか
    端なのかが区別できない
  - ⚠️ **押したあとフォーカスをそのボタンに戻すこと**（行ごと描き直すため）。
    戻さないと**1 つ動かすたびに押しにいくことになる**
- **`name` は表示名。空なら既定を解決する**（`EngineEntry.DisplayName`）:
  **`name`（人が付けた）→ `engineName`（エンジンが名乗った）→ パスのファイル名 →
  「同梱エンジン」。**
  ⚠️ **エンジンが `id name` で名乗る名前とは別物** —— あちらは繋いで初めて分かるので、
  繋ぐ前の見出しと、同じ exe を 2 つ登録したときの区別にこちらが要る。
  UI は既定の名前を **placeholder に出し、value には入れない**（入れるとパスを
  変えても名前が追従しなくなる。Go 側が `custom` を返しているのはこのため）。
  ⚠️ **そのぶん「値ではない」と見えること**（2026-09-08。**実際に「編集できない」と
  誤解された**）—— ここの placeholder は案内文ではなく**そのまま値になりうる名前**
  なので、色を落とすだけでは足りず**斜体**にしてある（`.engine-name::placeholder` /
  `.font-row-name-input::placeholder`）。⚠️ **他の欄まで斜体にしないこと**
- ⚠️ **名乗り（`engineName`）を既定の表示名にしてある**（2026-09-08）。
  `YaneuraOu_NNUE-tournament-clang++-avx2.exe` より、エンジン自身の名乗りのほうが
  読める。**繋いだ時点で控える**（`AnalyzeService` の「接続を確認」と解析の完了 →
  `SettingsService.rememberEngineName`）。
  - ⚠️ **人が付けた名前より前に出さないこと。** 同じ exe を option 違いで 2 つ
    登録すると**名乗りは同じ**になるので、**見分けが付くのは人が付けた名前だけ**
  - ⚠️ **設定ファイルに控えること**（メモリだけで持たない）。名乗りは繋がないと
    分からないので、**閉じた時点で消えると次の起動では二度と出てこない**
    （exe のファイル名に戻る）
  - ⚠️ **変わっていなければ書かないこと。** 解析が終わるたびに呼ばれるので、
    素通しにすると**1 手ごとに設定ファイルを書く**（連続解析では手数ぶん）
  - ⚠️ **実行ファイルを差し替えたら捨てること**（`OptionSpecs` と同じ扱い。
    別のエンジンの名乗りなので、残すと**違うエンジンの名前を出す**）。
    **人が付けた `name` のほうは捨てない**
  - ⚠️ **解析タブの見出しで名乗りを括弧で足すのは、`label` と違うときだけ**
    —— 一度繋いだあとは `label` 自体が名乗りなので、**同じ名前が 2 回並ぶ**
- **パスは手で打たせない**（`SettingsService.BrowseEngine` が追加、`BrowseEngineFor` が
  行の差し替え。⚠️ **この 2 つを混ぜないこと** —— 差し替えのつもりで登録が増える）。
  将棋エンジンは深いディレクトリに置かれるので、打ち間違いが一番起きやすい入口。
  テキスト欄も残してあるのは、貼り付けと確認のため
- **保存と接続の確認は別の操作。** まだ置いていないパスを先に書く順序が普通にあるので、
  保存時に起動はしない（**存在の確認だけ**する。打ち間違いは「解析を押したら繋がらない」
  より早く分かるほうがよい）。実際に起こすのは「接続を確認」（`AnalyzeService.CheckEngine(id)`）
- ⚠️ **「接続を確認」は 1 行ずつ。** まとめて起こすと、どれが遅くてどれが落ちたのかが
  分からない（複数を同時に起こすのは解析のときだけ）。結果も**その行に出す**
- **確認で繋いだ接続はそのまま解析に使う。** 確かめるためだけに起こして捨てると、
  直後の解析でまた起動を待つことになる
- **`options` は画面から設定できる**（2026-08-15。設定タブの行の折りたたみ
  「エンジンの設定」）。詳しくは下記「エンジンの option を画面から設定する」。
  ⚠️ **設定ファイルを手で編集する経路も残す** —— 宣言していない option を
  受け付けるエンジンがあるので、**画面から選べる範囲と、受け付ける範囲は別物**
  （折れ線の色と同じ扱い）
- ⚠️ **`options` は `isready` の前に送る**（`core/usi/client.Open`）。置換表の確保も
  評価関数の読み込みも `isready` で走るので、**後から送っても間に合わない**。
  しかもエンジンは黙って既定値で動くので、間違えても画面では気づけない
- **エンジンが `usi` で宣言した option には、`options` に書いていなくても既定値を送る**
  （将棋 UI の一般的な作法。`core/usi/client.plannedOptions`）。`options` に書いた値は
  その位置で差し替わる。**button と、既定値が空のものは送らない**
- **「接続を確認」は宣言と送信の件数を出す**（`option 42 件を宣言、38 件を送信`）。
  ⚠️ **`setoption` には応答が返らない**ので、効いているかを確かめる手掛かりがこれしかない
- **設定は解析を始めるたびに読む。** プロセスが 1 回の解析で終わるので、
  変えた結果が次の解析にそのまま効く（**繋ぎ直しの判断が要らない**）
- **終了時に走っている解析を打ち切り、エンジンが終わるまで待つ**（`main.go` の `quit`）。
  ⚠️ **待たないとプロセスが残る**（Windows では親が消えても子は道連れにならない）

### エンジンの option を画面から設定する（**2026-08-15**）

**「接続を確認」でエンジンの宣言を読み、その型どおりの入力欄を出す**
（設定タブの行の折りたたみ「エンジンの設定」）。

```
接続を確認 ──> client.Open ──> Session.Options ──> EngineEntry.OptionSpecs（宣言の控え）
   （繋ぐ）                       （宣言）              │
                                                       ├──> 設定タブの入力欄
解析 ──> engines[].options（値）──> setoption ─────────┘
```

⚠️ **宣言（`OptionSpecs`）と値（`Options`）は別物。混同しないこと。**
宣言は「このエンジンは何を受け付けるか」、値は「そのうち何をどう変えたか」。

| 型 | 入力欄 |
|---|---|
| `check` | チェックボックス |
| `spin` | 数値（`min`/`max` つき） |
| `combo` | 選択（`var` の並び） |
| `string` / `filename` | テキスト |
| `button` | ⚠️ **設定できない**（下記） |

- ⚠️ **宣言を控えるのが要点**（`EngineEntry.OptionSpecs`）。宣言はエンジンに繋がないと
  分からないので、控えないと**設定タブを開くたびにエンジンを起こす**ことになる
  （NNUE の読み込みで数秒かかるものがある）。**控える入口は `CheckEngine` の 1 か所**
- ⚠️ **保存の操作では繋がない**（元の線引きを変えていない）。だから
  **繋いだことのない登録には入力欄が出ない** —— そのとき出すのは
  「まだ読んでいない」であって「宣言が無い」ではない（`EngineSettings.OptionsKnown`。
  **同梱エンジンは本当に 1 つも宣言しない**ので、この 2 つは区別が要る）
- ⚠️ **既定と同じ値は書き残さない**（空にしたときと同じ扱いで消す）。エンジンが
  宣言した option には**書いていなくても既定値が送られる**ので、書き残すと
  「エンジンの既定に従う」という指定ができなくなり、**バージョンが上がって既定が
  変わっても古い値で固まる**（しかも画面では気づけない）
- ⚠️ **button は値を持たない**（送ること自体が「押した」という動作）。押せる相手は
  **繋がっているエンジン**だけで、設定タブには居ない（接続は解析タブに居るあいだしか
  生きていない）。**設定として保存しないこと**——画面には出すが押せなくしてある
- ⚠️ **値を検分するのは宣言があるときだけ**（範囲外の spin・選択肢に無い combo・
  true/false でない check）。**`setoption` には応答が返らない**ので、間違った値を
  送っても**画面では気づけない**。入れた瞬間に断るほうが早い
- ⚠️ **宣言に無い名前も受ける。** 宣言していない option を受け付けるエンジンがあり、
  設定ファイルを手で編集する経路も残してある。画面では「宣言に無い項目」として
  出し、**消す口だけ用意する**（黙って捨てない）
- ⚠️ **実行ファイルを差し替えたら宣言を捨てる**（別のエンジンの宣言なので、
  残すと**違うエンジンの入力欄**を出す）。**値のほうは捨てない** —— 置き場所を
  移しただけのことがあるうえ、人が書いた値を黙って消さない
- ⚠️ **変えた値は繋ぎ直さないと効かない**（`setoption` は `isready` の前にしか
  効かない）。判断は `AnalyzeService.engineKey`（パス + options の指紋）が持っている
  ので、**`SettingsService` から接続を触らないこと**
- ⚠️ **入力欄の形も既定値も範囲も選択肢も Go 側が渡したものを使う。**
  フロントに型ごとの表を書かないこと（`DisplayName` / 折れ線の色と同じ）
- **折りたたみは既定で閉じる。** やねうら王級だと option が 40 件を超えるので、
  開きっぱなしだと一覧そのものが読めない。⚠️ **見出しに件数を出すこと**
  （畳んだままでも既定のままかどうかが分かる必要がある）。**中は高さを頭打ちにして
  スクロールさせる** —— 素直に並べると設定タブが縦に伸びきって、下の設定へ辿り着けない
- ⚠️ **開いている状態はフロントだけが持つ**（`openOptions`）。一覧は保存のたびに
  描き直されるので、**覚えておかないと値を 1 つ変えるたびに閉じる**


## `AnalyzeService`（`_cmd/ikkyoku/analyzeservice.go`）

- **局面を持たない。** 解析するのは常に「今 `StudyService` が持っている**確定局面**」で、
  **フロントから SFEN を受け取らない**。渡してもらう形にすると、採り直した直後に
  古い局面を解析する経路ができる（フロントに局面の写しを持たせない方針と同じ）
- ⚠️ **`PositionService`（訂正タブ）を直に見ないこと**（2026-08-10）。駒を自由に
  動かせる状態の盤は「まだ決めていない局面」で、その評価値には意味が無い。以前は
  訂正モードかどうかをフロントが見てボタンを止めていたが、**タブを分けたことで
  構造上そこに手が届かなくなった**
- **解析する局面は 1 つ、エンジンは複数**（2026-08-11）。設定で「解析に使う」を
  付けたエンジンぶんの goroutine を起こし、**同時に走らせる**。
  ⚠️ **1 エンジン 1 プロセス・1 接続**（USI は 1 接続で 1 探索なので、束ねようがない）。
  ⚠️ **エンジンをまたいで結果を合成しないこと**（平均も多数決も取らない。並べて人が読む）
- ⚠️ **1 つのエンジンが落ちても他は続く**（設計原則3）。`analyze:failed` は
  **そのエンジンの**失敗で、解析全体の失敗ではない。**他の結果を消さないこと**
- **新しく始めると前の解析は全部打ち切る。** 打ち切った解析の途中経過は
  **後から届く**ので、`Seq`（解析の世代）でフロントが捨てる。
  **この仕組みを外さないこと**（古い局面の評価値が新しい盤の上に出る）
- ⚠️ **打ち切った世代が畳まれるまで待ってから始めること**（2026-09-09。
  `Start` の `cancelGrace`）。待たないと**前の世代の探索が `runMu` を掴んだまま**
  次が積み上がり、**1 つの接続に局面の違う探索が何本も並ぶ** ——
  連続解析では「他の手も同時に解析している」「そのうち止まる」という形で出た。
  ⚠️ **待ちは有界にすること**（`bestmove` を返さないエンジンで固まる）。
  見切ったら重なったまま始める（始められないよりまし。設計原則3）
- ⚠️ **done には「考える時間を使い切ったか」を載せる**（`Interrupted`）。
  **`Stopped` では区別できない** —— 時間切れもこちらから `stop` を送って
  終わるので、あれは普通に考え切ったときも立つ。**頼んだ秒数に届いたか**で見る
  （`interruptSlack` は往復ぶんの遊び）。⚠️ **連続解析がこれで止まる** ——
  打ち切られた解析も done を出す（設計原則3）ので、**無いと「1 手ぶん終わった」と
  読んで次の手へ進み、手数ぶんが数秒で流れる**
- ⚠️ **止めるときは全部止める**（同じ局面を比べるために走らせているので、
  片方だけ生かす意味が無い）。「全部終わった」ときだけ解析中の表示を解く
- 途中経過はイベント。`analyze:info` / `analyze:done` / `analyze:failed`。
  ⚠️ **どれにも `engineId` が載る。** 複数のエンジンが同時に喋るので、

### 局面が変わったら知らせる（`study:changed`）— **2026-09-08**

**`StudyService` は局面を変えるたびにイベントを流す。** `app.Event.Emit` は
**アプリ全体**に届くので、**呼んでいない窓もこれで気づける**。

```
以前:  メイン画面 ──GoTo()──> StudyService ──戻り値──> メイン画面が描く
今:    メイン画面 ──GoTo()──> StudyService ─┬─戻り値──────> 呼んだ窓がその場で描く
                                            └─study:changed─> **全部の窓**が描く
```

⚠️ **ペインを別ウィンドウへ切り離すための土台**（2 枚目・3 枚目の窓はこれに乗る）。
**今は見た目が 1px も変わらない** —— メイン画面は今までどおり戻り値でも描いており、
イベントは自分の描いた版と同じなので弾かれる。

- ⚠️ **変えたら必ず出すこと。** 出す場所は `Adopt` / `LoadKifu`（＝`loadKifuFrom`）/
  `LoadKifuURL` / `ReloadKifu` / `NewGame` / `Play` / `AddLine` / `Branch` /
  `Promote` / `DropFrom` / `GoTo` / `Clear`。**足したメソッドで忘れると、
  そこだけ別の窓が更新されない**（画面からは「たまに古い」に見える）
- ⚠️ **失敗したときは出さない**（状態は変わっていない）。判断は `publish` の 1 か所
- ⚠️ **ロックを外してから出すこと。** 先はフロントなので、ロックを持ったまま渡すと
  そこから戻ってきた呼び出しと噛み合う余地がある。**`defer` は LIFO** なので、
  各メソッドの**先頭**に `defer func() { s.publish(...) }()` を置いて
  `s.mu.Unlock()` より後に走らせている。**登録の順番を入れ替えないこと**
- ⚠️ **`StudyState.Rev`（版）を落とさないこと。** イベントと戻り値は**別の経路**なので
  **順番が入れ替わりうる** —— 受け取る側は「**既に描いた版より新しいときだけ描く**」で
  弾く（`mainscreen.ts` の `studyRev`）。無いと、十字キーで手を続けて辿ったときに
  **古い局面が後から届いて盤が戻る**
- ⚠️ **`rev` を進めるのは `changed()` だけ。** 読むだけの `state()` では進めない ——
  進めると**何も変えていないのに全部の窓が描き直す**
- ⚠️ **棋譜の読み込みは「取得元まで入った 1 回」で出すこと**（`loadKifuFrom` に
  一本化した）。以前は `LoadKifu` が読んでから取得元を入れ直していたので、
  イベントにすると**取得元が空の状態が 1 回ぶん外へ漏れる**
  （別の窓で再読み込みのアイコンが出たり消えたりする）
- ⚠️ **`Emit` が nil でも動くこと**（設計原則3）。呼んだ窓は戻り値で描けるので、
  効かなくなるのは**窓どうしの連動だけ**
- ⚠️ **評価値グラフ用のイベントは足していない。** あちらは `analyze:info` /
  `analyze:done`（既にアプリ全体へ流れている）＋この `study:changed` で足りる
