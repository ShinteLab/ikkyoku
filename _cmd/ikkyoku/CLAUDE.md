## GUI アプリ(Wails3)

`_cmd/ikkyoku/` に置いてある。数値で座標を指定する方式（盤面に枠を合わせる操作では
実用的ではない）の代わりに、画面に重ねる透過ウィンドウで領域を視覚的に合わせられるようにしたもの。
**現状 `ikkyoku` は「ルートパッケージ（ライブラリ）＋この GUI アプリ」の 2 つだけの構成で、
CLI は無い。**

- **独立したネストモジュール**（`kicho/_cmd/kicho`・`prokishi/_cmd/prokishi-server` と同じ構成）。
  `module ikkyoku`、`replace github.com/ShinteLab/ikkyoku => ../../` でルートパッケージを参照する
- **Wails のバージョンは手元の CLI に追従している。** このディレクトリを作った時点の CLI は
  `v3.0.0-beta.3` だった（`wails3 skill` が前提にしている `alpha2.117` より新しい）。
  ⚠️ **2026-09-08 時点では CLI も `go.mod` も `v3.0.0-beta.16`**（この節の
  「手元の CLI は beta.3」は古い記述だった）。**下に出てくる beta.3 の話は
  そのとき確かめたもの**で、beta.16 で再確認はしていない。
  `wails3 init` の `-t vanilla` フラグは **beta.3 では無視され、常に React テンプレートが
  生成される**（実機で確認したバグ）。そのため `wails3 init -t vanilla` の出力を
  React 抜きの vanilla TypeScript に手作業で作り直してある。将来 CLI を上げたときは
  この制約が直っているか確認すること
- **UI は素の DOM 操作で書く（React でアプリを組まない）。** ただしアイコンに
  `react-icons` を使っており、その描画のためだけに `react` / `react-dom` が入っている。
  react-icons が配るのは React コンポーネントで、SVG 文字列を取り出す公開 API が無いため、
  `frontend/src/icon.ts` が `react-dom/server` の `renderToStaticMarkup` で
  **マウント時に一度だけ**静的マークアップへ変換して `innerHTML` に埋める。
  **React の使用箇所はここだけ**（クライアント側の react-dom ランタイムは読み込まれない）。
  アイコンを増やすときも `iconMarkup()` を通すこと
- Wails 依存は `_cmd/ikkyoku/` にのみ置く（`ikkyoku` 側は触らない）。
  `Capture` / `SavePNG` / `DefaultOutDir` / `ParseHotkey` / `DefaultHotkey` を
  そのまま import して使っており、ロジックを再実装していない

### ウィンドウ構成(5枚)

将棋盤に重ねる透過ウィンドウの中に操作用の UI を置くと、その UI 自体がキャプチャに
写り込んでしまう。これを避けるため **ウィンドウを分けてある**（`main.go`）。

| ウィンドウ | URL | 役割 |
|---|---|---|
| 枠(`frame`) | `/?window=frame` | Frameless・透過。上部のツールバー(▼/□/カメラ/✕)とガイド枠だけを描く。**「どこを撮るか」の定義そのもの**。**起動時は出さない** |
| メイン画面(`main`) | `/?window=main` | アプリ本体。5 タブ。**起動するとこれが出る**（入力タブ）。**こちらも Frameless**（下記） |
| **評価値グラフ(`graph`)** | `/?window=evalgraph` | **解析タブから切り離したグラフ**（2026-09-08）。**普通のタイトルバーを持つ**（下記）。**閉じてもアプリは終わらない**（ドックに戻るだけ） |
| **候補手(`side`)** | `/?window=study` | **解析タブから切り離した候補手の面**（警告・解析の行・エンジンのカード。2026-09-08）。扱いは `graph` と同じ |
| **手順(`moves`)** | `/?window=moves` | **解析タブから切り離した手順の面**（見出しの行・手順のツリー。2026-09-12）。⚠️ **中身は `side` と同じモジュール**（`studyscreen.ts` が両方をまかなう）。⚠️ **連続解析を持っているのは `side`** —— こちらのボタンは持ち主へ頼むだけ |

⚠️ **切り離した 3 つ（`graph` / `side` / `moves`）は解析タブと一緒に出し入れする**
（2026-09-12。`CaptureService.SetStudyTabActive` → `syncPaneWindows`）。
**どれも解析タブの中身**なので、他のタブに居るあいだ出しておいても読む相手が居ない
（起動直後の入力タブも同じ）。⚠️ **設定（`config.json`）は触らない** —— やるのは
`Show`/`Hide` だけで、**タブに戻れば同じ形で出し直す**。詳しくは `_docs/ui/detach.md`。

**メインは枠ではなくメイン画面。** 枠は位置合わせが済めば用済みになりうる道具で、
アプリの寿命を握る画面ではない。

#### ⚠️ メイン画面も Frameless（**2026-08-12**）

**OS のタイトルバーを外し、その場所にタブの行を上げた**（`.main-toolbar` が
タイトルバーそのもの）。**狙いは縦の領域** —— 「タイトルバー + タブの行」で 2 段
使っていたところが 1 段になる。解析タブの盤は `100vh` から引いて決まるので、
**そのぶん盤が大きくなる**（`--board-size` の引き算も 92px → 82px に減った。
**両方が効く**）。

- ⚠️ **タブの行に物を足さないこと。** ここはタイトルバーなので、**アプリ名も
  状態メッセージも出さない**（窓の識別はタスクバーが持っている）。積めば
  そのぶん盤が小さくなる、という関係は今までと同じ
- ⚠️ **選択中のタブは下の面と地続きに見せる**（2026-08-22 に変えた）。
  それまでは丸い入れ物の中で**選択中だけが明るい**（セグメンテッド
  コントロール）だったが、**タブという見た目が約束しているのは
  「その紙を手前に引き出した」こと**なので、選んでいる 1 枚がパネルと
  同じ色になり、境界線がそこだけ途切れているのが本来の形
  （実際、`.tab` に `border-radius: 5px 5px 0 0` を付けて
  「線に乗っている見え方にする」と書きながら、入れ物のほうは
  セグメンテッドだったので、**2 つの作法が半々で混ざっていた**）
  - ⚠️ **選択中が「一番暗い」ことになるが、それで正しい。**
    この画面はパネルの地色（`#1b1d23`）が一番暗いので、
    **選んでいないタブのほうを浮かせて**前後を付ける。
    **選択中を明るくし直さないこと** —— 明るくした瞬間に
    「面から浮いた 1 枚」に戻り、**どのパネルに繋がっているのかが見えなくなる**
  - ⚠️ **タブの行をタイトルバーの下端に揃えること**（`.tabs` の
    `align-self: stretch` + `align-items: flex-end`）。**線に接していないと
    切れない**ので、この見せ方そのものが成立しない
  - ⚠️ **選択中と選んでいないタブで寸法を 1px も変えないこと。**
    選択中だけに枠線 1px と `margin-bottom: -1px` が付くので、
    そのぶん padding で戻してある。崩すと**切り替えるたびに文字が動く**
  - **高さは変わっていない**（34px）ので、`--board-size` の式には無関係
- ⚠️ **高さは固定**（34px）。内容で伸びると `--board-size` の式と食い違い、
  **盤が縦にはみ出す**
- ⚠️ **余白は `.main-screen` ではなく `.panel` が持つ**（14px 16px を移した）。
  ツールバーは**画面の端まで届いていないといけない**（掴める帯が途切れる）
- **移動は `--wails-draggable: drag`、リサイズはランタイムのウィンドウ端の検出。**
  ⚠️ 押せるもの（`.tabs` / `.win-controls`）は **`no-drag` に戻すこと** ——
  戻し忘れるとクリックが効かなくなる（枠の `.frame-actions` と同じ話）。
  ⚠️ どちらも `main.ts` の素の `import "@wailsio/runtime"` が前提
- **最小化 / 最大化 / 閉じるは自前**（ツールバー右端の `.win-controls`）。
  ⚠️ **✕ はランタイムの `Window.Close()` ではなく `CaptureService.Quit`**
  —— 自前のボタンは `WindowClosing` を通らないので、**位置・サイズが保存されない**。
  終了時の後始末は Go 側の 1 本（`quit`）に寄せてある。`registerMainHooks` の
  `WindowClosing` フックは Alt+F4・OS シャットダウン用に残す
- **タイトルバーのダブルクリックで最大化 / 元に戻す。** macOS ではランタイムが
  capture 段階で横取りして自分で `ToggleMaximise` を呼ぶので、**二重に切り替わらない**
- ⚠️ **枠と違って `DisableFramelessWindowDecorations` は付けない。** あちらは中継映像に
  重ねる透過ウィンドウなので影も角丸も邪魔だったが、こちらは普通のアプリの窓で、
  影と角丸が無いと**どこまでがウィンドウか分からなくなる**

#### ⚠️ 起動時に出るのはメイン画面（**2026-08-10 に入れ替えた**）

以前は**枠だけが出て、最初のキャプチャでメイン画面が現れる**という導線だった。
**入力の口が画面キャプチャだけではなくなる**（SFEN / KIF / 画像ファイル）ので、
「撮ること」を前提にした導線をやめた。**枠は「撮るときだけ使う道具」**の位置づけ。

- 起動すると**メイン画面が入力タブで出る**。**枠は出ない**
- **枠を出す入口は「枠を表示」だけ**（`CaptureService.ShowFrame`）。
  ⚠️ **置き場所はタイトルバー**（2026-08-18 に入力タブから上げた。下記
  「枠を出すトグルはタイトルバー」）
- ⚠️ **枠が出ていなければ撮れない**（`CaptureService.Capture` の `requireFrame`）。
  技術的には隠れていても HWND は生きているので撮れてしまうが、**「今どこを撮るのか」が
  画面に出ていないまま撮れるのは事故のもと**なので、**見えていることを撮れる条件に
  してある**（2026-08-10 決定）。断るときは「枠を表示」を促す文言を返す。
  ⚠️ **`FitFrame` にこの門番を掛けないこと** —— あちらは枠を隠して撮り直す手順を
  内側に持っており、起動時の自動フィットは枠を出す前に走るので、自分で自分を止める
- 唯一の例外が**設定「起動時に盤面を探す」**（既定オフ）。この設定の目的がまさに
  「最初から盤に合った枠が出ていること」なので、そのときは合わせ終えてから枠を出す
- ⚠️ **メイン画面は `Hidden: true` で作り、`revealMain` で出す。**
  `Hidden: false` で作らないこと —— 枠の外への配置（`placeMainBesideFrame`）も
  座標の記録もあちらが持っているので、通らないと**初回のキャプチャで窓が突然動く**
- ⚠️ **起動時に出す場所は枠の `WindowRuntimeReady` フックの中**（メイン画面側では
  ない）。`placeMainBesideFrame` は枠の座標を基準にするので、**枠の座標が確定する前に
  呼ぶと初回起動でセンチネル値（-32000）を基準に置いてしまう**。2 つのウィンドウの
  `WindowRuntimeReady` はどちらが先に来るか決まっていないので、順序を保証できる
  枠側に置いてある
- **撮るたびに毎回アクティブにする**（最小化されていれば戻して `Focus()`）。撮った直後に
  やることは結果を見ることなので、背面や最小化から出てくるのが速い。引き換えに中継の
  再生画面からフォーカスが外れる（動画は流れ続けるが、中継側のキー操作は効かなくなる。
  `Alt+S` はグローバルホットキーなのでフォーカスがどこにあっても撮れる）。
  **初回だけやること**（枠の外への配置・位置の記録）は `mainShown` で分けてある
- ⚠️ **最小化されているときは、`Show()` より先に `UnMinimise()` する**（下記「メイン画面が
  真っ黒になる」）。`UnMinimise` は内部で `Focus()` まで済ませるので、そちらを通ったときは
  重ねて `Focus()` を呼ばない
- **前面に出すのは撮り終えた後**（`Capture()` の最後）。メイン画面が枠に重なっていても
  その 1 枚には写らない。ただし重なったまま次を撮ると写り込むので、初回の配置
  （`placeMainBesideFrame`）で枠の外へ逃がしている
- **枠は閉じても破棄せず隠すだけ。** 領域の定義を生かしたままにするため。
  隠れていても HWND は生きているので、**出し直せば前と同じ領域に戻る**。
  ただし**隠しているあいだは撮れない**（上記の `requireFrame`）
- **メイン画面を閉じるとアプリが終了する。** 枠は隠れて生き続けるので、
  ここで明示的に `app.Quit()` しないとプロセスが残る
- **枠のツールバーの ▼ →「設定」でメイン画面を前面に出せる**（`CaptureService.ShowMain`）。
  メイン画面は起動時から出ているが、枠に隠れていたり最小化されていたりするので入口は要る
- **枠のツールバーの ▼ →「終了」でも終了する**（`CaptureService.Quit`）。
  枠の ✕ は「隠す」であって終了ではない。終了の入口が 2 つあるため、
  **位置・サイズの保存は `saveWindowState` の 1 本に寄せてある**
  （`app.Quit()` が `WindowClosing` のフックを通す保証は無いので、Quit の前に自分で保存する）
- 枠を隠した結果として可視ウィンドウが 0 枚になると操作不能になるため、
  `HideFrame` はメイン画面が未表示なら先に出す。**起動時に出しているので普通は
  既に出ているが、この保険は外さないこと**
- **キャプチャ領域の基準は枠のまま。これは移せない**（領域は枠のクライアント矩形そのもの）

#### 枠を出すトグルはタイトルバー（**2026-08-18 に入力タブから上げた**）

**枠は「撮るときだけ使う道具」だが、出したくなる場面はどのタブに居ても来る**
（撮って → 訂正 → 解析と進んだあと、もう一度撮る）。入力タブの中にあると
**そのたびにタブを行き来する**ことになるので、常に見えているタイトルバーへ移した。

⚠️ **「常設の機能に見えてしまう」という 2026-08-10 の懸念は、実際に使って
判断が変わったもの**（入力の口が増えても、**撮るときに要るのは枠を出すことだけ**で、
そこにタブの移動を挟む理由が無い）。**入力タブに戻さないこと。**

| | 置き場所 |
|---|---|
| **枠を出す / 隠す** | **メイン画面のタイトルバー**（`#frame-toggle`。**トグル**） |
| 枠を隠す（もう 1 つ） | **枠のツールバーの ✕**（`HideFrame`） |
| 盤に合わせる | **枠のツールバーの □**（`FitFrame`） |

- ⚠️ **押すたびに出す/隠すが入れ替わる**（2026-08-18。一度「押せなくする」に
  したのを変えた）。隠す口が枠の ✕ にもあるが、**出した口と同じ場所で戻せるのが
  素直** —— 枠が中継の裏に回っていたり別モニタにあったりすると、
  **✕ を押しに行くほうが遠い**。⚠️ **状態は 1 つ**（`frame:visible`）なので、
  入口が 2 つあっても食い違わない
- ⚠️ **アイコンにしてある**（`FiMaximize`。ガイド枠らしい四隅の括弧）。
  **絵は状態で変えない**ので、**今どちらなのかを伝えるのは `aria-pressed` の色だけ**。
  ⚠️ **薄い差にしないこと**（読めないと、押すまでどちらか分からない）。
  ⚠️ **`aria-label` と `title` は状態で書き換えること** —— 文字が無いぶん、
  「押すと何が起きるか」はこれでしか読めない
- ⚠️ **状態は Go 側が知らせる**（`frame:visible`。`ShowFrame` / `HideFrame` /
  起動時の自動フィット）。**フロントで覚えないこと** —— 枠の ✕ で隠したことは
  メイン画面からは分からないので、**隠れているのに「表示中」のまま**になる。
  起動した時点で出ていることもある（設定「起動時に盤面を探す」）ので、
  初期状態は `CaptureService.FrameVisible()` で取る
- ⚠️ **`captureWithoutSelf` からは知らせない**（探すあいだ一瞬隠してすぐ戻すだけ。
  知らせるとトグルが明滅する）
- ⚠️ **`no-drag` に戻すこと**（ツールバー全体が移動ハンドル。`.tabs` と同じ話）。
  戻し忘れると**押しても何も起きない**
- ⚠️ **入力タブに「盤に合わせる」を置かない**（2026-08-18 に消した）。
  合わせる相手は**枠**なので、枠が出ていない状態から押す操作ではない
  （□ は枠のツールバーにある）。**入力タブに残すのは案内だけ**
- ⚠️ **ここに他のボタンを増やさないこと。** タイトルバーはタブの行を兼ねており、
  **積むほど横が狭くなる**（アプリ名を出していないのと同じ理由）

#### 中継を追っているかは枠に出す（2026-09-15）

⚠️ **追跡中に見ているのは中継**（メイン画面は裏に回っている）。実機で
**「枠側が録画しているか分からない」**と出たので、**状態も操作も枠に置いた。**

| | 置き場所 |
|---|---|
| 追う / 止める | **枠のツールバー**（`#frame-follow`）と**解析タブの「中継を追う」**（どちらでも） |
| 追跡中の札 | **枠のツールバー**（`#frame-follow-state`。赤い点 + 短い文） |

- ⚠️ **状態を持つのはメイン画面だけ**（ループもあちら）。**枠は映すだけ**で、
  押したら `follow:toggle` を投げる。**2 か所が別々に覚えると食い違う**
  （枠の「枠を表示」と同じ話）
- ⚠️ **枠が出たら状態を送り直すこと**（`frame:visible`）。枠は出たばかりで
  何も知らないので、**追っている最中に枠を出し直すと「追跡中」が出ないまま**になる
- ⚠️ **点滅させること。** 長考のあいだ何分も同じ文が出たままになるので、
  **文字だけでは止まっているのか動いているのか読めない**。
  ⚠️ **`prefers-reduced-motion` は尊重する**
- ⚠️ **1 周ごとに必ず変わるもの**を出すこと（**最後に見た時刻**。2026-09-15）。
  ⚠️ **経過秒では動いている証明にならない** —— **ループが死んでも数字は増え続ける**
  （実機で「秒数を出したところで証明にならない」と指摘された）。
  時刻なら**止まれば数字も止まる**。長考の「何分も何も起きない」は、
  最後に手が付いてからの経過を**添えて**出す
- ⚠️ **1 周の予約は 1 か所から**（`followSchedule`）。**見送りの `return` が
  予約を飛ばして追跡が黙って死んだ**（2026-09-15 に実機で踏んだ。盤が映らなかった
  最初の 1 回で死に、盤に戻っても復活しなかった）。
  **「1 周やる」と「回し続ける」を同じ関数に混ぜないこと**
- ⚠️ **見張りを付けてある**（`followWatch`。1 周が返ってこなければ立て直す）。
  **保険であって設計ではない** —— 本体は予約の出口を 1 か所にしてあること
- ⚠️ **Go 側は「変わり目だけ」ログに出す**（`noteQuiet`）。毎回出すと 1 秒ごとで
  読めなくなるが、**何も出さないと「正常に見送っている」のか「止まっている」のかが
  ログから分からない**
- ⚠️ **読まずに済む周は認識を呼ばない**（2026-09-18。`CaptureService.gate`）。
  **認識は 2.1 秒**なので、**変わっていない 1 枚に払うとそのぶん次の手に
  気づくのが遅れる**。⚠️ **比べるのは盤の矩形の中だけ**（マスタが持っている）——
  画面全体だと**消費時間の秒読みで毎周「変化あり」になり素通しになる**。
  ⚠️ **判断できないときは読むほうへ倒すこと**（落とした手は戻らない）。
  ⚠️ **省いた周を見送りとして数えないこと**（`CaptureResult.Skipped`）——
  `followLost` も録画も「読んだのに繋がらなかった」ためのもので、混ぜると
  **長考のたびに「見失っています」と出る**。なぜそうしたかは ikkyoku の
  `CLAUDE.md`「読まずに済ませる」
- ⚠️ **盤の有無だけで落とす段がある**（2026-09-18。`CaptureService.detectGate`）。
  **大盤解説のあいだは画素が動き続ける**ので画素差分のふるいを素通りする ——
  検出は認識の 15% なので、**マスタと合わなければ 81 マスの推論に入らない**。
  ⚠️ **枠を動かしたら通すこと**（落とすと**マスタを取り直す後段に辿り着かない**）。
  ⚠️ **検出だけを根拠に落とし続けないこと**（`detectMissMax`）。
  ⚠️ **落としても `OffBoard` として返すこと**（`Skipped` にしない）——
  画面の振る舞いは変えない。⚠️ **`noteQuiet` と受け側は `OffBoard` を先に見ること**
  （この段で落ちた周は**読んでいないので SFEN が空**）
- ⚠️ **撮る間隔（`followTickMs`）と見張りの時間（`followStallMs`）を
  倍数で結ばないこと**（2026-09-18 に分けた）。**認識する周だけ 2 秒以上かかる**
  ので、撮る間隔を基準にすると**読んでいるだけの周を「死んだ」と見なして
  二重に回す**
- ⚠️ **`.frame-title`（撮影の一時的な文）とは別の要素にすること。**
  混ぜると**撮った瞬間に「追跡中」が消える**
- ⚠️ **ここから増やさないこと。** ツールバーは中継に重ねて常時見えるので、
  積むほど中継が隠れる（アプリ名を出していないのと同じ理由）

#### ⚠️ 撮った画像のパスは「認識詳細情報」だけに出す（2026-08-18）

入力タブの状態の行は `保存しました: <フルパス>` と出していたが、**その行はもう
見えていない**（撮ると訂正タブへ移る）うえ、パスは長くて 1 行を埋める。
**置き場所は訂正タブの「認識詳細情報」**（盤の下。ファイル名 +
押すとフルパスをコピー）で、
**そちらは元からある。2 か所に出さないこと。**

- 状態の行に残すのは「撮りました（幅x高さ）」と、認識の成否だけ
- ⚠️ **パスそのものを画面から消したのではない**（撮った PNG は学習にも他のツールにも
  使うので、**辿れる手段は必ず残す**）

同じフロントバンドルを URL クエリで出し分ける(wails3 skill `advanced.md` の
「マルチウィンドウは URL クエリで画面分岐」パターン)。フロント側は `frontend/src/main.ts` が
`?window=` を見て `frame.ts` / `mainscreen.ts` のどちらかをマウントする。

### ⚠️ メイン画面が真っ黒になって触れなくなる（2026-08-08 / 2026-08-13 に発生）

**症状**: メイン画面が真っ黒になり、クリックもキー操作も受け付けなくなる。
**Go 側は無傷**（黒くなったあとの `Alt+S` で PNG が保存できている）。
**原因は確定していない**（再現待ち）。⚠️ **調査の全文は `_docs/blackscreen.md`。
次に黒くなったら、手を動かす前にそれを読むこと。** ここに残すのは制約だけ。

**黒くなったら、まずログの心拍を見る**（`DiagService.Heartbeat`。5 秒ごと・
途切れると Go が warn を出す）。

| | 意味 | 手当て |
|---|---|---|
| **心拍が続いている** | WebView2 が不可視にされているだけ | 枠のメニュー →「メイン画面を描き直す」で戻る |
| **心拍が止まる** | レンダラが死んでいる**か、UI スレッドが詰まっている** | 描き直しでは戻らない。**起動し直すしかない** |

- ⚠️ **訂正タブのドラッグをネイティブ DnD（`draggable` + `dragstart`/`drop`）に
  戻さないこと。** **2 回とも訂正タブでドラッグしている最中に始まっている** ——
  Windows の Chromium はネイティブ DnD を OLE の `DoDragDrop` で動かし、
  **ブラウザプロセスの UI スレッドでモーダルなループが回る**。そこが抜けられなく
  なると Go の `Eval` / `Focus` も心拍も同じスレッドで止まる。だから
  pointer events に置き換えた（2026-08-13。`editor.ts`）
- ⚠️ **`RepairMain` の入口を枠に置いてあるのが要点**（`CaptureService.RepairMain`。
  中身は `Hide()` → `revealMain()`）。**黒くなるのはメイン画面なので、
  そこにボタンを置いても押せない。** 設定タブへ移すような整理をしないこと
- ⚠️ **畳まれたままの窓に `Show()` を当てないこと**（`revealMain` は `Show()` より先に
  `UnMinimise()` する）。Wails は最小化で WebView2 のコントローラを不可視にし、
  戻す分岐が条件付きなので、取りこぼすと不可視のまま残る
- ⚠️ **心拍の閾値を短くしないこと**（90 秒）。Chromium は隠れている・最小化されている
  ページのタイマーを間引き、`setInterval` は最悪 1 分に 1 回まで落ちる ——
  **追っているのがまさに最小化まわりの現象**なので、短いと調べたい状況で必ず誤検知する
- ⚠️ **ウィンドウの表示状態のログ（`registerVisibilityLog`）を消さないこと。**
  debug で出しているので既定では見えないが（枠を動かすだけで大量に出て他が埋もれる）、
  **出すのをやめたのではなく普段は黙らせているだけ**
- ⚠️ **起動し直すときは古いプロセスを必ず落とすこと。** 単一インスタンスの防止を
  入れていないので 2 つ走る（`app-window.json` の二重書き込み・ホットキー登録・
  エンジンのプロセスが重なる）
- ⚠️ **短時間の動作確認では再現しない**（2 回とも長時間起動しっぱなしのとき）。
  **「触ってみて大丈夫だった」を根拠にしないこと**

### 透過と Frameless

`WebviewWindowOptions.BackgroundType: application.BackgroundTypeTransparent` +
`BackgroundColour: application.NewRGBA(0, 0, 0, 0)` を枠ウィンドウに設定している。
**`application.WindowsWindow{ BackgroundType: ... }` ではない**（`WindowsWindow` 構造体には
`BackgroundType` フィールドが無い。実際の Wails v3 ソース(`webview_window_options.go`)で
確認済み。`BackgroundType`/`BackgroundColour` は `WebviewWindowOptions` 直下のフィールド）。

`Frameless: true`。OS のタイトルバーの代わりに、フロント側が上部にツールバーを描く。
ツールバーに置くのは ▼(メニュー)・□(盤に合わせる)・カメラ(撮る)・
✕(隠す)の 4 つと、状態メッセージだけ。**アプリ名は出さない**（中継に重ねて常時見えるので
邪魔になる）。よく押すものは左端、押し間違えると枠が消える ✕ は右端に離してある。

▼ のメニュー（`.frame-menu`）は**ツールバーの下に垂れるドロップダウン**。中身は
「設定」と「終了」で、**セパレータで終了だけを分けてある**（上の項目を押すつもりで
下まで滑らせる事故を減らすため）。どちらも**枠だけを出して使っているときに手が無かった**
ものの入口:

| 項目 | 何ができなかったか |
|---|---|
| 設定 | メイン画面を出す手段が「撮る」か「枠を✕で隠す」しか無かった（撮りたくないのに撮る / 位置合わせに使う枠が消える、という副作用つき）。`CaptureService.ShowMain("settings")` |
| 終了 | 枠の✕は隠すだけなので、メイン画面を一度出して閉じるしかなかった。`CaptureService.Quit` |

`ShowMain` は**開いてほしいタブ名をイベント（`main:tab`）で先に流してから**メイン画面を出す
（`Capture` と同じ順。前面に来た時点で目的のタブが開いている状態にする）。**メイン画面は
非表示でもフロントは動いている**ので、隠れているあいだに出したイベントも受け取れる。
枠は隠さない（位置合わせの基準そのものなので、設定を見るために消す理由が無い）。

**⚠️ 開いているあいだはガイド枠の内側＝キャプチャ領域に重なる**ので、
開いたまま `Alt+S`（グローバルホットキーなので止められない）を押すとメニューごと写り込む。
**開けっぱなしを前提にした置き方をしないこと。** 手当ては 3 つ:

- 項目を押したら閉じる / `Esc`・メニュー外のクリックで閉じる
- 撮れた（`capture:shot`）ら閉じる。写り込んだ 1 枚は避けられないが、続けて撮る 2 枚目は綺麗になる
- **よく押すもの（撮る・盤に合わせる）はメニューに移さない。** ツールバーに出したままにする

**メニューの DOM は `.frame-toolbar` の外（`#app` 直下）に置く。** ツールバーは
`toolbarHeightPx` で高さ固定・`overflow: hidden` なので、中に入れると垂れた部分が切れる。
メッセージ欄(`.frame-title`)は普段は空で、撮影・失敗・警告のときだけ文字が出る。
**ボタンは必ず `.frame-actions` の中に置くこと**（ツールバー全体が
`--wails-draggable: drag` で、`no-drag` に戻しているのが `.frame-actions` だけ。
外に出すとドラッグ扱いになりクリックが効かなくなる）。
`Windows.DisableFramelessWindowDecorations: true` も付けている（既定では DWM のフレームを
クライアント領域へ延ばして影・角丸を残すが、中継映像に重ねる透過ウィンドウなので
影も角丸も邪魔で、透過領域に DWM が描く余地も残したくない）。

#### 枠の内側で後ろの画面を操作する（**素通し**。2026-08-19）

**枠は中継の「上」に重ねる最前面のウィンドウ**（`AlwaysOnTop`）なので、合わせたあとは
**その下にある中継のシークバーや再生ボタンが押せない。** 押すには枠をどかすしかなく、
どかすと位置合わせがやり直しになる。設定タブの
「**枠の内側で後ろの画面を操作する**」（`Config.ClickThrough`。**既定は切**）で、
**撮る範囲の内側だけ**をマウスに対して透明にする。

```
カーソルが撮る範囲の内側 ──> 枠に WS_EX_TRANSPARENT ──> クリックが後ろの中継へ抜ける
カーソルがツールバー・縁 ──> 外す                    ──> 今までどおり押せる（撮る・□・✕・移動・リサイズ）
```

- ⚠️ **枠ごと素通しにしないこと。** `WS_EX_TRANSPARENT` はウィンドウ単位なので、
  素直に付けると**ツールバーも押せなくなる** —— 撮ることも枠を動かすこともできず、
  **切る口は設定タブにしかない**（＝メイン画面まで行かないと戻せない）。
  そこで**カーソルの位置で付け外しする**（`CaptureService.watchCursor`）
- ⚠️ **素通しにしているあいだ、枠にはマウスのイベントが 1 つも来ない。**
  「カーソルがツールバーへ戻ってきた」を知る手段が**ポーリング以外に無い**
  （50ms）。回すのは**設定が入のあいだだけ**で、切ったら goroutine ごと止める
- ⚠️ **撮る範囲そのものを素通しにしないこと**（`clickThroughInsetPx` = 10px 内側へ詰める）。
  Wails のリサイズ判定は「クライアント領域の端 5px（角は +10px）」で、
  **ガイド枠（2px）より内側まで食い込む**。詰めないと**左右と下の縁から
  リサイズできなくなる**。詰めたぶんは「押しても後ろへ抜けない細い縁」になるだけ
- ⚠️ **マウスのボタンを押している最中は切り替えない**（`mouseButtonDown`）。
  ドラッグ移動もリサイズも押したまま動かす操作なので、途中で素通しになると
  **掴んだまま外れて動かなくなる**
- ⚠️ **切ったら必ず素通しを解くこと**（`applyClickThrough`）。解き忘れると
  **設定を切ったのに枠が押せないまま**になり、画面からは理由が分からない。
  **枠を隠したときも解く**（出し直したときに、ツールバーの上なのに押せない状態から
  始まらないように）
- ⚠️ **`WS_EX_TRANSPARENT` だけでは全く効かない**（2026-08-19 に実機で確かめた。
  **最初にそれで実装して、まったく素通しにならなかった**）。**3 つ揃って初めて効く**:
  `WS_EX_TRANSPARENT` ＋ `WS_EX_LAYERED` ＋ **`SetLayeredWindowAttributes`**
  （ヒットテスト領域の更新。呼ばないと反映されない）。TRANSPARENT だけだと
  **拡張スタイルは確かに変わるのに、クリックは枠が取る** —— 枠の中身を描いている
  WebView2 が**別プロセスの子ウィンドウ**（`Chrome_WidgetWin_1`）で、そちらが
  マウスを受け取るため。⚠️ **子ウィンドウに TRANSPARENT を付けて回っても直らない**
  （これも試した）。Wails 自身の `setIgnoreMouseEvents` も LAYERED を一緒に付けている
- ⚠️ **`ChildWindowFromPointEx(CWP_SKIPTRANSPARENT)` で確かめないこと。**
  あれは「TRANSPARENT だけで素通しになる」と答えるが、**実際のクリックの行き先とは
  食い違う**（実測）。⚠️ **`WindowFromPoint` は更に駄目**（透明ウィンドウを飛ばさない）。
  **確かめるなら実際にクリックして `GetForegroundWindow` を見ること**
- **`WS_EX_LAYERED` を足しても枠の描画は変わらない**（2026-08-19 に実測。
  layered の前後で枠全体が同じに描かれ、ツールバーも赤いガイド枠も出たまま）。
  ⚠️ **それでも素通しでないあいだは LAYERED も外して元の姿に戻すこと** ——
  枠は `WS_EX_NOREDIRECTIONBITMAP` の合成で透過しているので、
  **普段の状態を変更前と 1 ビットも変えない**ほうが安全
- ⚠️ **切り替えたその場で効かせる**（`SettingsService.SetClickThrough` → フック →
  `CaptureService.applyClickThrough`）。**「起動時に盤面を探す」とはそこが違う** ——
  これは**中継を触りたくなったその瞬間**に切り替える設定なので、次の起動まで待たせない。
  ⚠️ **保存できたときだけ効かせること**（先に効かせると、保存に失敗したときに
  「チェックは外れているのに枠は素通しのまま」になる）
- ⚠️ **`SettingsService` から枠を直に触らないこと**（ウィンドウを持っていない）。
  HWND を触るのは `CaptureService` の仕事で、間はフック 1 本（`main.go` で繋ぐ）
- ⚠️ **Windows のみ。** 他 OS はスタブが何もしない（設定は保存できる）
- **撮った画像には影響しない**（描画は変わらないので、枠もツールバーも今までどおり写らない）

#### Frameless の移動とリサイズ(**ここを踏むと枠が一切動かせなくなる**)

Frameless にすると移動もリサイズも OS 任せでなくなる。

- **移動** … ツールバーに CSS の `--wails-draggable: drag`。カスタムプロパティは継承するので、
  ボタン側は `no-drag` に戻す
- **リサイズ** … Wails ランタイムがウィンドウ端 5px（角は +10px）を座標で検出する。
  `DisableResize` は `false` のままにしておくこと
- **⚠️ どちらも `frontend/src/main.ts` の素の `import "@wailsio/runtime"` が前提。**
  ランタイムの `drag.js` がページ全体の mousedown/mousemove を監視して初めて成立する仕組みで、
  **これが無いと `--wails-draggable` を書いても何も起きない**
  （wails3 skill `frameless.md` の冒頭。名前付き import だけでは副作用が有効化されないことがある）

フロント側(`frame.ts` / `style.css`)は `html.is-frame` に `background: transparent` を指定し、
ツールバー（不透明）とガイド枠（`border` だけの要素）を縦に積む。ガイド枠は
`pointer-events: none` だが、**リサイズの端検出は座標だけで要素を見ていない**ので影響しない。

> **⚠️ wails3 skill `frameless.md` の「リサイズ領域の確保(必須): ルート要素に 5px の
> パディングを設けること」は beta.3 では不要。** あれは alpha2.117 前提の記述で、
> beta.3 のランタイム実装(`drag.ts`)はウィンドウ端 5px(角は +10px)を
> **座標だけで判定しており要素を見ていない**。ソースを読んだ時点での推測どおりだったことが
> 実機で確認できた。**このためにレイアウトを歪めないこと。**

### キャプチャ領域の決定(物理ピクセル・HWND 直接取得)

**キャプチャ領域は「クライアント領域から、ツールバーとガイド枠を除いた内側の矩形」**という
決定論的な方式にしてある(`captureservice.go` の `captureRegion`)。「撮る直前に枠を消して
少し待って撮る」というタイミング依存の方式は採っていない。

```
┌──────────────────────────┐ ← 端 5px = リサイズ(Wails ランタイムが座標で検出)
│ ツールバー(toolbarHeightPx)│ ← 撮る/✕。ドラッグ移動もここ
├──────────────────────────┤
│ ┌──────────────────────┐ │ ← ガイド枠(guideBorderPx)
│ │   ここを撮る(透過)    │ │
│ └──────────────────────┘ │
└──────────────────────────┘
```

- **寸法の唯一のソースは Go 側**(`captureservice.go` の `guideBorderPx` /
  `toolbarHeightPx`)。フロントは起動時に `CaptureService.Layout()` を呼び、
  CSS 変数(`--guide-border` / `--toolbar-height`)に流し込んでから描く。
  **フロントに既定値を書かないこと。** ずれると「見えている枠」と「実際に撮れる領域」が
  食い違い、枠が写り込む。取得に失敗したときは黙って描かず、ツールバーにエラーを出す
- Frameless なので**クライアント領域はウィンドウ全体と一致する**(Wails が `WM_NCCALCSIZE` で
  標準フレームを外す)。タイトルバー・枠の厚みを別途足し引きする必要はない
- **CSS px → 物理ピクセルの変換は切り上げる**(`scaleUp`)。丸めで 1px ずれたとき、
  内側に食い込む(盤が 1px 欠ける)のは実害が無いが、外側にはみ出すと赤い枠が写り込むため
- **⚠️ `framelessBottomPaddingPx = 1` を引くこと。** Wails は Frameless のとき
  `WM_NCCALCSIZE` で `rgrc.Bottom += 1` と `setPadding(edge.Rect{Bottom: 1})` を行っている
  (リサイズ時のちらつき回避)。結果として**クライアント領域の最下 1 行には WebView が
  描画されず**、ガイド枠の下辺が `GetClientRect` の下端より 1px 上に来る。これを引かないと
  撮った画像の最下行に赤い枠が 1px 写り込む(実測で確認 → 修正済み)。
  この余白のせいで**枠ウィンドウはクライアント高さがウィンドウ高さより 1px 大きい**
  (`480x421` client / `480x420` window)という妙な状態になる。ウィンドウ判別に
  「client == window なら Frameless」という判定を使わないこと
- 座標は**物理ピクセル**で取得する。`kbinani/screenshot` は物理ピクセルで動くが、
  Wails の `Window.Position()`/`Size()` は **DIP(論理ピクセル)** を返すため、
  マルチモニタでスケーリング(150% 等)が混在する環境ではそのまま使うとずれる
- **`Window.NativeWindow()` で HWND(`unsafe.Pointer`)を取得し、Windows API の
  `GetClientRect` + `ClientToScreen` を `golang.org/x/sys/windows` 経由で直接呼んで
  クライアント領域のスクリーン座標を物理ピクセルで得ている**(`native_windows.go`)。
  per-monitor DPI aware なプロセスでは `GetClientRect` 自体が物理ピクセルを返すため、
  DPI 変換もタイトルバー・枠の厚みの計算も不要になる
- ガイド枠の太さ(CSS px 指定)を物理ピクセルのオフセットに変換するためだけに、
  `GetDpiForWindow(hwnd)/96` のスケール係数を使っている(`GetDpiForWindow` が無い
  環境では 1.0 にフォールバック)
- **cgo は使っていない**(`golang.org/x/sys/windows` の `NewLazySystemDLL`/`NewProc` 経由)。
  `ikkyoku` ルートパッケージが PureGo 方針のため、GUI 側も踏襲している
- Windows 以外は `native_other.go`(`!windows` ビルドタグ)でエラーを返すだけの
  スタブにしてあり、ビルド自体は壊れないようにしてある。**実装・動作確認は Windows のみ**


### ホットキー

⚠️ **画面には出していない**（2026-08-10）。登録はしてあるが、`Alt+S` という文字列を
UI のどこにも書かない。理由は 2 つ:

- **枠が出ていないと撮れない**ようにしたので、「フォーカスがどこにあっても撮れる」という
  ホットキーの売りが**枠が出ているあいだに限られる**（枠のツールバーのカメラで足りる場面が増えた）
- **入力の口はこれから増える**（SFEN / KIF / 画像ファイル）。撮ることを前提にした
  案内を常設のツールバーに置き続けたくない

**登録失敗も画面に出さない**（Go 側の warn ログだけ）。案内していない操作なので、
失敗を伝えても何をすればよいか分からない。`hotkey:register-failed` イベント自体は
残してある（出す先が要るときのために）。**フロントに listener は無い。**

既定 `Alt+S`。実際の登録は `golang.design/x/hotkey` ではなく **Wails 標準の
`app.GlobalShortcut.Register`** を使っている(`main.go`)。理由は `hotkey.go` のコメントに
書いてあるとおり、GlobalShortcut はウィンドウが非フォーカスでも確実に発火する経路として
wails3 skill(`tray-hotkey.md`)で保証されており、二重にホットキー実装を持ち込むと
競合のリスクがあるため。一方で「alt+s」のような文字列の妥当性検証・既定値の一元化は
既存の `ikkyoku.ParseHotkey` / `ikkyoku.DefaultHotkey` を単一のソースとして再利用し
(`hotkeyAccelerator` 関数)、「有効なホットキー文字列」の定義をルートパッケージに
一本化してある。

### ウィンドウ状態の永続化

枠とメイン画面**両方**の位置・サイズを `os.UserConfigDir()/ikkyoku/app-window.json` に
保存・復元する(`window.go` / `window.go`)。**ルートパッケージの `Config`(`config.json`)とは
あえて別ファイルにしてある**。ルートパッケージに Wails 依存(`application` パッケージの
`ScreenNearestDipPoint` 等)を持ち込まないための分離。

- 未設定(初回起動)の判定にはセンチネル値 `-32000` を使う。マルチモニタで左/上に
  モニタがあると座標が負になりうるため、`0` や `< 0` では判定できない(wails3 skill
  `window-state.md`)
- **⚠️ 終了時に `Position()`/`Size()` を読んではいけない。** `WindowClosing` の時点では
  破棄が進行しており、**不正な値が返る**(wails3 skill `window-state.md`「特に Frameless で
  発生しやすい」。このアプリでも実測で確認し、枠を動かしても保存値が追従しない不具合が出た)。
  代わりに `geometryTracker`(`window.go`)が `WindowDidMove` / `WindowDidResize` の
  たびに位置を記録しておき、**終了時にはその記録を保存する**。
  スキルが挙げている回避策(フロントの✕から Go の `Quit()` を呼ぶ)は自前の✕しか無い
  ウィンドウ向けで、**ネイティブのタイトルバーを持つメイン画面には使えない**
  (Alt+F4・OS シャットダウンを自前の経路に通せないため)
- 保存の起点はメイン画面の `WindowClosing` の **`RegisterHook`**(`OnWindowEvent` ではない)。
  デフォルトの破棄用リスナーは並列 goroutine で走るため、hook(同期・listener より前に実行)
  でないと破棄とレースする(wails3 skill `tray-hotkey.md` の hook/listener 順序の説明)。
  **枠は閉じられないので、保存経路はここ 1 本だけ**
- 枠の `WindowClosing` hook は `e.Cancel()` + `Hide()`。ツールバーの自前✕は
  `WindowClosing` を通らない(wails3 skill `pitfalls.md`)ので、そちらは JS から
  `CaptureService.HideFrame()` を呼んで同じ入口に合流させている
- マルチモニタのクランプ(`clampToScreen`)は `events.Common.WindowRuntimeReady` で行う
  (`ScreenNearestDipPoint` は `app.Run()` 前は `nil` を返すため)
- **旧フォーマット(枠 1 枚ぶんのフラットな JSON)との互換は取っていない。**
  ツールバーが増えて同じウィンドウサイズでも撮れる領域が変わったので、
  旧い座標を復元しても位置合わせはやり直しになるため
