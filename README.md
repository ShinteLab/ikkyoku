# ikkyoku（一局）

将棋のオンライン中継を観ながら、**その場で盤面を解析して遊ぶ**ためのデスクトップアプリ。

> 中継の画面から盤面を割り出し、エンジンで解析して、
> **「次善手を選んだらどう転ぶか」を対話的に辿れるようにする。**

**撮る → 認識する → 訂正する → 解析する → 手を進めて評価値を追う**、までが繋がっている。
**キャプチャツールではない。**

⚠️ **放送局に依存しない。** 入口は OS の画面キャプチャなので、画面に映ってさえいれば
ABEMA でも YouTube でもキャプチャボードでも同じ経路で扱える
（検証は [ABEMA 将棋中継](https://abema.tv/now-on-air/shogi) で行った。下記「経緯」）。

## 名前の由来

**「それもまた一局」から。** 最善手を唯一の答えとして示すのではなく、別の選択も
一つの局として辿らせる、という思想をそのまま名前にしている。

## なぜ Chrome 拡張ではなくネイティブなのか（経緯）

最初のプロトタイプは Chrome 拡張（MV3）だった（検証コードは Phase 0 完了後に削除済み。
結果は [`_docs/phase0-capture.md`](_docs/phase0-capture.md) の表に記録してある）。要点だけ書くと以下の通り。

- ABEMA は盤面データを通信でも DOM でも流していない（映像に焼き込んで配信している）
- `<video>` → canvas の `drawImage`、および `chrome.tabs.captureVisibleTab` はどちらも
  **真っ黒になる**。Widevine DRM (EME) による保護がかかっているため
- **しかし OS レベルの画面キャプチャ（Win+Shift+S 等）では盤面が普通に写る。**
  Widevine L3 の保護は Chrome 自身のキャプチャ API に対しては効くが、
  OS の画面キャプチャは素通りする

つまり、入口を Chrome 拡張ではなく **OS の画面キャプチャを使うネイティブアプリ**にすれば、
DRM を一切気にせず済む。副次的な利点として:

- 放送局ごとのアダプタが要らない。画面に映ってさえいれば同じ経路で扱える
- Go で書けるので `core` / `engine` / `suteme` / `kicho` を直接 import できる。
  WASM も gRPC-web も不要（⚠️ **エンジンだけは USI で外から繋ぐ**。上記ロードマップの ⚠️）
- MV3 の制約（service worker の寿命・offscreen document・CSP・MAIN world）が全部消える

## 現時点でできること

**画面は 5 タブ**（入力 / 棋譜 / 訂正 / 解析 / 設定）。

- **撮る** — 画面に重ねた透過の枠で範囲を決めて PNG に保存する（ホットキー可）。
  枠を盤に自動で合わせるボタンもある
- **認識する** — 撮った画像を `suteme` に渡して盤面を出す。どこが怪しいかも一緒に出る
- **訂正する** — 認識の誤りを 1 マスずつ直す。駒台・「足りない駒」・手番・撮った向きまで。
  **直した局面は `suteme` の学習データに戻せる**
- **解析する** — 確定した局面を USI エンジンに渡す。**複数のエンジンを同時に走らせて
  並べて読める**（合成はしない）。候補手（MultiPV）・勝率バー・評価値グラフ
- **手を進める** — 合法手だけを辿る。戻って別の手を指すと**枝が生える**（前の手順は消えない）。
  エンジンの読み筋を枝として足せる
- **棋譜を扱う** — KIF の貼り付け・URL からの取り込み・中継からの取得・棚（`kicho` の
  棋譜データベース）への登録と検索。中継は**取り直して最新手まで追える**

盤面認識は [`suteme`](https://github.com/ShinteLab/suteme)、将棋の仕様（SFEN/USI/KIF）は
[`core`](https://github.com/ShinteLab/core)、エンジンは
[`engine`](https://github.com/ShinteLab/engine)、棋譜データベースは
[`kicho`](https://github.com/ShinteLab/kicho) にある。`ikkyoku` はそれらを**束ねて
アプリにする側**で、局面の矯正・検討 UI・キャプチャがこのリポジトリに入る。

### 設計上の約束

- **履歴に依存しない。** 「最初から観戦していないと動かない」「CM 中に盤面が進んだら
  迷子になる」を避けるための根幹。1 回のキャプチャは他と完全に独立している
- **スナップショットが基本。** 多くの放送は盤面を映し続けない（解説者・検討盤面・
  カメラ切り替え）。撮る瞬間をユーザーが決める方式にすることで、
  「今、盤面が映っているか」の判定を人間がやってくれる
- **段階的に劣化する。** 認識が弱くても棋譜が繋がらなくても、
  「撮ったこの 1 局面を解析する」は必ず成立する

これは `../TODO.md` の「どの層も履歴に依存しない」「suteme は棋譜の仕組みを持たない」という
原則を、取り込み層であるこのツールでも踏襲したもの。

## インストール・ビルド・使い方

CLI は無い。ビルドと使い方は下記「GUI アプリ（Wails3）」を参照。

⚠️ **配布ビルドは認識器をバイナリに焼き込む**（`task build:embed`）。配る相手の環境に
`suteme` のリポジトリは無いので、「exe の隣に .bin を 2 つ置いてください」を避けるため。
開発中は設定で `suteme` のリポジトリを指すほうが正しい（**育て続けるデータ**なので、
焼き込みに倒れると更新が反映されない）。

## 採用ライブラリと cgo 確認

このプロジェクト群は PureGo 方針（`../CLAUDE.md` 参照）。以下 2 つを採用前に
`CGO_ENABLED=0` で Windows ビルドが通ることを実際に確認した。

| 用途 | ライブラリ | cgo |
|---|---|---|
| 画面キャプチャ | `github.com/kbinani/screenshot` | 不要（Windows は GDI 直呼び） |
| グローバルホットキー | `golang.design/x/hotkey` | 不要（Windows は `RegisterHotKey` を x/sys 経由で直呼び。cgo が要るのは macOS 側の実装のみ） |
| 棋譜データベース | `kicho` 経由で `modernc.org/sqlite` / `dop251/goja` ほか | 不要（どれも PureGo） |

⚠️ **`kicho` を抱えるとバイナリが膨らむ**（`go build` だけの素の exe で 36.9MB）。
sqlite と goja（読売の Nuxt ペイロードを評価する JS エンジン）が効いている。

`golang.design/x/hotkey` は現状ルートパッケージの `ParseHotkey` / `DefaultHotkey`
（文字列パースと既定値）だけに使っている。GUI アプリ自体のホットキー登録は
Wails 標準の `app.GlobalShortcut` を使っており、この節のライブラリを直接呼んではいない
（詳細は `ikkyoku/AGENTS.md` の「ホットキー」節を参照）。

## GUI アプリ（Wails3）

数値で座標を指定する方式は盤面に枠を合わせる操作では実用的ではないため、
画面の上に重ねる「透過した枠」で範囲を指定できる GUI アプリを `_cmd/ikkyoku/` に用意した。
枠を将棋盤の上にドラッグ・リサイズして合わせ、ボタンかホットキー(既定 `Alt+S`)で撮る。
**`ikkyoku` は「ルートパッケージ（ライブラリ）＋この GUI アプリ」の構成で、CLI は無い。**

**ウィンドウは 4 枚**（同じフロントを URL クエリで出し分けている）。

| ウィンドウ | 役割 |
|---|---|
| 枠 | 盤に重ねる透過ウィンドウ。**「どこを撮るか」の定義そのもの** |
| メイン画面 | アプリ本体（5 タブ）。閉じるとアプリが終了する |
| 評価値グラフ | **解析タブから切り離したグラフ**（任意） |
| 解析の列 | **解析タブから切り離した候補手・手順**（任意） |

- **透過**: `BackgroundType: BackgroundTypeTransparent` +
  `BackgroundColour: NewRGBA(0,0,0,0)` でクライアント領域(WebView の中身)を透過させる。
  フロントは 2px のガイド枠と上部のツールバーだけを描き、それ以外は完全に透明
- **Frameless**: 枠とメイン画面は OS のタイトルバーを持たない。枠は中継に重ねるので
  影も角丸も邪魔だから、メイン画面は**タイトルバーのぶんを盤に返す**ため
  （タブの行がタイトルバーを兼ねている）
- **キャプチャ領域の決定**: 「クライアント領域を、ツールバーとガイド枠のぶん内側へ
  オフセットした矩形」という決定論的な方式。タイミング依存(枠を消して撮る)の方式は
  採っていない。座標は Windows API の `GetClientRect` + `ClientToScreen` を HWND
  (`Window.NativeWindow()`)から直接呼んで**物理ピクセル**で取得する。Wails の
  `Window.Position()`/`Size()` は DIP(論理ピクセル)を返すため、マルチモニタで
  スケーリングが混在する環境ではそのまま使うとずれる
- **ガイド枠にクリックできる UI を置かない**: 置いた要素はそのままキャプチャに
  写り込む。操作するものはツールバー(撮る範囲の外)かメイン画面に置く
- **ペインを別ウィンドウへ切り離せる**: 評価値グラフと解析の列は、盤の大きさに
  効かない形で見たいことがある(`--board-size` は両方の取り分を引いている)ので、
  それぞれ窓へ出せる。**閉じればドックに戻る**
- **ウィンドウ状態の永続化**: 4 枚とも位置・サイズを終了時に保存し、次回起動時に
  復元する(`os.UserConfigDir()/ikkyoku/app-window.json`。ルートパッケージの
  `Config`(`config.json`)とは別ファイル)

ビルド:

```powershell
cd ikkyoku\_cmd\ikkyoku
npm --prefix frontend install    # 初回のみ
wails3 build                     # frontend のビルド〜bindings 生成〜go build まで一括
# または
wails3 dev                       # 開発モード
```

`wails3 build` で `bin\ikkyoku.exe` が生成される。詳細な設計判断は
`_cmd/ikkyoku/AGENTS.md` を参照。

## コード構成

- ルート（`github.com/ShinteLab/ikkyoku`）: ライブラリ。GUI に依存しない。
  主なパッケージは次のとおり

  | | |
  |---|---|
  | ルート | キャプチャ（`Capture` / `SavePNG`）と設定（`Config`） |
  | `app/` | **フロントに公開する Service**（設定・訂正・解析・棋譜・駒の字ほか） |
  | `recognize/` | 画像 → 盤面（`suteme` を呼ぶだけ） |
  | `position/` | **画像を知らない「とある局面」**。訂正・手順の木・棋譜の取り込み |
  | `analyze/` | 確定した局面 → 評価値（USI）。先手視点への統一と勝率もここ |
  | `legal/` | 合法手生成のラッパ（`engine` を呼ぶのはここだけ） |
  | `guide/` | ガイド枠の寸法と幾何 |
  | `piecefont/` | 端末のフォントから駒の字を焼く |
  | `training/` | 訂正した局面を `suteme` の学習用サーバへ送る |

- `_cmd/ikkyoku/`: Wails3 GUI アプリ(独立したネストモジュール、モジュール名は
  `ikkyoku`)。⚠️ **ここに置くのは「Wails の口が要るもの」だけ** ——
  Service は `app/`、枠の幾何は `guide/` にある
