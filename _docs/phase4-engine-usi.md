# 【決定済み】Phase 4 のエンジン接続を USI クライアント方式にする

**2026-08-08 に案 B（＋ Step 方式）を採用した。** 以下は決定に至った検討の記録で、
**この文書は履歴として残す**（実装の説明は `ikkyoku/CLAUDE.md` の「Phase 4」節）。

決め手は案 A の弱点そのもの ——「**自作 `engine` に縛られる**」。検討ツールとして
実用になるかは繋ぐエンジンの棋力で決まり、そこを自作 `engine` の完成に賭けるのは重い。

実装した順序も下記「段階的に入れる道」のとおり:

| Step | 状態 |
|---|---|
| Step 1（`io.Pipe` で同一プロセスの `engine`） | **完了**。`ikkyoku/usi/local.go` |
| Step 2（`os/exec` で外部エンジンの exe） | 未着手。`usi.Transport` を差し替えるだけ |
| Step 3（`prokishi.exe`） | 未着手。設定でパスを変えるだけ |

この決定を受けて `engine` 側に積み残しを整理した（**MultiPV が無いのが最大の穴**）:
`engine/TODO.md`。

## 決めること

**ikkyoku はエンジンを「Go の関数として呼ぶ」のか、「USI を話す相手として扱う」のか。**

この 1 点だけ。ここで決めた形が Phase 5（MultiPV・分岐ツリー）の作りをそのまま規定するので、
後から差し替えるのは安くない。

---

## 案 A: `engine` を直接 import する（現行の `TODO.md`）

```go
import "github.com/ShinteLab/engine"
```

- **速い。** 依存の向き（`ikkyoku → engine`）も既定路線どおり
- プロセス管理が要らない。起動・終了・タイムアウト・ハンドシェイクの一切が不要
- Go の型でそのまま扱える（`Board` / `Action` / `Info`）。文字列のパースが挟まらない
- `engine` の開発と ikkyoku の開発を一緒に進められる

**弱点は 1 つだけだが、それが重い。自作 `engine` に縛られる。**
検討ツールとして実用になるかどうかは繋ぐエンジンの棋力で決まる。
「次善手を選んだらどう転ぶか」を辿るのに評価が信用できないエンジンでは、
構想そのものが成立しない。やねうら王・水匠のような既存エンジンを挿す道が
最初から塞がっている。

## 案 B: ikkyoku を USI クライアント（＝将棋 UI）にする

ShogiGUI / ShogiHome と同じ立ち位置に ikkyoku が入る。
繋ぎ先は「USI を話すプロセス」であれば何でもよい。

| 繋ぎ先 | ikkyoku 側の差 |
|---|---|
| 既存エンジン（やねうら王・水匠など） | **無し** |
| `prokishi.exe`（リモート実行） | **無し**（後述） |
| 自作 `engine` | **無し** |

- 棋力の問題が設定の問題になる。エンジンを差し替えれば済む
- `engine` の探索やビルドの都合が ikkyoku に漏れてこない
- 自作 `engine` も同じ口から繋がるので、**A を捨てても `engine` が使えなくなるわけではない**

### prokishi に新しい口を作る必要は無い

prokishi の client は**それ自体が USI エンジンのフリをするプロセス**として作られている。

```
[将棋UI] ↕ stdin/stdout(USI) [prokishi client] ↕ gRPC [prokishi-server] ↕ [エンジン本体]
```

つまり ikkyoku が USI を話す側になった時点で、**prokishi 対応は
「設定でエンジンのパスを `prokishi.exe` にする」だけで終わる。**
新しい RPC もエンドポイントも要らず、prokishi 側は 1 行も触らずに済む。

逆に ikkyoku から gRPC で `prokishi-server` を直接叩く形にすると、
prokishi のルートパッケージ（client lifecycle）がやっている仕事を
ikkyoku で書き直すことになる。**そちらは採らない。**

### 「best を問い合わせる口」には丸めないこと

`GetBestMove(sfen) → 指し手` のような同期 API まで畳みたくなるが、
**それをやると Phase 5 の中核が最初から取れない。**

- **MultiPV が出せない。** 次善手を辿るのが構想の中心であって、`bestmove` 1 個では足りない
- **`info` の逐次ストリーム（深さ・評価値・読み筋）を捨てることになる。** 検討 UI の本体はこれ
- **`stop` で途中まで読んだ結果を使う**という検討ツールの基本操作が表現できない

USI がステートフル（`position` → `go` → `info`… → `bestmove`）なのは面倒に見えるが、
**その面倒さがそのまま欲しい機能**なので、素直に USI のまま扱う。

## 案 B を段階的に入れる道（A のコストで B の形が手に入る）

案 B の唯一の実コストは「プロセス管理」だが、**最初のステップではそれを払わなくてよい。**

`engine.NewUSI` は `io.Writer` / `io.Reader` を受け取る形になっている
（`engine/usi.go`。`Start()` で回る）。**プロセスを起こさずに `io.Pipe` で直結できる。**

```
Step 1  ikkyoku(USIクライアント) ──io.Pipe──> engine.NewUSI(...).Start()   ※同一プロセス
Step 2  ikkyoku(USIクライアント) ──os/exec──> 外部エンジン .exe
Step 3  ikkyoku(USIクライアント) ──os/exec──> prokishi.exe                 ※設定のみ
```

- **Step 1 は案 A と同じくらい速い。** プロセス管理・タイムアウト・異常終了の処理が
  まだ要らず、依存も `ikkyoku → engine` のまま
- それでいて **ikkyoku 側のコードは最初から USI クライアント**なので、
  Step 2 で `io.Pipe` を `os/exec` のパイプに差し替えるだけで外部エンジンに広がる
- Step 3 は実質ゼロ（設定でパスを変えるだけ）
- `engine` には `ContextEngine`（`GetBestContext(ctx, board, info func(Info))`）があるので、
  Step 1 の時点で `info` のストリームと `stop` によるキャンセルも成立する

**この道を取る場合、案 A と案 B は「どちらか」ではなく「B の Step 1 が A に見える」だけになる。**
判断の重さがかなり下がる。

## 責務の置き場所

既存の線引き（仕様は `core`、アプリのロジックは `ikkyoku`）にそのまま乗る。

| 置き場所 | 持つもの |
|---|---|
| `core/usi` | **プロトコルの語彙。** コマンド文字列の組み立て、`info` 行のパース、`option` の表現 |
| `ikkyoku` | **セッション管理。** どのエンジンをいつ起動し、いつ `stop` し、いつ捨てるか |

現状の `core/usi` は指し手の表記変換（`FormatSquare` / `ParseSquare` / `ParseMove`）だけで、
プロトコルの語彙は入っていない。**足すなら core 側**（Go と JS の 2 ソースを揃える方針も同じ）。

`prokishi/usi` にも似たもの（`Sender` がエンジンのサブプロセスを包む）があるが、
`ikkyoku → prokishi` という依存は今の依存図に無い。**そこは踏まない。**

## コストとリスク

案 B が案 A に対して増やすもの:

- `usi` → `usiok` → `isready` → `readyok` のハンドシェイク
- `go` 中に次の `position` が来たときの `stop` 待ち、応答が来ないときのタイムアウト
- エンジンの異常終了・応答なしからの復帰
- `info` 行のパースと UI への流し込み

**ただし上記「段階的に入れる道」の Step 1 では、このうち最後の 1 つしか要らない。**
残りは Step 2 で外部プロセスに広げるときに初めて必要になる。

リスク:

- `core/usi` にプロトコルの語彙を足す判断が要る（Go / JS 両方を揃える方針との兼ね合い）
- USI のオプション（`setoption`）はエンジンごとに違う。汎用の設定 UI を作り込むと重い。
  **最初は素通しでよい**（設定ファイルに書いたものをそのまま送る）

## 案 A のままにする理由があるとすれば

- **自作 `engine` を育てること自体が目的なら、A のほうが摩擦が少ない。**
  ikkyoku が engine の実利用者になり、API の使いにくさが早く分かる
- 検討 UI を作り切るまでは棋力が問題にならない（表示と操作の確認が先）ので、
  棋力の話を後回しにする判断もありうる

## 決着（2026-08-08）

- ~~案 A / 案 B（+ Step 方式）のどれを取るか~~ → **案 B の Step 方式。** Step 1 実装済み
- ~~`core/usi` にプロトコルの語彙を足すか、ikkyoku 内に閉じるか~~ → **`core/usi` に足した**
  （`protocol.go`。`info` 行と `bestmove` 行の読み取り）。**JS 側（`core/web`）には
  対応物を置いていない** —— USI を話すのはデスクトップアプリの Go 側で、ブラウザは
  構造化された結果しか見ないため。ブラウザから USI を扱う必要が出たら、そのときに揃える
- 千日手・連続王手の判定ができない件（履歴のない局面を渡すため）→ **仕様として受け入れる。**
  設計原則1（どの層も履歴に依存しない）そのものなので、直す対象ではない

## 実装して分かったこと

- **`go movetime` が使えない。** 自作 `engine` の `parseGoTime` は
  `btime`/`wtime`/`byoyomi`/`binc`/`winc` しか読まない。そのため
  **常に `go infinite` で投げ、打ち切りは ikkyoku 側の `stop` で行う**形にした。
  外部エンジンでも「こちらが時間を握る」ほうが揃っているので、向こうが直っても
  この形は変えなくてよい
- **詰みが `score cp` で来る。** 自作 `engine` は `score mate` を出さず、
  `MateScore - ply` の生値を `score cp` に詰める。`analyze` 側に推定を入れてあるが、
  **`score mate` を返すエンジンではそちらを優先する**（`engine/TODO.md` の 2）
- **エンジンが送受信した行を全部 `slog.Info` に出す。** テストでは捨てているが、
  アプリでは解析のたびに info 行が全部ログに流れる（`engine/TODO.md` の 4）
