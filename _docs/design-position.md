## Phase 3/5: 局面を扱う層（`position`）

**2026-08-07 決定。** 訂正（Phase 3）も検討ツリー（Phase 5）も `position` の上に載っている。

### `position` パッケージ（画像を知らない層）

局面矯正（Phase 3）と検討ツリー（Phase 5）は **`ikkyoku/position`**。
**別モジュールには切らない**（`ikkyoku → core` の依存で足りる）。

⚠️ **`recognize` には入れない。** あちらは画像を知っている層で、`position` が扱うのは
**画像を一切持たない「とある局面」**。境界は「`recognize` が返した盤面を受け取ったら、
そこから先は画像を参照しない」。**`position` の型に画像やその座標系を持たせないこと。**

**型と不変条件は `position/AGENTS.md`**（⚠️ `HandsFixed` を落とさない / `Cell` の
ゼロ値が空マス / 駒台の未決を片側に寄せない / `SFEN` と `LabelSFEN` の使い分け /
`Study` の枝の規則 / `Rotate180` / 手数と手番）。

### 訂正 UI（**入っている**。2026-08-07 に実機で確認済み）

**「存在するはずの駒」を中心に回す。** 盤上の枚数ではなく**残り**（先後合計の上限 −
盤上）を駒箱に出す。認識は**余計な駒を作る**（実測で香が 11 枚）ので、過剰は
「n枚多い」という負の残りとして出し、**盤から外す先**を用意する
（`position.Inventory()` がその 1 行ぶん）。

⚠️ **訂正タブに居ること自体が訂正モード**（トグルは無い。タブが意味の境界）。
**画面の作りは `_docs/ui/editor.md`**、**訂正 → 解析の継ぎ目は `app/AGENTS.md`**
（`Adopt` の 1 か所だけ）。

#### ⚠️ 詰将棋のような「正常でない局面」も確定できること

**訂正の対象は対局の局面だけではない。** 詰将棋は玉が 1 枚しかなく、駒数保存則も
静的合法性も成立しないが、**それで正しい**。「論理的におかしくても確定する」は
想定内の使い方であって、異常系ではない（**警告は出すだけ・確定を止めるのは未決だけ**。
制約は `position/AGENTS.md` と `_docs/app-handicap-mate.md`）。

**詰将棋は「操作」ではなく「属性」**（2026-09-12。`position.MateProblem`）。
「この盤は詰将棋だ」と決めた時点で**余った駒の行き先（玉方）は決まっている**ので、
盤を直すたびに自動で追随させる。寄せる操作（「まとめる」）は**押し忘れれば確定できず**、
一度入れて外した。⚠️ **手合割（`HandsFixed`）とは排他** —— どちらも「盤にも駒台にも
無い駒」への答えで、手合割は**存在しない**、詰将棋は**玉方が持っている**。

⚠️ **攻方の玉が無い局面は同梱エンジンにしか渡さない**（外部エンジンは落ちずに
**黙って返ってこない**）。⚠️ **攻方の玉を仮置きする案も採らない** —— 玉方が王手で
手番を稼げてしまい、**別の問題を解いて「解けました」と出す**ことになる。
長手数は詰将棋エンジンの `go mate` で解く。

**全体像（3 通りの解釈・入口・側の呼び名）・詰将棋エンジンの繋ぎ方・
どのエンジンが何を返すかの実測はスキル `ikkyoku-handicap-mate`。**

### 視点（画面のどちら側が手前か）

⚠️ **「視点」という 1 語に 2 つの別の話がぶら下がっている。混同しないこと。**

| | 何の話か | どこで効くか |
|---|---|---|
| **A: 表示視点**（`#study-flip`。2026-08-13） | **どちら側から盤を眺めるか。** 局面には一切効かない | 解析タブの画面だけ。⚠️ **Go 側は視点を知らない**・訂正タブには無い（撮った画像と見比べられなくなる）。`_docs/ui/layout.md` |
| **B: 取り込みの向き**（訂正タブの「目線」。2026-08-18） | **撮った画像が後手目線だと、盤面そのものが上下逆に返る。** 局面が間違っている | **訂正 → 解析の境界の 1 回だけ**回す（`adoptPosition` → `position.Rotate180`）。`_docs/app-viewpoint.md` |

**A は「見え方の好み」、B は「モデルが間違っている」。** A をいくら切り替えても
B は直らない（盤の絵を裏から見るだけで、SFEN は 1 文字も変わらない）。

- ⚠️ **B は黙って間違う。** 自己矛盾が無いので警告も出ないし信頼度も落ちない。
  訂正 UI でも直せない（先後反転を 40 枚やっても盤の上下は直らない）。だから人が選ぶ
- ⚠️ **認識も訂正も、画像に見えたとおりの盤面を持つ**（取り込みで反転しない）。
  見えたものと違う盤面を返す層があると**どこで像がねじれたか追えず**、
  **学習ラベルが画素と一致しなくなる**（`design-capture.md`「訂正した局面は学習にも回す」）
- ⚠️ **回す場所は訂正 → 解析の境界。** エンジンに渡す直前まで引っ張ると、
  解析タブの盤・手順・棋譜・評価値が全部ひっくり返ったままになる
- ⚠️ **勝手に反転させないこと**（A も B も）。ユーザーが押したときだけ切り替わる、を
  崩すと「勝手に盤が回るアプリ」になる
- **正式な SFEN を要求するのはエンジンだけ。** 手番か駒台の先後が未決なら
  `Position.SFEN()` がエラーを返し、解析は始まらない（設計原則5）

### 永続化は前提にしない（メモリのみ＋クラッシュ対策の自動保存）

検討ツリーは**メモリ上の「検討セッション」**として持つ。**1 時間で捨ててよい情報**の
ために、保存形式・一覧 UI・寿命管理を先に決めない（設計原則1。ツリーが無くても
撮った 1 局面の解析は成立する）。**木は `core/kifu` の形で持つ** —— 後から残したく
なってもシリアライズするだけで済む、が先送りしても損しない条件。

入れたのは 3 つだけ（2026-09-16〜26。**制約は全部 `_docs/app-studystore.md`**）:

| | 何をする | なぜ |
|---|---|---|
| **自動保存**（`StudyStore`） | 木と評価値を控え、起動時に前回の続きを戻す | 再起動のたびに積み上げた評価値が消えていた |
| **棚と結ぶ**（`GameID`） | 棋譜タブの「解析する」で前の検討の続きが開く | 同じ棋譜を開き直すたびにゼロから |
| **出どころの鍵**（`SourceKey`） | 棚に入れる前の検討も、同じ棋譜にあとから結ぶ | 中継は数時間かけて完成し、そのあいだに別の棋譜を解析するのが普通 |

- ⚠️ **一覧 UI も管理機能も作らない**（入れたのは「前回の続きを戻す」だけ）。
  ⚠️ **一覧の行に「検討あり」の印も出さない** —— ほとんどの棋譜は一度は開くので
  **全部に付いて情報量がゼロ**になる
- ⚠️ **同一性を棋譜から借りないこと**（設計の要）。棚の主キーは `(source, source_id)`
  なので**中継を撮っている最中は行が作れない**。解析セッションは自前の id を持ち、
  棋譜とは**あとから結ぶ**
- ⚠️ **控えは棋譜ではない**（交換形式にしない）・**控えはおまけ**（書けなくても
  読めなくても解析は動く。設計原則3）
- ⚠️ **開き直しても棚の棋譜を据え直す**（`Graft`）。棚の側が伸びていても**枝と評価値を
  捨てない**（`TODO.md`「本譜は URL が更新し続け、分岐は手入力」）
- **検討を棚へ入れる口（`KifuService.SaveStudy`）は画面から外した**（2026-09-26。
  押し間違えるうえ、終局後に入れる使い方は出どころの鍵で足りる）。撮った局面が根でも
  **盤面図**で書ける（⚠️ **黙って平手として出さない**。`core/kifu/AGENTS.md`）
