## Phase 2: suteme への接続（**動いている**）

撮った画像を `suteme` に渡し、返った SFEN で盤面を描くところまで繋がっている
（`recognize` パッケージ → `CaptureService.Capture` → メイン画面）。

**認識の精度はまだ低い**（実測で `L: 11枚（上限4）` のような警告が出る状態）。
これは Phase 2 の失敗ではない。**「今どれくらいか」が見えるようになったこと自体が成果**で、
精度は学習データを育てて上げていく。`Result.Warnings()` がそのまま
「どれくらい外しているか」の指標になっている。

### 認識の継ぎ目 — **詳細は `recognize/AGENTS.md`**

`recognize` パッケージが `suteme.Recognize` を呼び、`Board` にまとめる。
⚠️ **認識器はここに書かない**（suteme の責務）。⚠️ **Phase 3 の局面矯正層も
`recognize` に入れない**（2026-08-07 に方針変更）—— あちらは**画像を知っている層**で、
訂正から先が扱うのは**画像を一切持たない「とある局面」**（`position`）。

- **`CaptureService.Capture` が撮った直後に呼び、`CaptureResult` に
  `sfen` / `confidence` / `warnings` / `handTotal` / `recognizeError` / `debug` を載せる**
- ⚠️ **認識に失敗してもキャプチャは成功として扱う**（設計原則3）。PNG の保存は済んで
  おり、盤が出ない代わりに理由が UI に出るだけ
- ⚠️ **`suteme` の型を包み直さない**（`recognize.Option` / `recognize.Debug` は
  型エイリアス）。同じ形の型を定義し直すと、変換のぶんだけ嘘が入る余地が増える

`recognize/AGENTS.md` にあるのは: **使う API と既定のまま呼ぶ理由** /
⚠️ **学習データの置き場所**（駒種推論器と**盤の縁の帯の判定器**の 2 つ。片方だけ
配線して事故った）/ ⚠️ **認識器は 3 段**（学習データ / 配布モデル / 焼き込み。
`auto` を焼き込み優先にしないこと。下の「決定: 認識器は 3 段」）/ **焼き込みのビルド手順** /
**分かっていること**（駒数保存則の逆算・`Debug` の使い道）。

### 撮る → 訂正 → 解析、の間にある約束

**タブが意味の境界になっている**（5 枚。並び順・ラベル・画面の作りは `_docs/ui/screens.md`）。

| タブ | 何をする面か | 盤 |
|---|---|---|
| 入力 | 局面を**取り込む**（新規対局・キャプチャ・棋譜の貼り付け・URL から取得） | 無し |
| 棋譜 | **棚（棋譜データベース）から探して解析へ送る** | 無し |
| 訂正 | 認識の誤りを**直して確定する** | **自由編集**（合法性を問わない・未決でよい） |
| 解析 | 確定局面から**手を進めて評価値を追う** | **合法手だけ**動かせる |
| 設定 | 設定 | — |

⚠️ **訂正タブと解析タブは別の局面を持っている**（`PositionService` / `StudyService`）。
繋がるのは**「この局面を解析する」の 1 回だけ**（写しを渡す。`app/AGENTS.md` の `Adopt`）。
**片方の値をもう片方に流用しないこと。**

⚠️ **撮ることと認識することを分ける**（イベントは `capture:shot` → `capture:done` の 2 段）。
認識には数秒かかり、1 回だけ知らせていた頃は**待つあいだ今どの画像の話なのかが
読めなかった**（`_docs/ui/screens.md`）。

**入口は「何を通って、どこへ行くか」で決まる**（行き先ごとの制約は `app/AGENTS.md` の索引から引く）:

| 入口 | 通る層 | 行き先 |
|---|---|---|
| **画面から撮る** / **画像ファイルを読み込む** | 認識（`recognize`）。⚠️ **同じ経路**（`_docs/cmd-capture.md`） | **訂正タブ**（まず直すもの） |
| **棋譜を貼り付ける**（KIF） | 認識を通らない | **解析タブ**（既に確定している） |
| **新しく対局を始める**（手合割） | 何も通らない | 解析タブ（初期局面は手合割で一意） |
| 手合割を「訂正タブで調整」/ **詰将棋を並べる** | 何も通らない | **訂正タブ**（表に無い局面を人が作る。スキル `ikkyoku-handicap-mate`） |
| 訂正タブ → **本譜に繋ぐ** | 盤面の差分を手順に復元（`position.Connect`） | 解析タブ（⚠️ **根を入れ替えず、本譜の先へ足す**。Phase 6） |
| **棋譜の URL**（**どのサイトでも 1 つの欄**）→ 取得 | 取得（`kicho.Fetcher`）だけ | **カード** → 「解析する」で解析タブ / 「保存」で棚 |
| **棋譜タブの「解析する」** | 棚から読むだけ | 解析タブ |

- ⚠️ **「棚に入れる」と「解析する」は別の系統。** 棚は解析の前提条件ではない（下記）
- ⚠️ **URL の欄を取得元ごと・行き先ごとに分けないこと。** ユーザが持っているのは
  「棋譜の URL」1 つで、読売か連盟かは**こちらの都合**。判別は kicho が持つ
- **KIF の読み取りも指し手 → USI の変換も `core/kifu`**（ikkyoku にもフロントにも書かない）

### 駒の描画と駒の字

- **盤は `core/web` の `<shogi-board>` をそのまま配信する**（`/shinte-web/`。
  ファイルをコピーしない・npm 依存にしない。`_docs/ui/screens.md`）
- **駒の字を端末のフォントから焼ける**（設定タブ）。同梱して配る駒フォントは再配布を
  認めるライセンスに限られるが、**自分の端末のフォントを自分の端末で表示に使うのは
  再配布ではない** —— そこだけを通す経路。⚠️ **焼いた字を書き出す口を作らないこと**
  （`piecefont/AGENTS.md`）

### 棋譜データベース（棚）— **kicho をライブラリとして使う**（2026-09-04）

**`ikkyoku` は「ユーザ環境で動く将棋ソフト」**なので、棋譜のデータベース化も
ikkyoku から使えないと**ユーザが 2 つのアプリを立ち上げる**ことになる。
kicho の UI が持っていた機能（取得 / 登録 / 蔵書）を ikkyoku へ移した。
⚠️ **実装は `kicho` のままで、ikkyoku は利用する側。**

- ⚠️ **棚は解析の前提条件にしない。** `kicho.Open` が失敗してもアプリは起動し、
  撮った 1 局面と貼った棋譜は解析できる（設計原則3）。**棋譜タブだけ**が機能しない
- ⚠️ **取得元の知識をこちらに書かない**（`source_url` の決め方・文字コード・手数の
  数え方・取り直せる URL か）。同じ変換を `kicho/_cmd/kicho` も持つので、書くと必ず割れる
- ⚠️ **goja が第三者サイトの JavaScript を ikkyoku のプロセス内で実行する**
  （読売の Nuxt ペイロード）。**同じプロセス**で盤面キャプチャもエンジンも動く

**線引き・DTO・制限時間・DB の場所・棋譜タブ・カード・仮の一覧は `_docs/app-shelf.md`。**

## 決定: 認識器は 3 段（2026-10-04）

**基本は焼き込みで動かす。ダウンロードした配布モデルを置けばそちらを、自分で学習した
データを指せばさらにそちらを使う。** 3 段で、上ほど優先する:

| 段 | 何か | 置き場所 | 設定 |
|---|---|---|---|
| 1. 学習データ | suteme で**自分で育てた**もの（生の `training_data_v*.bin` / `strip_data_v1.bin`） | suteme の学習ディレクトリ | `sutemeDataDir` |
| 2. 配布モデル | **ダウンロードして置いた**配布セット（`predictor.bin.gz` / `strip.bin.gz` / `source.txt`） | 既定は `%LOCALAPPDATA%\ikkyoku\model` | `sutemeModelDir`（空なら既定） |
| 3. 焼き込み | **exe に最初から入っている**配布セット（`-tags embedmodel`） | exe の中 | — |

設定 `sutemeSource` は「どの段から見始めるか」（`auto` / `dir` / `model` / `embed`）。
**置かれていない段は黙って飛ばし、置いてあるのに読めない段は ⚠ に出して下へ落とす。**
どの段も読めなければ盤面が読めない（撮ること・棋譜・解析は動く。設計原則3）。

**なぜこの形か:**

- **上の段を優先するのは、置いたもの・指定したものが利用者の意思表示だから。**
  焼き込みは配るときに固定したデータで、学習データは育て続けるデータ。⚠️ **`auto` を
  焼き込み優先にしないこと** —— 開発中に焼き込みへ倒れると、**学習データを更新しても
  反映されない**という最も気づきにくい事故になる
- **読めない段は飛ばして下で動く**（以前は、指定したディレクトリが読めないと焼き込みが
  あってもエラーで止まっていた）。読めない理由は画面の ⚠ に出す（`_docs/cmd-windows.md`
  の「起動で黙って消えない」）。黙って落ちると、置いたモデルが効いていないことに気づけない
- ⚠️ **駒種の推論器と盤の縁の判定器は同じ段から 1 組で差し替える**（`recognize.Set.Use`）。
  別々に読むと「駒種は最新の学習データ、盤の位置合わせは学習前」になる（2026-08-22 に踏んだ）
- ⚠️ **配布モデルは焼き込みと同じ形にする。** 焼き込み＝「exe に最初から入っている配布セット」
  なので、読む口が 1 本で済む（`recognize.LoadPack` と `LoadEmbedded` が組み立てを共用）。
  作り方も同じ（`task model:copy` が作る `recognize/model/` の 3 ファイルがそのまま配布モデル）
- ⚠️ **形式の版が合わない配布モデルは読めずに下へ落ちる**（suteme の読み込みが断る）。
  古い exe に新しい形式のモデルを置いても、焼き込みで動く
- ⚠️ **焼き込みより古い配布モデルは使わない**（`source.txt` の日付で比べる。`auto` のとき）。
  exe を更新したのに、昔置いたモデルが優先されて精度が下がるのを防ぐ。**「配布モデルから」を
  選んでいれば古くても使う**（意思表示）。日付が読めないものは古いと見なさない
- ⚠️ **配布モデルの既定の置き場所は exe の隣にしない。** Program Files には書けず、
  exe を置き換えるたびに一緒に動かすことになる。設定（`%APPDATA%`）とも分けて
  `%LOCALAPPDATA%` に置く（10MB 級で、移動プロファイルに乗せるものではない）
- ⚠️ **suteme 既定の探索（カレントディレクトリ → 実行ファイルの隣）は使わない。** 認識器を
  1 組も差し替えていなければ `recognize.FromImage` は suteme を呼ばずに断る
  （`ErrNoRecognizer`）。呼ぶと、たまたま置いてあったファイルで黙って動く
- **配布モデルの取得は、今は手で置く**（2026-10-04）。アプリから取りに行く口
  （取得元・新しいモデルがあるかの確認）は後回し。置く手順はスキル `ikkyoku-build`
- **自分で学習するのは suteme の仕事**（ikkyoku はラベリング UI を作らない。下の決定）。
  ikkyoku からは「訂正した局面を suteme に送る」だけ

## 決定: 訂正した局面は学習にも回す（2026-08-07・Phase 5 で実装）

**「ikkyoku を学習データの収集ツールにはしない」（2026-08-04）は生きているが、
訂正結果の還元はその例外。** あの決定の理由は「ラベル入力そのものがきついので、
入口を増やしても解決しない」だった。Phase 5 の訂正 UI は**エンジンに正しい局面を渡すため**に
人間がどのみち行う作業なので、**ラベル入力のコストが既に払われている**。捨てるのは勿体ない。

- **ikkyoku にラベリング UI は作らない。** 作るのは訂正 UI（別目的）で、そこに
  「学習に回す」の 1 操作を足すだけ
- **書き出しの実装は `suteme` に置く。** 学習サンプルの単位は
  **（PNG・SFEN の盤面フィールド・盤面矩形）の 3 点組**で、そこから 81 マスを切り出している
  （`suteme/training/server.go` の `samplesFromRegion`。履歴は `data/<id>.png` + `history.json`）。
  ikkyoku がこの形式を知って自分で書くと、向こうが変わったときに黙って壊れる。
  ikkyoku が渡すのは画像と正解の局面まで
- **自動では送らない。** 「決定」で無条件に送ると、人間が直したのは 1 マスで残り 80 マスは
  推論結果のまま、という自分の出力を正解として食う形になり、間違いが固定される
- **画面に見えていない駒を知識で補った訂正は送らない**（テロップで盤が隠れている等）。
  ラベルが画素と一致しなくなる。これも自動送信にしない理由

**実装と規約は `training/AGENTS.md`**（`POST /api/register` の形・
⚠️ **送る SFEN で持ち駒を落とさない**（`LabelSFEN`）・
⚠️ **ループバックからは「登録受付: 無効」でも送れる**・
⚠️ **送る SFEN は「手前が先手」の規約に従う**・
⚠️ **駒台の情報は「意味が無い」のではない**）。

## 経緯: なぜ Chrome 拡張ではなくネイティブなのか

**もともとは Chrome 拡張だった。** Phase 0 の検証で、ABEMA が Widevine DRM で
`<video>` の画素を保護しており **Chrome 自身のキャプチャ API はいずれも黒フレームになる**
一方、**OS レベルの画面キャプチャは DRM を素通りする**ことが分かった。そのため入口を
ネイティブアプリに切り替えた（検証当時の `_probe-chrome/` は削除済み）。
⚠️ **この結論は再検証しなくてよい**（2026-08-04 / ABEMA 将棋中継で実測）。
経路ごとの結果は `_docs/phase0-capture.md`。

この結果、**放送局ごとのアダプタも供給元の抽象化（`SourceAdapter`）も不要**になった。
画面に映ってさえいれば ABEMA でも YouTube でもキャプチャボードでも同じ経路で扱える。
また Go ネイティブになったことで、`suteme` / `engine` を直接 import できる
（WASM も gRPC-web も Native Messaging も不要。この検討は全部消えた）。
