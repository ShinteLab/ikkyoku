# メイン画面が真っ黒になって触れなくなる（調査ログ）

2026-08-08 / 2026-08-13 に発生。**まだ再現待ちで、原因が確定していない。**

⚠️ **ここは調査の記録。** 守るべき制約（ネイティブ DnD に戻さない・
`RepairMain` の入口を枠から動かさない・心拍の閾値 90 秒・表示状態のログを消さない）は
`AGENTS.md` の「メイン画面が真っ黒になる」に置いてある。**次に黒くなったらここを読む。**

**症状**: メイン画面が真っ黒になり、クリックもキー操作も受け付けなくなる。
**Go 側は無傷**（黒くなったあとの `Alt+S` で PNG が保存できている）。
ログに出たのは `[WebView2] Focus failed: The group or resource is not in the correct state`
が数行だけで、他には**何も出ない**。

#### 2026-08-13 の 2 回目 — **仕込んだ計測が答えを出した**

**下の「疑っていること」（最小化で不可視のまま取り残される説）では説明が付かない。**
計測はこの判別のために入れたものなので、**まずここを読むこと。**

```
15:21:57  盤面を認識しました        ← 正常
15:23:33  心拍（main / frame の両方）← ここが最後
15:23:35  Eval failed ×4            ← 2 秒後から、以後ずっと失敗し続ける
15:25:06  心拍が途切れました（90 秒閾値）main / frame とも 隠れていた=false
```

| 観測 | 何を否定するか |
|---|---|
| **2 枚が同じ秒に心拍停止** | 最小化説は**ウィンドウ単位**の話。2 枚まとめては起きない |
| 両方 `隠れていた=false` | タイマーの間引きではなく本当に止まっている |
| `heapMB` 11 / 12 | メモリ枯渇ではない（元から薄いと見ていた線が消えた） |
| `Focus failed` **だけでなく `Eval failed`** | ⚠️ **ここが決め手**（下記） |

⚠️ **`Eval failed` は「ページが壊れた」ではなく「WebView2 の側が居ない」。**
ページの JS 文脈さえ生きていれば `ExecuteScript` は通るので、
**dev server や HMR の事故なら `Eval` は成功する**（1 度そちらを疑って外した）。
通らないということは、コントローラが有効な状態にない＝**WebView2 が落ちている**。

**2 つのウィンドウは同じ WebView2 環境（＝同じブラウザプロセス）にぶら下がっている**ので、
それが落ちれば 2 枚まとめて黒くなり、以後 Go からは何も差し込めなくなる。これは
**心拍が止まる側**（下の表）で、⚠️ **`RepairMain` は原理的に効かない**（戻す相手が居ない）。
**手当てはプロセスを終了して起動し直すことだけ。**

⚠️ **起動し直すときは古いプロセスを必ず落とすこと。** 単一インスタンスの防止は
入れていないので 2 つ走る（`app-window.json` の二重書き込み・ホットキー登録・
エンジンのプロセスが重なる）。

#### 引き金は**訂正タブのドラッグ**だった（→ ネイティブ DnD をやめた）

**2 回とも、訂正タブで「足りない駒」をドラッグしている最中に始まっている。**
しかも**先に DnD が壊れ、そのあと黒くなる**という順序（1 回目は掴めなくなり、
2 回目はドロップできず禁止カーソルになった。**そこから何度か試しているうちに黒くなった**
ので、特定の操作が引き金というわけではない）。

Windows の Chromium はネイティブ DnD を **OLE の `DoDragDrop`** で動かしており、
**ブラウザプロセスの UI スレッドでモーダルなループが回る**。そこが抜けられなくなると:

- 掴めない / 落とせない（ドラッグの状態機械が「継続中」のまま取り残される）
- 画面が黒い・入力を受け付けない（合成も入力もそのスレッドが握っている）
- Go の `Eval` / `Focus` が失敗し続ける（**同じスレッドへ行く**）
- **2 枚同時に心拍が止まる**（同じ WebView2 環境＝同じ UI スレッド）

⚠️ **Chromium の中の話なので、こちらから直せる場所が無い。** そこで
**訂正タブのドラッグを pointer events に置き換えた**（2026-08-13。`editor.ts`）。
pointer events は**レンダラの中で完結する**のでこのループに入らない。
⚠️ **ネイティブ DnD（`draggable` + `dragstart`/`drop`）に戻さないこと。**

⚠️ **2 回とも「長時間起動しっぱなし」の状態で起きている。** 撮った直後や起動直後では
**まだ一度も起きていない**。ドラッグは何十回も通っているのに 2 回しか起きていないのは
この条件で説明が付き、**何かが積み上がった末に壊れている**ことを示唆する
（＝ドラッグは引き金であって、原因そのものではないかもしれない）。
⚠️ **短時間の動作確認では再現しない**ので、**「触ってみて大丈夫だった」を根拠にしないこと。**

⚠️ **これで直ったと決まったわけではない**（因果は状況証拠。2 回とも同じ入口、
という一致に基づく）。**次に黒くなったら、まずドラッグしていたかを思い出すこと** ——
ドラッグしていないのに起きたなら、この線は外れている。

**なぜ DnD が壊れたか自体は分かっていない。** 直前は認識が通っており、
フロントの例外（`ReportError`）は 1 行も出ていない。⚠️ **`ProcessFailed` を握る話は
当面不要**（あれはプロセスが死んだときの話で、**詰まりには反応しない**）。

#### 疑っていること（**2026-08-13 の回には当てはまらない**。上を読むこと）

Wails beta.3 は `WM_SIZE / SIZE_MINIMIZED` で **WebView2 のコントローラを不可視にする**
（`chromium.Hide()` = `PutIsVisible(false)`。`webview_window_windows.go`）。
**元に戻すのは復帰の分岐 1 か所だけで、しかも条件付き**:

```go
if (w.windowShown || w.showRequested) && w.webviewNavigationCompleted &&
	w.chromium != nil && w.chromium.GetController() != nil {
	_ = w.chromium.Show()
}
```

ここを取りこぼすと**コントローラは不可視のまま戻らない**。そのときの窓が症状と一致する:
黒い（何も合成されない）・入力を取らない・`MoveFocus` が「状態が正しくない」で失敗する
（Wails 自身のコメントも *"MoveFocus can legitimately fail ... when the window is hidden
or minimised"*）・**JS は動き続けている**。

**`revealMain` はキャプチャのたびにこの経路を踏む**（中継を観ながら使う以上、メイン画面が
最小化・背面にあるのが常態）。そのため `Show()` より先に `UnMinimise()` するよう直した。
**畳まれたままの窓に `Show()` を当てないこと。**

#### 復帰手段（枠のメニュー →「メイン画面を描き直す」）

`CaptureService.RepairMain`。中身は `Hide()` → `revealMain()` だけで、Wails がこの 2 つで
`PutIsVisible(false)`/`(true)` を呼ぶので、不可視のまま取り残されたコントローラが戻る。

⚠️ **入口を枠に置いてあるのが要点。** 黒くなるのはメイン画面なので、メイン画面の中に
ボタンを置いても押せない。**この入口を「メイン画面の設定タブへ移す」ような整理をしないこと。**

⚠️ **効くのは「心拍が続いている」ときだけ。** 2026-08-13 の回のように WebView2 ごと
落ちている（`Eval` が通らない）場合は**戻す相手が居ないので何も起きない**。
**黒くなったら、押す前にログの心拍を見ること**（押しても直らないのを見てから
ログを読むと、その間に状況が動く）。

#### 計測（`diagservice.go` / `frontend/src/main.ts`）

**次に起きた 1 回で決まるようにしてある。** フロントが 5 秒ごとに `DiagService.Heartbeat` を
呼び、途切れたら Go 側が warn を出す。

| 黒くなったとき | 意味 | 手当て |
|---|---|---|
| **心拍が続いている** | JS は生きていて、WebView2 が不可視にされているだけ | 「メイン画面を描き直す」で戻る |
| **心拍が止まる** | レンダラが死んでいる**か、UI スレッドが詰まっている** | 描き直しでは戻らない。起動し直すしかない |

⚠️ **「心拍が止まった＝レンダラの死」と読まないこと**（2026-08-13 に訂正）。
心拍は `DiagService.Heartbeat` の**呼び出し**なので、**UI スレッドが詰まれば、
JS が動いていても Go には届かない**。2 回目がまさにそれ（上記のドラッグの件）。
⚠️ **手当ては両方とも同じ**（描き直しでは戻らない）なので、**この表で判断を
分けるのは「描き直すか / 起動し直すか」まで**。それ以上は `Eval` が通るかで見る。

- ⚠️ **閾値を短くしないこと**（90 秒）。Chromium は**隠れている・最小化されている**ページの
  タイマーを間引き、`setInterval` は最悪 1 分に 1 回まで落ちる。**追っているのがまさに
  最小化まわりの現象**なので、短い閾値だと調べたい状況で必ず誤検知する。
  `document.hidden` も一緒に送っているので、途切れたときに見分けが付く
- `window.onerror` / `unhandledrejection` も Go 側のログへ流す。**今までフロントの例外は
  どこにも出ていなかった**ので、「例外は出ていない」を根拠にできなかった
- ウィンドウの表示状態（表示・非表示・最小化・復帰・戻す）も 1 行ずつログに出す
  （`registerVisibilityLog`）。**最小化 → 復帰の並びのどこで戻し損ねたかは、記録が無いと追えない**。
  ⚠️ **ただし debug で出す**（2026-08-11）。枠を動かすだけで「戻す」が大量に出て、
  **他のログが埋もれる**ため。**アプリのログレベルは info のまま**なので既定では出ない。
  **消さないこと** —— 出すのをやめたのではなく、普段は黙らせているだけ
  （追うときはこの 1 行を Info に戻すか、ハンドラの Level を debug にする）
- **メモリ枯渇の線は消えている**（発生時のキャプチャは 10〜20 枚。1 枚 650KB の base64 では
  レンダラが死ぬ水準に遠く届かない）。ヒープを心拍に載せているのは次に疑う順番を決めるため
