# app: エンジンの登録・option・AnalyzeService

**`settings.go`（エンジンの登録）・`analyzeservice.go` を触るときに読む。** `app/AGENTS.md` から分けた**制約**（「⚠️ …しないこと」）で、
⚠️ **自動では読まれないので、触る前に必ずここを開くこと**（索引は `app/AGENTS.md`）。

## エンジンの登録（設定タブ）— **複数登録できる**（2026-08-11）

**繋ぎ先は設定の問題**にしてある（`ikkyoku.Config` の `engines`）。
**1 つに絞らない** —— 登録は一覧で、`enabled` を付けたものが**解析のときに同時に走る**。

```json
{ "engines": [
    { "id": "engine-1", "name": "やねうら王", "path": "D:/shogi/YaneuraOu.exe",
      "options": { "USI_Hash": "1024", "Threads": "4", "EvalDir": "eval" }, "enabled": true },
    { "id": "builtin", "enabled": true }
  ] }
```

- **なぜ複数か。** どのエンジンが正しいかは局面によって違うので、**評価が食い違う
  ところを並べて読めること**自体が「別の選択も一つの局として辿る」という構想に効く。
  同じ exe を **option 違いで 2 つ登録**して比べるのも正当な使い方（だから鍵はパスではなく `id`）
- ⚠️ **`engines` が空なら同梱エンジン 1 つ**として扱う（`Config.EngineList`）。
  設定ファイルを作っていない状態でも解析できる、という既定の挙動を変えないため。
  **「空だったら同梱」を呼び出し側に書かないこと**（判断が 2 か所に散る）
- ⚠️ **旧形式（`engine: { path, options }`）は読み込み時に `engines` へ移す**
  （`migrateEngines`。移したら旧欄は捨て、次の保存でファイルからも消える）。
  **移行を落とすと、設定してあった外部エンジンが黙って同梱に戻る**（画面には何も出ない）
- ⚠️ **「外部エンジンを使う」の真偽値は持たない。** **パスが空なら同梱、入っていれば外部。**
  2 つ持つと「パスが入っているのに無効」という食い違いが起きる
- **`enabled` を外しても登録は消えない。** エンジンを入れ替えて比べる作業では、
  外したものをまた戻すことが多い。**全部削除すると同梱エンジン 1 つに戻る**
  （解析できない状態に落とし込まない）
- **並べ替えられる**（各行の ▲▼。`SettingsService.MoveEngine`。2026-08-12）。
  **一覧の順序は表示の順序そのもの** —— 解析タブのエンジンごとの結果も、
  評価値グラフの折れ線も、勝率バーが最初に出すエンジンもこの順で決まるので、
  **よく見るものを上に置けること**は要る。
  - ⚠️ **順序は「優先度」ではない。** 上が正しいという意味も、先に走るという意味も
    無い（**解析は全部同時に走る**）
  - ⚠️ **「解析に使う」を外した登録も含めた一覧の中で動かす。** 走るものだけを
    詰めて数えると、**チェックを外した瞬間に見えている順番と食い違う**
  - ⚠️ **端で回り込ませない**（一番上を上げたら一番下へ飛ぶ、では驚く）。
    端の行はボタンを**押せなくする** —— 押しても何も起きないと、壊れているのか
    端なのかが区別できない
  - ⚠️ **押したあとフォーカスをそのボタンに戻すこと**（行ごと描き直すため）。
    戻さないと**1 つ動かすたびに押しにいくことになる**
- **`name` は表示名。空なら既定を解決する**（`EngineEntry.DisplayName`）:
  **`name`（人が付けた）→ `engineName`（エンジンが名乗った）→ パスのファイル名 →
  「同梱エンジン」。**
  ⚠️ **エンジンが `id name` で名乗る名前とは別物** —— あちらは繋いで初めて分かるので、
  繋ぐ前の見出しと、同じ exe を 2 つ登録したときの区別にこちらが要る。
  UI は既定の名前を **placeholder に出し、value には入れない**（入れるとパスを
  変えても名前が追従しなくなる。Go 側が `custom` を返しているのはこのため）。
  ⚠️ **そのぶん「値ではない」と見えること**（2026-09-08。**実際に「編集できない」と
  誤解された**）—— ここの placeholder は案内文ではなく**そのまま値になりうる名前**
  なので、色を落とすだけでは足りず**斜体**にしてある（`.engine-name::placeholder` /
  `.font-row-name-input::placeholder`）。⚠️ **他の欄まで斜体にしないこと**
- ⚠️ **名乗り（`engineName`）を既定の表示名にしてある**（2026-09-08）。
  `YaneuraOu_NNUE-tournament-clang++-avx2.exe` より、エンジン自身の名乗りのほうが
  読める。**繋いだ時点で控える**（`AnalyzeService` の「接続を確認」と解析の完了 →
  `SettingsService.rememberEngineName`）。
  - ⚠️ **人が付けた名前より前に出さないこと。** 同じ exe を option 違いで 2 つ
    登録すると**名乗りは同じ**になるので、**見分けが付くのは人が付けた名前だけ**
  - ⚠️ **設定ファイルに控えること**（メモリだけで持たない）。名乗りは繋がないと
    分からないので、**閉じた時点で消えると次の起動では二度と出てこない**
    （exe のファイル名に戻る）
  - ⚠️ **変わっていなければ書かないこと。** 解析が終わるたびに呼ばれるので、
    素通しにすると**1 手ごとに設定ファイルを書く**（連続解析では手数ぶん）
  - ⚠️ **実行ファイルを差し替えたら捨てること**（`OptionSpecs` と同じ扱い。
    別のエンジンの名乗りなので、残すと**違うエンジンの名前を出す**）。
    **人が付けた `name` のほうは捨てない**
  - ⚠️ **解析タブの見出しで名乗りを括弧で足すのは、`label` と違うときだけ**
    —— 一度繋いだあとは `label` 自体が名乗りなので、**同じ名前が 2 回並ぶ**
- **パスは手で打たせない**（`SettingsService.BrowseEngine` が追加、`BrowseEngineFor` が
  行の差し替え。⚠️ **この 2 つを混ぜないこと** —— 差し替えのつもりで登録が増える）。
  将棋エンジンは深いディレクトリに置かれるので、打ち間違いが一番起きやすい入口。
  テキスト欄も残してあるのは、貼り付けと確認のため
- **保存と接続の確認は別の操作。** まだ置いていないパスを先に書く順序が普通にあるので、
  保存時に起動はしない（**存在の確認だけ**する。打ち間違いは「解析を押したら繋がらない」
  より早く分かるほうがよい）。実際に起こすのは「接続を確認」（`AnalyzeService.CheckEngine(id)`）
- ⚠️ **「接続を確認」は 1 行ずつ。** まとめて起こすと、どれが遅くてどれが落ちたのかが
  分からない（複数を同時に起こすのは解析のときだけ）。結果も**その行に出す**
- **確認で繋いだ接続はそのまま解析に使う。** 確かめるためだけに起こして捨てると、
  直後の解析でまた起動を待つことになる
- **`options` は画面から設定できる**（2026-08-15。設定タブの行の折りたたみ
  「エンジンの設定」）。詳しくは下記「エンジンの option を画面から設定する」。
  ⚠️ **設定ファイルを手で編集する経路も残す** —— 宣言していない option を
  受け付けるエンジンがあるので、**画面から選べる範囲と、受け付ける範囲は別物**
  （折れ線の色と同じ扱い）
- ⚠️ **`options` は `isready` の前に送る**（`core/usi/client.Open`）。置換表の確保も
  評価関数の読み込みも `isready` で走るので、**後から送っても間に合わない**。
  しかもエンジンは黙って既定値で動くので、間違えても画面では気づけない
- **エンジンが `usi` で宣言した option には、`options` に書いていなくても既定値を送る**
  （将棋 UI の一般的な作法。`core/usi/client.plannedOptions`）。`options` に書いた値は
  その位置で差し替わる。**button と、既定値が空のものは送らない**
- **「接続を確認」は宣言と送信の件数を出す**（`option 42 件を宣言、38 件を送信`）。
  ⚠️ **`setoption` には応答が返らない**ので、効いているかを確かめる手掛かりがこれしかない
- **設定は解析を始めるたびに読む。** プロセスが 1 回の解析で終わるので、
  変えた結果が次の解析にそのまま効く（**繋ぎ直しの判断が要らない**）
- **終了時に走っている解析を打ち切り、エンジンが終わるまで待つ**（`main.go` の `quit`）。
  ⚠️ **待たないとプロセスが残る**（Windows では親が消えても子は道連れにならない）

### エンジンの option を画面から設定する（**2026-08-15**）

**「接続を確認」でエンジンの宣言を読み、その型どおりの入力欄を出す**
（設定タブの行の折りたたみ「エンジンの設定」）。

```
接続を確認 ──> client.Open ──> Session.Options ──> EngineEntry.OptionSpecs（宣言の控え）
   （繋ぐ）                       （宣言）              │
                                                       ├──> 設定タブの入力欄
解析 ──> engines[].options（値）──> setoption ─────────┘
```

⚠️ **宣言（`OptionSpecs`）と値（`Options`）は別物。混同しないこと。**
宣言は「このエンジンは何を受け付けるか」、値は「そのうち何をどう変えたか」。

| 型 | 入力欄 |
|---|---|
| `check` | チェックボックス |
| `spin` | 数値（`min`/`max` つき） |
| `combo` | 選択（`var` の並び） |
| `string` / `filename` | テキスト |
| `button` | ⚠️ **設定できない**（下記） |

- ⚠️ **宣言を控えるのが要点**（`EngineEntry.OptionSpecs`）。宣言はエンジンに繋がないと
  分からないので、控えないと**設定タブを開くたびにエンジンを起こす**ことになる
  （NNUE の読み込みで数秒かかるものがある）。**控える入口は `CheckEngine` の 1 か所**
- ⚠️ **保存の操作では繋がない**（元の線引きを変えていない）。だから
  **繋いだことのない登録には入力欄が出ない** —— そのとき出すのは
  「まだ読んでいない」であって「宣言が無い」ではない（`EngineSettings.OptionsKnown`。
  **同梱エンジンは本当に 1 つも宣言しない**ので、この 2 つは区別が要る）
- ⚠️ **既定と同じ値は書き残さない**（空にしたときと同じ扱いで消す）。エンジンが
  宣言した option には**書いていなくても既定値が送られる**ので、書き残すと
  「エンジンの既定に従う」という指定ができなくなり、**バージョンが上がって既定が
  変わっても古い値で固まる**（しかも画面では気づけない）
- ⚠️ **button は値を持たない**（送ること自体が「押した」という動作）。押せる相手は
  **繋がっているエンジン**だけで、設定タブには居ない（接続は解析タブに居るあいだしか
  生きていない）。**設定として保存しないこと**——画面には出すが押せなくしてある
- ⚠️ **値を検分するのは宣言があるときだけ**（範囲外の spin・選択肢に無い combo・
  true/false でない check）。**`setoption` には応答が返らない**ので、間違った値を
  送っても**画面では気づけない**。入れた瞬間に断るほうが早い
- ⚠️ **宣言に無い名前も受ける。** 宣言していない option を受け付けるエンジンがあり、
  設定ファイルを手で編集する経路も残してある。画面では「宣言に無い項目」として
  出し、**消す口だけ用意する**（黙って捨てない）
- ⚠️ **実行ファイルを差し替えたら宣言を捨てる**（別のエンジンの宣言なので、
  残すと**違うエンジンの入力欄**を出す）。**値のほうは捨てない** —— 置き場所を
  移しただけのことがあるうえ、人が書いた値を黙って消さない
- ⚠️ **変えた値は繋ぎ直さないと効かない**（`setoption` は `isready` の前にしか
  効かない）。判断は `AnalyzeService.engineKey`（パス + options の指紋）が持っている
  ので、**`SettingsService` から接続を触らないこと**
- ⚠️ **入力欄の形も既定値も範囲も選択肢も Go 側が渡したものを使う。**
  フロントに型ごとの表を書かないこと（`DisplayName` / 折れ線の色と同じ）
- **折りたたみは既定で閉じる。** やねうら王級だと option が 40 件を超えるので、
  開きっぱなしだと一覧そのものが読めない。⚠️ **見出しに件数を出すこと**
  （畳んだままでも既定のままかどうかが分かる必要がある）。**中は高さを頭打ちにして
  スクロールさせる** —— 素直に並べると設定タブが縦に伸びきって、下の設定へ辿り着けない
- ⚠️ **開いている状態はフロントだけが持つ**（`openOptions`）。一覧は保存のたびに
  描き直されるので、**覚えておかないと値を 1 つ変えるたびに閉じる**

## `AnalyzeService`（`analyzeservice.go`）

- **局面を持たない。** 解析するのは常に「今 `StudyService` が持っている**確定局面**」で、
  **フロントから SFEN を受け取らない**。渡してもらう形にすると、採り直した直後に
  古い局面を解析する経路ができる（フロントに局面の写しを持たせない方針と同じ）
- ⚠️ **`PositionService`（訂正タブ）を直に見ないこと**（2026-08-10）。駒を自由に
  動かせる状態の盤は「まだ決めていない局面」で、その評価値には意味が無い。以前は
  訂正モードかどうかをフロントが見てボタンを止めていたが、**タブを分けたことで
  構造上そこに手が届かなくなった**
- **解析する局面は 1 つ、エンジンは複数**（2026-08-11）。設定で「解析に使う」を
  付けたエンジンぶんの goroutine を起こし、**同時に走らせる**。
  ⚠️ **1 エンジン 1 プロセス・1 接続**（USI は 1 接続で 1 探索なので、束ねようがない）。
  ⚠️ **エンジンをまたいで結果を合成しないこと**（平均も多数決も取らない。並べて人が読む）
- ⚠️ **1 つのエンジンが落ちても他は続く**（設計原則3）。`analyze:failed` は
  **そのエンジンの**失敗で、解析全体の失敗ではない。**他の結果を消さないこと**
- **新しく始めると前の解析は全部打ち切る。** 打ち切った解析の途中経過は
  **後から届く**ので、`Seq`（解析の世代）でフロントが捨てる。
  **この仕組みを外さないこと**（古い局面の評価値が新しい盤の上に出る）
- ⚠️ **打ち切った世代が畳まれるまで待ってから始めること**（2026-09-09。
  `Start` の `cancelGrace`）。待たないと**前の世代の探索が `runMu` を掴んだまま**
  次が積み上がり、**1 つの接続に局面の違う探索が何本も並ぶ** ——
  連続解析では「他の手も同時に解析している」「そのうち止まる」という形で出た。
  ⚠️ **待ちは有界にすること**（`bestmove` を返さないエンジンで固まる）。
  見切ったら重なったまま始める（始められないよりまし。設計原則3）
- ⚠️ **done には「考える時間を使い切ったか」を載せる**（`Interrupted`）。
  **`Stopped` では区別できない** —— 時間切れもこちらから `stop` を送って
  終わるので、あれは普通に考え切ったときも立つ。**頼んだ秒数に届いたか**で見る
  （`interruptSlack` は往復ぶんの遊び）。⚠️ **連続解析がこれで止まる** ——
  打ち切られた解析も done を出す（設計原則3）ので、**無いと「1 手ぶん終わった」と
  読んで次の手へ進み、手数ぶんが数秒で流れる**
- ⚠️ **止めるときは全部止める**（同じ局面を比べるために走らせているので、
  片方だけ生かす意味が無い）。「全部終わった」ときだけ解析中の表示を解く
- 途中経過はイベント。`analyze:info` / `analyze:done` / `analyze:failed`。
  ⚠️ **どれにも `engineId` が載る。** 複数のエンジンが同時に喋るので、
  **`seq` だけでは行き先を決められない**（落とすと結果が 1 か所で上書きし合う）。
  ⚠️ **ペイロードの型は bindings に出ない**（メソッドの戻り値ではないため）。
  `CaptureResult` と同じで `mainscreen.ts` が手で書いているので、**Go 側を変えたら
  そちらも直す**
- ⚠️ **「解析に使う」が 1 つも無ければ `Start` はエラー。** 何も起きないより、
  設定を直す先が分かるほうがよい

## テスト

  ⚠️ **並べ替えても色が付いてくること**を見ている（動くと、前に見ていた線と
  同じ色が別のエンジンを指す）。ほかは保存されること・空で既定に戻ること・
  **壊れた値を断ったときに今の色を変えないこと**。並べ替えのほうは、並び順が
  表示の順序そのものなので、動かした結果が**保存されること**と、⚠️ **端で回り込まないこと**、
  ⚠️ **「解析に使う」を外した登録も数に入れること**（走るものだけを詰めて数えると、
  チェックを外した瞬間に見えている順番と食い違う）を見ている。
  ⚠️ **`SettingsService` は `path` を一時ディレクトリに向けて手で組むこと** ——

  その場で効くこと**（フックが呼ばれること）—— 中継を触りたくなったその瞬間に
  切り替える設定なので、次の起動まで待たせない。**切ったことも設定ファイルに残ること**
  （キーが消えると手で編集する側から存在に気づけない）。

  ⚠️ **一番の要点は「既定が表示であること」** —— `Show...` で持つと bool の

  もう片方を巻き添えにしない**）。
