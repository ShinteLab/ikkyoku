# app: 棋譜データベース（棚）と中継のカード

**`KifuService`（`kifuservice.go`）・仮の一覧（`watches`） を触るときに読む。** `app/AGENTS.md` から分けた**制約**（「⚠️ …しないこと」）で、
⚠️ **自動では読まれないので、触る前に必ずここを開くこと**（索引は `app/AGENTS.md`）。

## 棋譜データベース（棚）— **kicho をライブラリとして使う**（2026-09-04）

**`ikkyoku` は「ユーザ環境で動く将棋ソフト」**なので、棋譜のデータベース化も
ikkyoku から使えないと**ユーザが ikkyoku と kicho の 2 つを立ち上げる**ことになる。
そこで kicho の UI が持っていた機能（取得 / 登録 / 蔵書）を ikkyoku へ移した。

kicho の UI は将来「テスト用のモック」または
「ikkyoku 以外の将棋ソフトからの読み込み口」になる。

```
入力タブ ─ 貼り付け/URL ─┬─ 読み込む ────────────────→ 解析タブ（棚に入らない）
                        └─ 棚に登録する ─┐
入力タブ ─ 中継から取得 ─ カード ─ 保存 ──┤
                                        ↓
                                 kicho.Library ─→ store(SQLite)
                                        ↑
                        棋譜タブ（棚）─ 検索 ─「解析する」──→ 解析タブ
```

`kicho.Open(dbPath, logger)` は**dbPath が空でなければ kicho 側の `settings` を
見ない**し、HTTP サーバも作るだけで起動しない（`httpapi.Server.Stop` は未起動でも安全）。

⚠️ **移行の直後は kicho を 1 行も変えずに済ませたが、その形は維持できなかった**
（2026-09-07 に整理）。当時は `kicho.Library.Store()` で `*store.Store` を直接触っており、

- 実質の公開 API が `store` パッケージ全体になっていた
- **保存の組み立てが 2 か所に分かれていた** —— 取得元ごとの `source_url` の決め方、
  文字コードの既定、手数の数え方を ikkyoku と `kicho/_cmd/kicho` がそれぞれ持ち、
  片方だけ直せば黙って割れる状態だった（実際 kicho 側は読売の `source_url` を
  入れ忘れていた）

いまは **`Store()` は無く、蔵書の操作も取得元の知識も `kicho.Library` にある**。
ここに書くのは DTO の変換と入力チェックだけ。

### 崩してはいけない線引き

1. ⚠️ **棚は解析の前提条件にしない。** `kicho.Open` が失敗してもアプリは起動し、
   撮った 1 局面と貼った棋譜は解析できる（設計原則3）。**棋譜タブだけ**が理由を
   出して機能しない。判断は `KifuService.library()` の 1 か所で、
   **どのメソッドも同じ文言を返す**（読めないと設定タブへ辿り着けない）
2. ⚠️ **棚に入るのは KIF の原本だけ。** 検討ツリー（`position.Study`）も評価値も
   入れない（kicho の「原本を保持する。整形し直さない」原則そのもの）。
   Phase 5 の決定「検討ツリーは永続化を前提にしない」も生きている。
   ⚠️ **仮の一覧（`watches`）はこの例外ではない** —— あちらが残すのは
   「どのサイトのどの棋譜か」だけで、**KIF 本文を持たない**（後述）
3. ⚠️ **ikkyoku で伸ばした枝を KIF に書き戻さない。** 棚の KIF は
   **実際に現れた指し手**で、エンジンの読み筋や自分で指した手ではない
   （`TODO.md` の「本譜のロック」と同根）
4. ⚠️ **取得元の知識をこちらに書かない。** 取得元ごとの `source_url` の決め方、
   文字コードの既定、手数の数え方、「再読み込みで取り直せる URL か」の判断、
   **「仮の一覧に載せられる取得元か」**は
   **kicho 側**（`kicho.Fetched` / `Library.Save` / `Library.Watch` / `RefetchableURL`）。
   同じ変換を `kicho/_cmd/kicho/kifuservice.go` も持つので、こちらに書くと必ず割れる。
   足りないものが出たら **kicho の `Library` に足す**（`Store()` は無い）。
   直したら kicho 側で `.\check-consumers.ps1` を流し、タグを打ってこちらの go.mod を上げること
5. ⚠️ **DTO は `app` にローカルに持つ**（`GameSummary` / `GameDetail` /
   `SearchQuery` / `SearchResult` / `WatchEntry`）。
   `store.Record` / `store.Watch` をそのままフロントへ出さないこと ——
   bindings に kicho の型が漏れると、向こうのスキーマ変更がフロントに直撃する
6. ⚠️ **ikkyoku は HTTP サーバを持たない**（`ServerService` は移していない）。
   kicho の UI の「棋譜 URL をコピー」「取得 URL をコピー」は**外部ツール
   （ShogiHome 等）へ渡すため**のもので、ikkyoku では渡す先が自分自身。
   **代わりに置いたのが「解析する」**。⚠️ **URL コピーを戻すなら、先に
   「ikkyoku がサーバを持つか」を決めること**
7. ⚠️ **エラーは文言比較で分岐しない。** kicho は**「画面と文言は使う側にある」
   という前提で sentinel を公開している**（`ErrNoInput` / `ErrEmptyKifu` /
   `ErrNotKifu` / `ErrUnsupportedSource` と `store.ErrNotFound` /
   `ErrSchemaTooNew`）。**種類だけ向こうから貰い、何をすればよいかはこちらが書く**
   （`describeKifuError` / `describeOpenError` の 2 か所）。
   ⚠️ **kicho の文言を書き写さないこと** —— `%w` で包んで足すだけにする。
   写すと向こうを直してもこちらだけ古い言い方で残る
   （実際 `SendToStudyGame` が「棋譜が空です」を手書きで持っていた）
8. ⚠️ **一覧の上限を「並んだ件数」として画面へ渡さないこと。**
   `Library.Search` が丸めるのは **Limit が 0 か上限超えのときだけ**で、
   呼び出し側が指定した `Limit` はそのまま効く。`MaxSearchRows`（500）を
   決め打ちで返すと、**1 件しか並べていないのに「500 件だけを表示しています」**と
   出る。返すのは `SearchResult.Shown`（＝実際に並んだ行数）で、
   **切ったときはそれが適用された上限そのもの**なので丸め方を写さずに済む

### kicho を抱えると付いてくるもの

`kicho.Library` を import した時点で、ikkyoku のバイナリには次が入る。

| 依存 | 何のため |
|---|---|
| `modernc.org/sqlite` | 棚（PureGo。cgo 不要） |
| `github.com/dop251/goja` | **読売のペイロード評価** |
| `golang.org/x/net/html` | 読売の対局ページから iframe を辿る |
| `golang.org/x/text` | Shift_JIS の判別 |

⚠️ **goja は第三者サイトの JavaScript を ikkyoku のプロセス内で実行する。**
読売の `_payload.js` は Nuxt の IIFE で、値が引数リストの変数として共有されているため
文字列パースでは解けず、JS として評価するしかない（理由は kicho の CLAUDE.md）。

- 盤面キャプチャ・エンジン・解析と**同じプロセス**で動くことは認識しておく
- kicho 側に `vm.Interrupt` による 10 秒のタイムアウトがある。**外さないこと**
- ikkyoku から呼ぶ経路は「中継から取得」（`KifuService.Fetch` / `Refresh`）だけ。
  貼り付け・URL 取り込みは goja を通らない

### 棚の呼び出しには必ず制限時間を付ける

⚠️ **`context.Background()` をそのまま `kicho.Library` へ渡さないこと。**
kicho の `store` は接続を 1 本に絞っているので、止まらないクエリが 1 つあると
**以後の棚の操作が全部待たされる**（画面からは「棚が反応しない」に見える）。

`KifuService` の `kifuDBContext()` / `kifuNetContext()` を通す
（DB は 10 秒、サイトへの取得は 60 秒）。

### DB の場所

**既定は `os.UserConfigDir()/ikkyoku/kicho.db`**（`Config.KifuDB` の 1 か所で解決）。
設定タブ「棋譜データベース」で任意のパスを指せるので、**kicho アプリの DB
（`%APPDATA%\kicho\kicho.db`）を共用**できる（開発時に確かめやすい）。

- ⚠️ **既定を kicho と同じにしないこと。** `store` の `SetMaxOpenConns(1)` は
  **プロセス内**の直列化でしかない。プロセスをまたぐ競合には kicho 側で
  WAL と `busy_timeout` を入れてある（2026-09-07）ので即 `database is locked` には
  ならないが、**共用を勧める状態ではない**。ユーザーが設定で指定したときだけにする
- ⚠️ **kicho と ikkyoku は別バイナリなので DB のスキーマ版が食い違いうる。**
  片方だけ更新した状態で同じ DB を指すと `store.ErrSchemaTooNew` で開けない
  （黙って開いて後段が `no such column` で落ちるより良い、という判断）。
  **実際に 2026-09-08 に v4 へ上がった**（仮の一覧 / `watches`）——
  **kicho のタグを上げてビルドし直せば揃う**（2026-10-05 からタグで引いている。手元の kicho を直しただけでは入らない）
- ⚠️ **存在チェックをしない**（SQLite は無ければ作る）。まだ無い場所を先に書く
  順序が普通にある（エンジンのパスとはそこが違う）
- ⚠️ **変えたその場で開き直す**（`SettingsService.onKifuDBPath` → `KifuService.open`）。
  **`SettingsService` から DB を直に触らないこと**（棚を持っているのは `KifuService`）
- **開けているかは設定ではなく状態**なので `KifuService.Status` から取る
  （設定は「どこを開こうとしているか」、状態は「開けたか」）

### 二系統を残す（**貼り付け／URL の行き先**）

⚠️ **「棚に入れる」と「保存せず解析する」は別操作。** 入力タブの
「棋譜を貼り付ける」には**同じ入力欄に対して 2 つのボタン**がある。

| ボタン | 行き先 | 棚 |
|---|---|---|
| 読み込む / URL から読み込む | **解析タブ**（`StudyService.LoadKifu` / `LoadKifuURL`） | 入らない |
| 棚に登録する | **棚**（`KifuService.ImportKIF` / `ImportURL`） | 入る。**解析タブは触らない**。⚠️ **`ImportURL` は `Fetch` + `Save`**（2026-09-12）—— `kicho.Library.ImportURL` は何を渡しても `source` が `url` になるので、**連盟・読売の URL で中継としての ID を捨てる** |

- ⚠️ **入力欄を 2 つに増やさないこと。** 同じ入力の**行き先が 2 つある**だけで、
  欄を分けると「どちらに貼ったか」で挙動が変わる面になる
- ⚠️ **登録してもタブは移らない。** 登録は「あとで探せるようにする」操作で、
  今すぐ見るなら「解析する」。**代わりに棋譜タブの一覧は取り直す**
  （反映されていないと、登録できたのか分からない）

### 棋譜タブ（棚）

移植元は kicho の「棋譜一覧」タブ（`_cmd/kicho/frontend/src/App.tsx` の `LibraryTab`）。

- 行の操作は **「解析」＝棋戦名のリンク** /「表示」（棋戦名と先手のあいだ）/
  「削除」（右端）（2026-09-14 に「解析」と「表示」を入れ替えた）。
  ⚠️ **一覧の主目的は解析へ送ること**なので、**その棋譜そのものである棋戦名**を
  押すのが解析に当たる。詳細は補助なので、**押し間違えても何も起きないボタン**の側。
  ⚠️ **行の左端に押すものを戻さないこと** —— 左端は一覧を目で追う起点（開始日）で、
  そこにボタンがあると**拾い読みのたびに避けることになる**。
  ⚠️ **行そのものを押して解析する作りにしないこと**（選ぶつもりの操作で毎回飛ぶ）
- ⚠️ **タブを開くたびに棚を読み直すこと**（`selectTab` → `libraryUI.reveal()`）。
  同じ DB を kicho アプリからも触れるので、**初回だけ読む作りにすると
  向こうで足した棋譜が見えない**（共用にした意味が消える）
- ⚠️ **検索は打つたびに走らせない**（Enter か「検索」）。**3 文字未満は索引
  （FTS5 trigram）が効かず全件走査になる**ので、そのことを案内する。
  ⚠️ **案内は打っている途中に出さない**（2026-09-12）——
  **検索を走らせたときだけ、見出し（棋譜一覧の横）に出す。**
  検索欄の下に置いて 1 文字ごとに出し入れしていた頃は、**下の表が動いていた。**
  ⚠️ **文字数は `MinSearchLength`（＝ `store.MinTrigramLen`）を写すだけ** ——
  **判定そのものは Go 側**で、フロントを検索の条件に使わないこと
- ⚠️ **削除の確認は `window.confirm` ではなく `popup.ts`**（初期フォーカスは
  「やめる」。手順を消すときと同じ）
- **詳細はモーダル**（2026-09-12。それまでは一覧の下に開いていた）。
  ⚠️ **KIF の本文は画面に出さない** —— 150 手を流すと詳細だけで画面が埋まる。
  持ち出す口は**「KIF をコピー」だけ**で、渡すのは**原本のまま**（整形し直さない。
  棚の中身と食い違わせない）。⚠️ **クリップボードは Wails ランタイム**
  （`navigator.clipboard` はカスタムスキーム配信の webview では当てにできない）

### 棋戦名を直す・備考を残す（人が書く欄）— **2026-10-02**

**中継などの外部サービス由来の棋譜は棋戦名が欠けていることがあり、一覧で
見分けられるよう人が埋める。** 口は `KifuService.Annotate`（詳細モーダルの「保存」
「元に戻す」）で、中身は `kicho.Library.Annotate` を呼ぶだけ。
整え方（前後の空白を落とす・取得した値と同じ名前は「直していない」として持つ・
空で取り消す）は**kicho が決める** —— ⚠️ **こちらにもフロントにも同じ規則を書かないこと。**

- ⚠️ **取得した値の列（`Event`）を書き換えないこと。** 直した名前は別の列
  （`EventEdited`）にあるので、**取り直して保存しても消えない**（`Library.Save` は
  人が書く欄に触らない）。⚠️ **`GameSummary.Event` も取得した値のまま運ぶ** ——
  画面は `eventEdited` と `event` の両方を見て「直してある」印と取得元の棋戦名を出す。
  1 つにまとめて渡すと、どちらも画面から消える
- ⚠️ **`detailToFetched` で `EventEdited` / `Note` を運ばないこと。** `kicho.Fetched` は
  **取得した値**の入れ物で、運ぶ道を作ると**取得した値の列に人の値が入る経路**ができる。
  人が書く欄を書く口は `Annotate` の 1 か所だけ
- ⚠️ **外部ツールへの配信（kicho の httpapi）は取得した値のまま**（ユーザーが決めた）。
  直した名前が効くのは棋譜タブの一覧・検索（kicho の検索は直した名前と備考にも当たる）だけ
- ⚠️ **KIF 本文は編集しない**（上の「棚に入るのは KIF の原本だけ」）
- ⚠️ **対象は棚に入っている棋譜だけ。** 仮の一覧（`watches`）・中継のカードには書けない
  （あちらは「どのサイトのどの棋譜か」の写しで、人が書く欄を持たない）
- 画面: 一覧の棋戦名は**直した名前 → 取得した名前**。直してあれば名前の後ろに小さな印、
  備考は名前の下に薄く 1 行。⚠️ **押せる場所は増やさない**（棋戦名のリンクが解析の口で、
  印も備考も押せない。直すのは「表示」のモーダルから）

### 中継から取得（入力タブのカード）

移植元は kicho の「取得」タブ。読売（竜王戦）のスクレイピングと
日本将棋連盟の棋譜中継（.kif の直取得）の 2 つで、**取り方は違うが
カードに積む・更新する・保存する、の扱いは同じ**（判別も取得も Go 側）。

- ⚠️ **取得は 1 件だけ持つ設計にしない。** 同じ日に 2 局以上進むこと（並行対局、
  複数局を交互に追う）があるので、取得のたびにカードを 1 枚積む（新しいものが先頭）
- ⚠️ **同じ棋譜を取り直したらカードを増やさない。** key（`{取得元}:{棋譜 ID}`）が
  一致するカードは**位置と「保存済み」を保って中身だけ差し替える**
  （`mergeCard`）。⚠️ **取得元も key に含めること** —— 棋譜 ID の形が取得元ごとに
  違う（読売は 24 桁の ID、連盟は中継のパス）
- ⚠️ **保存は画面の内容をそのまま書き込む**（サイトへ取り直しには行かない）。
  そのため**保存済みで手数が変わったら「保存し直す」よう促すこと** ——
  黙っていると「更新＝保存」だと誤解される
- ⚠️ **「閉じる」で消えるのは画面のカードと仮の一覧だけ。棚の棋譜は消えない。**
  棋譜タブの「削除」と見た目が同じ赤いボタンなので、**文言で分ける**
- ⚠️ **日本将棋連盟の中継はここで扱うこと。** 上の「棋譜を貼り付ける」の URL 欄から
  入れると `source_id` が毎回 UUID になり、取り込むたびに別の棋譜として増える
- ⚠️ **取得は棚（DB）を通らない**（`kicho.NewFetcher()`。`kifufetch.go`）。
  **棚が開けないことと取得できないことを繋げない**（設計原則3）
- ⚠️ **`kicho.RefetchableURL` が取り直せる URL を返すことが前提** —— カードの
  「解析する」が解析タブへ渡す唯一の道なので、そこで落とすと**解析タブの
  「再読み込み」が出ない**（検討の枝と評価値を保って中継を追う流れが成立しない）
- ⚠️ **URL の欄を取得元ごと・行き先ごとに分けないこと**（画面は `_docs/ui/screens.md`）。
  判別は `kicho.Fetcher.Fetch` で、**ikkyoku に「このサイトならこちら」を書かない**

### 中継そのものを覚えておく（仮の一覧 / `watches`）— **2026-09-08**

**2 日制の対局では翌日また中継の URL を貼り直すことになる。** それを避けるため、
取得カードを棚の DB（`watches`）に残して**再起動後に並べ直す**。
kicho 側の実装で、ikkyoku は `Library.Watches / Watch / Unwatch / UnwatchAll` を呼ぶだけ。

⚠️ **残すのは「サイト」であって棋譜ではない。**

| 持つもの | 持たないもの |
|---|---|
| `source` / `source_id` / `source_url` | **KIF 本文** |
| 一覧で見分けるためのメタ（棋戦名・対局者・開始日時・手数・終局種別） | 手合割・場所・文字コード |

メタは**表示用の写しであって原本ではない**（原本は取り直せば取れる）。
⚠️ **棋譜そのものを残すのは「この内容を保存」（棚）の役目で、役割を混ぜないこと。**

```
取得 / 更新 ──> mergeCard（画面）──remember──> KifuService.Watch ──> 棚の watches
起動 ────────> KifuService.Watches ──> cardFromWatch（本文は空）
```

- ⚠️ **復元ではサイトへ取りに行かない。** 起動のたびに追跡ぶんの通信が走ると
  待たされるうえ、**中継を追っていない日でも毎回外へ出ることになる。**
  中身はカードの「**更新**」で取り直す（復元直後なら「**取り直して解析**」が
  1 回で済ませる）。⚠️ **まとめて回す口は置かない**（2026-09-12 に「すべて更新」を
  外した）—— **カードは 2〜3 枚が普通**なので 1 枚ずつでよく、**サイトへ順に
  投げる制御を抱える理由が無い**
- ⚠️ **復元しただけのカードでも「解析する」は押せる**（2026-09-09。
  ラベルは**「取り直して解析」**に変わり、押すと
  **先に `Refresh` してから送る**）。⚠️ **以前は押せなくしていたが、
  その理由は「送っても必ず失敗する」（`SendToStudyGame` の `ErrEmptyKifu`）
  だけだった** —— 取り直してから送れば消える理由なので、
  人に「更新 → 解析」と 2 回押させない
  - ⚠️ **「この内容を保存」は今までどおり押せないまま**（`isRestored` ＝ 本文が空）。
    **保存は画面の内容をそのまま書き込む操作**なので（上の「保存は画面の
    内容をそのまま書き込む」）、**ここで取り直しに行くとその約束が崩れる**
  - ⚠️ **本文があるカードでは取り直しに行かないこと。** 送るのは
    「いま画面に出ているこの内容」で、最新手を追うのは「更新」か
    解析タブの「再読み込み」の役目
  - ⚠️ **取り直しているあいだはボタンにそう出す**（「取り直しています…」）。
    外へ取りに行くので数秒かかる —— **「解析する」と同じラベルにしないこと**
    （押したところで通信が始まるとは読めない）
  - ⚠️ **取れなかったときは解析へ進まないし、理由を書き直さないこと**。
    取得の失敗を「送れなかった」で上書きすると、
    **取得と送りのどちらで失敗したのかが分からなくなる**
  - ⚠️ **これは kicho に無い分岐**（あちらに「解析する」は無い）
  - ⚠️ **取り直しの本体は `fetchInto` の 1 か所**（「更新」も「取り直して解析」も
    ここを通る）。**busy の出し入れは押した側が持つ** ——
    `fetchInto` が自分で解くと、**取り直しを終えた瞬間に
    解析を待たずボタンが押せるようになる**
- ⚠️ **判定に別のフラグを持たせないこと。** 本文の有無で見れば、更新して中身が
  入った瞬間に自動で外れる（フラグだと復元扱いのまま残る道ができる）
- ⚠️ **載せられるのはライブ中継（読売・連盟）だけ。** 貼り付け・URL 取り込みは
  取得元での一意な ID を持たず `source_id` が毎回 UUID なので、復元しても
  「更新」が必ず失敗するカードになる。**判断は kicho**（`ErrUnsupportedSource`）で、
  **ここに取得元ごとの分岐を書かないこと**
- ⚠️ **載せ損ねても取得結果は画面に残すこと。** 今日の作業は続けられるので
  失敗にはせず、**「仮の一覧に無し」の札**を出して「再起動すると消える」ことだけ伝える
  （黙っていると「昨日のカードが無い」の理由が分からない）
- 一覧から外れるのは次の 2 つ。**どちらも棚の棋譜（`games`）には触らない。**

  | 操作 | 動き |
  |---|---|
  | カードの「閉じる」 | `Unwatch`。⚠️ **外さずに閉じると再起動で戻ってくる** |
  | 終局済みの棋譜を「保存」 | `Library.Save` が自動で `Unwatch` |

  ⚠️ **「クリア」（`UnwatchAll`）は画面から外した**（2026-09-12）。
  **1 枚ずつ「閉じる」で足りる**（カードは 2〜3 枚）うえ、
  **「閉じる」は赤くて問い合わせがあるのに、全部消すクリアは問い合わせ無し**
  という不揃いな操作だった。⚠️ **`KifuService.UnwatchAll` は残してある**ので、
  戻すなら**「閉じる」と同じ作法（問い合わせ）にすること。**

- ⚠️ **終局していないときは保存しても外さない**（2 日制なら 1 日目の封じ手時点で
  保存しても翌日また同じカードで追う）。**分岐を持っているのは kicho の `Save`** で、
  フロントは `rec.finished` を見て札を落とすだけ。**こちらで判断し直さないこと**
- ⚠️ **既に無いものを外すのは失敗にしない**（`KifuService.Unwatch` が
  `store.ErrNotFound` を飲む）。終局後の保存では kicho が先に外しているので、
  エラーにすると**カードが閉じられなくなる**
- ⚠️ **棚を開き直したとき（設定タブ）に復元し直していない。** 復元はメタだけで
  カードを作り直すので、**今日取ったカードの本文（KIF）を捨てることになる。**
  閉じれば新しい棚からも外れる（無ければ何も起きない）ので実害は無い
- ⚠️ **`GameDetail` を返す形にしないこと**（`WatchEntry` を別に持っている）。
  本文の欄に空文字を詰めて返すと、**「棋譜が取れている」ように見える**

### ⚠️ 解析タブの「再読み込み」に渡せる URL は取得元による

棚（または取得カード）から解析タブへ送るとき、**取得元の URL も一緒に渡す**と
解析タブの「再読み込み」で中継の最新手を追える。**が、全部の取得元では渡せない。**

| 取得元 | `source_url` | 取り直せるか |
|---|---|---|
| `shogilive` | 中継ページ（HTML） | **○**（`KifURLFromHTML` で .kif を辿る） |
| `url` | 指定された .kif | **○** |
| `yomiuri` | 棋譜ビューアのページ | ⚠️ **×**。Nuxt のページで .kif が無い（KIF は `_payload.js` から組み立てている）。**取り直す口は取得カードの「更新」** |
| `paste` | 空 | —（取り直す先が無い） |

⚠️ **判断は kicho の `RefetchableURL` の 1 か所。フロントにも ikkyoku にも
書かないこと**（取得元ごとの知識は向こうが持つ。上の「取得元の知識をこちらに
書かない」）。
取り直せない URL を渡すと**再読み込みのアイコンが出るのに押すと必ず失敗する**、
という画面からは理由の分からない壊れ方になる。
