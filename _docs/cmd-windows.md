# _cmd/ikkyoku: ウィンドウ（5 枚・起動・真っ黒・状態の永続化）

**`main.go`（ウィンドウの生成）・`window.go`・`frontend/src` のウィンドウまわり を触るときに読む。** `_cmd/ikkyoku/AGENTS.md` から分けた**制約**（「⚠️ …しないこと」）で、
⚠️ **自動では読まれないので、触る前に必ずここを開くこと**（索引は `_cmd/ikkyoku/AGENTS.md`）。

## ウィンドウ構成(5枚)

将棋盤に重ねる透過ウィンドウの中に操作用の UI を置くと、その UI 自体がキャプチャに
写り込んでしまう。これを避けるため **ウィンドウを分けてある**（`main.go`）。

| ウィンドウ | URL | 役割 |
|---|---|---|
| 枠(`frame`) | `/?window=frame` | Frameless・透過。上部のツールバー(▼/□/カメラ/✕)とガイド枠だけを描く。**「どこを撮るか」の定義そのもの**。**起動時は出さない** |
| メイン画面(`main`) | `/?window=main` | アプリ本体。5 タブ。**起動するとこれが出る**（入力タブ）。**こちらも Frameless**（下記） |
| **評価値グラフ(`graph`)** | `/?window=evalgraph` | **解析タブから切り離したグラフ**（2026-09-08）。**普通のタイトルバーを持つ**（下記）。**閉じてもアプリは終わらない**（ドックに戻るだけ） |
| **候補手(`side`)** | `/?window=study` | **解析タブから切り離した候補手の面**（警告・解析の行・エンジンのカード。2026-09-08）。扱いは `graph` と同じ |
| **手順(`moves`)** | `/?window=moves` | **解析タブから切り離した手順の面**（見出しの行・手順のツリー。2026-09-12）。⚠️ **中身は `side` と同じモジュール**（`studyscreen.ts` が両方をまかなう）。⚠️ **連続解析を持っているのは `side`** —— こちらのボタンは持ち主へ頼むだけ |

⚠️ **切り離した 3 つ（`graph` / `side` / `moves`）は解析タブと一緒に出し入れする**
（2026-09-12。`CaptureService.SetStudyTabActive` → `syncPaneWindows`）。
**どれも解析タブの中身**なので、他のタブに居るあいだ出しておいても読む相手が居ない
（起動直後の入力タブも同じ）。⚠️ **設定（`config.json`）は触らない** —— やるのは
`Show`/`Hide` だけで、**タブに戻れば同じ形で出し直す**。詳しくは `_docs/ui/detach.md`。

**メインは枠ではなくメイン画面。** 枠は位置合わせが済めば用済みになりうる道具で、
アプリの寿命を握る画面ではない。

### ⚠️ メイン画面も Frameless（**2026-08-12**）

**OS のタイトルバーを外し、その場所にタブの行を上げた**（`.main-toolbar` が
タイトルバーそのもの）。**狙いは縦の領域** —— 「タイトルバー + タブの行」で 2 段
使っていたところが 1 段になる。解析タブの盤は `100vh` から引いて決まるので、
**そのぶん盤が大きくなる**（`--board-size` の引き算も 92px → 82px に減った。
**両方が効く**）。

- ⚠️ **タブの行に物を足さないこと。** ここはタイトルバーなので、**アプリ名も
  状態メッセージも出さない**（窓の識別はタスクバーが持っている）。積めば
  そのぶん盤が小さくなる、という関係は今までと同じ
- ⚠️ **選択中のタブは下の面と地続きに見せる**（2026-08-22 に変えた）。
  それまでは丸い入れ物の中で**選択中だけが明るい**（セグメンテッド
  コントロール）だったが、**タブという見た目が約束しているのは
  「その紙を手前に引き出した」こと**なので、選んでいる 1 枚がパネルと
  同じ色になり、境界線がそこだけ途切れているのが本来の形
  （実際、`.tab` に `border-radius: 5px 5px 0 0` を付けて
  「線に乗っている見え方にする」と書きながら、入れ物のほうは
  セグメンテッドだったので、**2 つの作法が半々で混ざっていた**）
  - ⚠️ **選択中が「一番暗い」ことになるが、それで正しい。**
    この画面はパネルの地色（`#1b1d23`）が一番暗いので、
    **選んでいないタブのほうを浮かせて**前後を付ける。
    **選択中を明るくし直さないこと** —— 明るくした瞬間に
    「面から浮いた 1 枚」に戻り、**どのパネルに繋がっているのかが見えなくなる**
  - ⚠️ **タブの行をタイトルバーの下端に揃えること**（`.tabs` の
    `align-self: stretch` + `align-items: flex-end`）。**線に接していないと
    切れない**ので、この見せ方そのものが成立しない
  - ⚠️ **選択中と選んでいないタブで寸法を 1px も変えないこと。**
    選択中だけに枠線 1px と `margin-bottom: -1px` が付くので、
    そのぶん padding で戻してある。崩すと**切り替えるたびに文字が動く**
  - **高さは変わっていない**（34px）ので、`--board-size` の式には無関係
- ⚠️ **高さは固定**（34px）。内容で伸びると `--board-size` の式と食い違い、
  **盤が縦にはみ出す**
- ⚠️ **余白は `.main-screen` ではなく `.panel` が持つ**（14px 16px を移した）。
  ツールバーは**画面の端まで届いていないといけない**（掴める帯が途切れる）
- **移動は `--wails-draggable: drag`、リサイズはランタイムのウィンドウ端の検出。**
  ⚠️ 押せるもの（`.tabs` / `.win-controls`）は **`no-drag` に戻すこと** ——
  戻し忘れるとクリックが効かなくなる（枠の `.frame-actions` と同じ話）。
  ⚠️ どちらも `main.ts` の素の `import "@wailsio/runtime"` が前提
- **最小化 / 最大化 / 閉じるは自前**（ツールバー右端の `.win-controls`）。
  ⚠️ **✕ はランタイムの `Window.Close()` ではなく `CaptureService.Quit`**
  —— 自前のボタンは `WindowClosing` を通らないので、**位置・サイズが保存されない**。
  終了時の後始末は Go 側の 1 本（`quit`）に寄せてある。`registerMainHooks` の
  `WindowClosing` フックは Alt+F4・OS シャットダウン用に残す
- **タイトルバーのダブルクリックで最大化 / 元に戻す。** macOS ではランタイムが
  capture 段階で横取りして自分で `ToggleMaximise` を呼ぶので、**二重に切り替わらない**
- ⚠️ **枠と違って `DisableFramelessWindowDecorations` は付けない。** あちらは中継映像に
  重ねる透過ウィンドウなので影も角丸も邪魔だったが、こちらは普通のアプリの窓で、
  影と角丸が無いと**どこまでがウィンドウか分からなくなる**

### ⚠️ 起動時に出るのはメイン画面（**2026-08-10 に入れ替えた**）

以前は**枠だけが出て、最初のキャプチャでメイン画面が現れる**という導線だった。
**入力の口が画面キャプチャだけではなくなる**（SFEN / KIF / 画像ファイル）ので、
「撮ること」を前提にした導線をやめた。**枠は「撮るときだけ使う道具」**の位置づけ。

- 起動すると**メイン画面が入力タブで出る**。**枠は出ない**
- **枠を出す入口は「枠を表示」だけ**（`CaptureService.ShowFrame`）。
  ⚠️ **置き場所はタイトルバー**（2026-08-18 に入力タブから上げた。下記
  「枠を出すトグルはタイトルバー」）
- ⚠️ **枠が出ていなければ撮れない**（`CaptureService.Capture` の `requireFrame`）。
  技術的には隠れていても HWND は生きているので撮れてしまうが、**「今どこを撮るのか」が
  画面に出ていないまま撮れるのは事故のもと**なので、**見えていることを撮れる条件に
  してある**（2026-08-10 決定）。断るときは「枠を表示」を促す文言を返す。
  ⚠️ **`FitFrame` にこの門番を掛けないこと** —— あちらは枠を隠して撮り直す手順を
  内側に持っており、起動時の自動フィットは枠を出す前に走るので、自分で自分を止める
- 唯一の例外が**設定「起動時に盤面を探す」**（既定オフ）。この設定の目的がまさに
  「最初から盤に合った枠が出ていること」なので、そのときは合わせ終えてから枠を出す
- ⚠️ **メイン画面は `Hidden: true` で作り、`revealMain` で出す。**
  `Hidden: false` で作らないこと —— 枠の外への配置（`placeMainBesideFrame`）も
  座標の記録もあちらが持っているので、通らないと**初回のキャプチャで窓が突然動く**
- ⚠️ **起動時に出す場所は枠の `WindowRuntimeReady` フックの中**（メイン画面側では
  ない）。`placeMainBesideFrame` は枠の座標を基準にするので、**枠の座標が確定する前に
  呼ぶと初回起動でセンチネル値（-32000）を基準に置いてしまう**。2 つのウィンドウの
  `WindowRuntimeReady` はどちらが先に来るか決まっていないので、順序を保証できる
  枠側に置いてある
- **撮るたびに毎回アクティブにする**（最小化されていれば戻して `Focus()`）。撮った直後に
  やることは結果を見ることなので、背面や最小化から出てくるのが速い。引き換えに中継の
  再生画面からフォーカスが外れる（動画は流れ続けるが、中継側のキー操作は効かなくなる。
  `Alt+S` はグローバルホットキーなのでフォーカスがどこにあっても撮れる）。
  **初回だけやること**（枠の外への配置・位置の記録）は `mainShown` で分けてある
- ⚠️ **最小化されているときは、`Show()` より先に `UnMinimise()` する**（下記「メイン画面が
  真っ黒になる」）。`UnMinimise` は内部で `Focus()` まで済ませるので、そちらを通ったときは
  重ねて `Focus()` を呼ばない
- **前面に出すのは撮り終えた後**（`Capture()` の最後）。メイン画面が枠に重なっていても
  その 1 枚には写らない。ただし重なったまま次を撮ると写り込むので、初回の配置
  （`placeMainBesideFrame`）で枠の外へ逃がしている
- **枠は閉じても破棄せず隠すだけ。** 領域の定義を生かしたままにするため。
  隠れていても HWND は生きているので、**出し直せば前と同じ領域に戻る**。
  ただし**隠しているあいだは撮れない**（上記の `requireFrame`）
- **メイン画面を閉じるとアプリが終了する。** 枠は隠れて生き続けるので、
  ここで明示的に `app.Quit()` しないとプロセスが残る
- **枠のツールバーの ▼ →「設定」でメイン画面を前面に出せる**（`CaptureService.ShowMain`）。
  メイン画面は起動時から出ているが、枠に隠れていたり最小化されていたりするので入口は要る
- **枠のツールバーの ▼ →「終了」でも終了する**（`CaptureService.Quit`）。
  枠の ✕ は「隠す」であって終了ではない。終了の入口が 2 つあるため、
  **位置・サイズの保存は `saveWindowState` の 1 本に寄せてある**
  （`app.Quit()` が `WindowClosing` のフックを通す保証は無いので、Quit の前に自分で保存する）
- 枠を隠した結果として可視ウィンドウが 0 枚になると操作不能になるため、
  `HideFrame` はメイン画面が未表示なら先に出す。**起動時に出しているので普通は
  既に出ているが、この保険は外さないこと**
- **キャプチャ領域の基準は枠のまま。これは移せない**（領域は枠のクライアント矩形そのもの）
- ⚠️ **枠の合図が来ないときの保険がある**（2026-10-04。`revealIfStuck`）。起動から
  `mainRevealTimeout`（15 秒）たっても枠の `WindowRuntimeReady` が来ていなければ、
  メイン画面だけを出す（下記「起動で黙って消えない」）。⚠️ **枠の横へは置かない**
  （合図が来ていないので枠の座標がセンチネル値のまま）

### 枠を出すトグルはタイトルバー（**2026-08-18 に入力タブから上げた**）

**枠は「撮るときだけ使う道具」だが、出したくなる場面はどのタブに居ても来る**
（撮って → 訂正 → 解析と進んだあと、もう一度撮る）。入力タブの中にあると
**そのたびにタブを行き来する**ことになるので、常に見えているタイトルバーへ移した。

⚠️ **「常設の機能に見えてしまう」という 2026-08-10 の懸念は、実際に使って
判断が変わったもの**（入力の口が増えても、**撮るときに要るのは枠を出すことだけ**で、
そこにタブの移動を挟む理由が無い）。**入力タブに戻さないこと。**

| | 置き場所 |
|---|---|
| **枠を出す / 隠す** | **メイン画面のタイトルバー**（`#frame-toggle`。**トグル**） |
| 枠を隠す（もう 1 つ） | **枠のツールバーの ✕**（`HideFrame`） |
| 盤に合わせる | **枠のツールバーの □**（`FitFrame`） |

- ⚠️ **押すたびに出す/隠すが入れ替わる**（2026-08-18。一度「押せなくする」に
  したのを変えた）。隠す口が枠の ✕ にもあるが、**出した口と同じ場所で戻せるのが
  素直** —— 枠が中継の裏に回っていたり別モニタにあったりすると、
  **✕ を押しに行くほうが遠い**。⚠️ **状態は 1 つ**（`frame:visible`）なので、
  入口が 2 つあっても食い違わない
- ⚠️ **アイコンにしてある**（`FiMaximize`。ガイド枠らしい四隅の括弧）。
  **絵は状態で変えない**ので、**今どちらなのかを伝えるのは `aria-pressed` の色だけ**。
  ⚠️ **薄い差にしないこと**（読めないと、押すまでどちらか分からない）。
  ⚠️ **`aria-label` と `title` は状態で書き換えること** —— 文字が無いぶん、
  「押すと何が起きるか」はこれでしか読めない
- ⚠️ **状態は Go 側が知らせる**（`frame:visible`。`ShowFrame` / `HideFrame` /
  起動時の自動フィット）。**フロントで覚えないこと** —— 枠の ✕ で隠したことは
  メイン画面からは分からないので、**隠れているのに「表示中」のまま**になる。
  起動した時点で出ていることもある（設定「起動時に盤面を探す」）ので、
  初期状態は `CaptureService.FrameVisible()` で取る
- ⚠️ **`captureWithoutSelf` からは知らせない**（探すあいだ一瞬隠してすぐ戻すだけ。
  知らせるとトグルが明滅する）
- ⚠️ **`no-drag` に戻すこと**（ツールバー全体が移動ハンドル。`.tabs` と同じ話）。
  戻し忘れると**押しても何も起きない**
- ⚠️ **入力タブに「盤に合わせる」を置かない**（2026-08-18 に消した）。
  合わせる相手は**枠**なので、枠が出ていない状態から押す操作ではない
  （□ は枠のツールバーにある）。**入力タブに残すのは案内だけ**
- ⚠️ **ここに他のボタンを増やさないこと。** タイトルバーはタブの行を兼ねており、
  **積むほど横が狭くなる**（アプリ名を出していないのと同じ理由）
  - **例外は ⚠（`#issues-btn`。2026-10-04。ユーザーが置き場所に選んだ）。**
    **問題があるときだけ出る**（ふだんは `hidden` で幅を取らない）ので、常設のボタンとは
    扱いが違う。⚠️ **常に出しておく形に変えないこと**。⚠️ **枠のトグルより左に置く**
    （出たり消えたりするので、右に置くといつも押すトグルの位置が動く）

## ⚠️ 起動で黙って消えない（**2026-10-04**）

**配る exe は `-H windowsgui` で標準エラーの行き先が無い。** それまでは次の 3 つが、
**画面に何も出さずに終わっていた**（ログに 1 行残るか、何も残らない）。利用者からは
「起動しない」にしか見えず、別の端末へ exe だけを持っていったときに一番困る。

| 起きること | 以前 | 今 |
|---|---|---|
| WebView2 が無い・初期化できない・Wails の致命的なエラー・Wails の goroutine の panic | Wails がログに出して `os.Exit(1)` | **OS のメッセージボックス**で理由とログの場所を出してから終わる（`fatal.go` の `handleWailsError`。`Options.ErrorHandler`）。WebView2 なら入れ方を添える |
| main の goroutine の panic | 黙って落ちる | 同じくメッセージボックス（`recoverMain`） |
| 自分で起こした goroutine の panic | 黙って落ちる（記録も無い） | 止められないので**ファイルに残し**（`log.CatchCrash`。ログの隣の `ikkyoku_crash.log`）、**次の起動で ⚠ に「前回は異常終了しました」** |
| 枠の `WindowRuntimeReady` が来ない | **窓が 1 枚も出ないまま動き続ける**（タスクバーにも出ない） | 15 秒でメイン画面だけを出し、⚠ に出す（`revealIfStuck`） |

**起動はできるが足りないもの**（認識器・棋譜データベース・壊れた設定ファイル・ログ・
検討の控え）は、**起動を止めずに** `app.IssueService` へ載せ、**メイン画面のツールバーの ⚠**
（`frontend/src/issues.ts`）に一覧する。載せ方は `_cmd/ikkyoku/issues.go`。

- ⚠️ **起動を止めるほうへ寄せないこと**（設計原則3）。メッセージボックスで終わるのは
  **画面を出せない（出していられない）ものだけ**。足りないものは ⚠ へ
- ⚠️ **その場で失敗を返せる操作の失敗は ⚠ に積まない**（外部エンジンが無いのは解析した
  ときに `analyze:failed` で出る。棋譜の取得の失敗はその場で出る）。⚠ は**操作する前から
  分かっていて、操作しないと気づけないもの**の置き場所
- ⚠️ **ホットキーの登録失敗は ⚠ に載せない**（2026-08-10 の決定。`frontend/src/mainscreen.ts` の末尾）
- ⚠️ **直ったら消すこと**（`IssueService.Clear`）。認識器は読み直すたび
  （`CaptureService.onRecognizer`）、棋譜データベースは開き直すたびに合わせている。
  **画面で「既読」にして隠す口は作っていない** —— 直っていないのに消えると、また
  「黙って動かない」に戻る
- ⚠️ **`ErrorHandler` で箱にするのは `*application.FatalError` だけ。** ここには
  WebView2 の致命的でないエラーも来る（`chromium.SetErrorCallback`）ので、全部を箱に
  すると動いているのに止まって見える
- ⚠️ **壊れた設定ファイルは写してから既定で動く**（`SettingsService.LoadProblem`。
  `config.json.broken-<日時>`）。写さないと、**次に設定を 1 つ変えた瞬間に上書きして
  元の設定が全部消える**（それまでは黙ってそうなっていた）
- 認識器は 3 段（学習データ → 配布モデル → 焼き込み。`_docs/design-capture.md`）で、
  **どれも読めなければ赤、置いてあるのに読めない段があれば黄**（下の段で動いている）。
  起動時に全部の段を読むので、**焼き込みの無い exe を別の端末へ持っていっても、撮る前に気づける**

## ⚠️ メイン画面が真っ黒になって触れなくなる（2026-08-08 / 2026-08-13 に発生）

**症状**: メイン画面が真っ黒になり、クリックもキー操作も受け付けなくなる。
**Go 側は無傷**（黒くなったあとの `Alt+S` で PNG が保存できている）。
**原因は確定していない**（再現待ち）。⚠️ **調査の全文は `_docs/blackscreen.md`。
次に黒くなったら、手を動かす前にそれを読むこと。** ここに残すのは制約だけ。

**黒くなったら、まずログの心拍を見る**（`DiagService.Heartbeat`。5 秒ごと・
途切れると Go が warn を出す）。

| | 意味 | 手当て |
|---|---|---|
| **心拍が続いている** | WebView2 が不可視にされているだけ | 枠のメニュー →「メイン画面を描き直す」で戻る |
| **心拍が止まる** | レンダラが死んでいる**か、UI スレッドが詰まっている** | 描き直しでは戻らない。**起動し直すしかない** |

- ⚠️ **訂正タブのドラッグをネイティブ DnD（`draggable` + `dragstart`/`drop`）に
  戻さないこと。** **2 回とも訂正タブでドラッグしている最中に始まっている** ——
  Windows の Chromium はネイティブ DnD を OLE の `DoDragDrop` で動かし、
  **ブラウザプロセスの UI スレッドでモーダルなループが回る**。そこが抜けられなく
  なると Go の `Eval` / `Focus` も心拍も同じスレッドで止まる。だから
  pointer events に置き換えた（2026-08-13。`editor.ts`）
- ⚠️ **`RepairMain` の入口を枠に置いてあるのが要点**（`CaptureService.RepairMain`。
  中身は `Hide()` → `revealMain()`）。**黒くなるのはメイン画面なので、
  そこにボタンを置いても押せない。** 設定タブへ移すような整理をしないこと
- ⚠️ **畳まれたままの窓に `Show()` を当てないこと**（`revealMain` は `Show()` より先に
  `UnMinimise()` する）。Wails は最小化で WebView2 のコントローラを不可視にし、
  戻す分岐が条件付きなので、取りこぼすと不可視のまま残る
- ⚠️ **心拍の閾値を短くしないこと**（90 秒）。Chromium は隠れている・最小化されている
  ページのタイマーを間引き、`setInterval` は最悪 1 分に 1 回まで落ちる ——
  **追っているのがまさに最小化まわりの現象**なので、短いと調べたい状況で必ず誤検知する
- ⚠️ **ウィンドウの表示状態のログ（`registerVisibilityLog`）を消さないこと。**
  debug で出しているので既定では見えないが（枠を動かすだけで大量に出て他が埋もれる）、
  **出すのをやめたのではなく普段は黙らせているだけ**
- ⚠️ **起動し直すときは古いプロセスを必ず落とすこと。** 単一インスタンスの防止を
  入れていないので 2 つ走る（`app-window.json` の二重書き込み・ホットキー登録・
  エンジンのプロセスが重なる）
- ⚠️ **短時間の動作確認では再現しない**（2 回とも長時間起動しっぱなしのとき）。
  **「触ってみて大丈夫だった」を根拠にしないこと**

## ウィンドウ状態の永続化

枠とメイン画面**両方**の位置・サイズを `os.UserConfigDir()/ikkyoku/app-window.json` に
保存・復元する(`window.go` / `window.go`)。**ルートパッケージの `Config`(`config.json`)とは
あえて別ファイルにしてある**。ルートパッケージに Wails 依存(`application` パッケージの
`ScreenNearestDipPoint` 等)を持ち込まないための分離。

- 未設定(初回起動)の判定にはセンチネル値 `-32000` を使う。マルチモニタで左/上に
  モニタがあると座標が負になりうるため、`0` や `< 0` では判定できない(wails3 skill
  `window-state.md`)
- **⚠️ 終了時に `Position()`/`Size()` を読んではいけない。** `WindowClosing` の時点では
  破棄が進行しており、**不正な値が返る**(wails3 skill `window-state.md`「特に Frameless で
  発生しやすい」。このアプリでも実測で確認し、枠を動かしても保存値が追従しない不具合が出た)。
  代わりに `geometryTracker`(`window.go`)が `WindowDidMove` / `WindowDidResize` の
  たびに位置を記録しておき、**終了時にはその記録を保存する**。
  スキルが挙げている回避策(フロントの✕から Go の `Quit()` を呼ぶ)は自前の✕しか無い
  ウィンドウ向けで、**ネイティブのタイトルバーを持つメイン画面には使えない**
  (Alt+F4・OS シャットダウンを自前の経路に通せないため)
- 保存の起点はメイン画面の `WindowClosing` の **`RegisterHook`**(`OnWindowEvent` ではない)。
  デフォルトの破棄用リスナーは並列 goroutine で走るため、hook(同期・listener より前に実行)
  でないと破棄とレースする(wails3 skill `tray-hotkey.md` の hook/listener 順序の説明)。
  **枠は閉じられないので、保存経路はここ 1 本だけ**
- 枠の `WindowClosing` hook は `e.Cancel()` + `Hide()`。ツールバーの自前✕は
  `WindowClosing` を通らない(wails3 skill `pitfalls.md`)ので、そちらは JS から
  `CaptureService.HideFrame()` を呼んで同じ入口に合流させている
- マルチモニタのクランプ(`clampToScreen`)は `events.Common.WindowRuntimeReady` で行う
  (`ScreenNearestDipPoint` は `app.Run()` 前は `nil` を返すため)
- **旧フォーマット(枠 1 枚ぶんのフラットな JSON)との互換は取っていない。**
  ツールバーが増えて同じウィンドウサイズでも撮れる領域が変わったので、
  旧い座標を復元しても位置合わせはやり直しになるため
