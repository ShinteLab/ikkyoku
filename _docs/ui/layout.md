# 盤の寸法とスプリットバー（`style.css` / `mainscreen.ts`）

**盤の大きさは式で決まる。DOM から自動では決まらない。**
行を増やしたら `--board-size` の引き算からも引くこと —— さもないと盤がはみ出す。
⚠️ **重ねたグリッドの位置合わせで何度も外している**ので、この節の ⚠️ を消さないこと。
⚠️ **ここは画面の話。** Go 側の制約は `AGENTS.md` と各パッケージの AGENTS.md にある。
⚠️ **ここに書いてある ⚠️ は「実際に踏んだ」もの。要約したり消したりしないこと。**

#### ⚠️ 盤に重ねるグリッドの位置合わせ

**盤の描画は `<shogi-board>`（core/web）のまま**で、訂正用に盤を描き直していない
（描画が 2 実装になると訂正中と確定後で見た目が変わる）。当たり判定は透明な 9x9 の
グリッドを**上に重ねて**取る（`.edit-grid`）。

- ⚠️ **位置は `svg.getScreenCTM()` で SVG 座標 →画面座標に変換して求める。**
  要素の矩形から測ってはいけない。SVG の `preserveAspectRatio` は既定
  （`xMidYMid meet`）なので、**箱が正方形でないと絵が箱の中で中央寄せになり、
  左右（または上下）に余白ができる**。箱の左端から測ると、その余白のぶんだけずれる
  （実際に踏んだ。**箱に対する割合で重ねる方式も同じ理由で駄目**）。
  CTM なら余白も拡大率もまとめて解決される
- 変換の起点にするのは `MARGIN=28` と `CELL=56`（core/web の shogi-board.js）。
  **向こうが変わったらここも直す**
- 位置合わせを呼ぶのは「ウィンドウのリサイズ」「箱のリサイズ（ResizeObserver）」
  「盤の描き直し」「局面の読み込み」「**訂正タブを開いたとき**」。
  **大きさが変わりうる場面を 1 つでも落とすと、駒の見た目とクリック領域がずれる**
- ⚠️ **タブで隠れているあいだは測れない。** `display: none` の中では
  `getScreenCTM()` が null を返すので、**開いた瞬間に測り直す**
  （`selectTab` → `EditorHandle.relayout`）。これが無いとグリッドが出ないか、
  前回の大きさのまま残って**1 マスずれたところを編集する**
- ⚠️ **CSS コメントの閉じ忘れで `.board-stage` のルールが丸ごと消え、`position: relative`
  が効かずにグリッドがページ基準になっていたことがある**（横に大きくずれる）。
  CSS は壊れても黙って動くので、`npm run build` の前に `check-css.mjs` が
  コメントの対応を検査する。JS 側も `getComputedStyle(stage).position` を見て
  `static` なら自分で `relative` にし、基準は `grid.offsetParent` から取る
- ⚠️ **`.board-stage` の幅を `--board-max`（560px）で頭打ちにすること。**
  SVG はそれ以上大きくならないので、箱だけが広がると**グリッドが盤からずれ、
  1 マス違うマスを編集する**。`--board-max` は core/web の `CELL*9 + MARGIN*2` と
  同じ値で、**向こうが変わったらこちらも直す**
- ⚠️ **`.board-stage` の幅に `%` を使わないこと。** 駒台を置くために grid の
  `auto` トラックに入っているので、`%` だと中身の大きさに依存して決まらなくなり、
  箱が潰れる（＝盤とグリッドがずれる）
- ⚠️ **`.board-area` を縮ませないこと**（`flex: 1 0 auto`。2026-08-11 に踏んだ）。
  盤（`.board-with-hands`）は `flex: 0 0 auto` で縮まないので、この箱だけが縮むと
  `align-items: center` のせいで**上下にはみ出し、上の行（「認識詳細情報」の
  折りたたみ）に盤が重なる**。はみ出すぶんは `#panel-edit` のスクロールで受ける
- 局面を読み込んでいないときは `pointer-events: none`（盤を素通しにする）
- ⚠️ **解析タブの盤にもグリッドが乗っている**（2026-08-11。`.study-grid`）。
  ただし**別の要素・別の意味**で、あちらは**合法手だけ**をクリック 2 回で指す。
  **訂正のグリッドを流用しないこと**（`study.ts` に別に持っている）。
  ⚠️ **測り直し（`relayout`）は両方に要る** —— 片方だけだと、そちらのタブで
  **1 マスずれたところを指す**

### 解析タブの表示 — **盤が主役。解析のものは全部「盤の右の列」**（2026-08-12）

```
┌──────────────────────────────╥──────────────┐
│        勝率バー（盤と同じ幅）      ║ 警告 / 解析の行            │
│  駒台   盤（fluid）        駒台    ║ エンジンの結果             │
│  ← 左上を起点に、取れるだけ →      ║ 視点 / 手順                │
│        SFEN（盤と同じ幅・1 行）    ║                            │
├══════════════════════╩══════════════════════┤ ← 横のスプリットバー
│ 評価値グラフ（横いっぱい。畳める）                          │
└─────────────────────────────────────────────┘
                              ↑ 縦のスプリットバー
```

⚠️ **右の列と評価値グラフは別ウィンドウへ切り離せる**（2026-09-08。下記）。
切り離すと**その行/列ごと消えて、盤がそのぶん大きくなる。**

**境目は全部ドラッグできる**（2026-08-13。**3 本目は 2026-08-15**）。
⚠️ **どれも書き換えるのは CSS 変数 1 つだけ**で、大きさはその式から付いてくる:

| バー | 書き換える値 | 効くこと |
|---|---|---|
| 横（盤 ⇄ 評価値グラフ） | `:root` の `--eval-graph-h` | グラフの高さ。**0 まで下げると畳む** |
| 縦（盤 ⇄ 解析の列） | `#panel-study` の `--study-side-min` | 列の幅（＝盤の横の取り分） |
| 横（解析結果 ⇄ 手順） | `:root` の `--analyze-engines-h` | 右の列の中の取り分（下記） |

**盤は固定サイズではない。** 盤が**左上を起点に取れるだけ取り**、右の列（`.study-side`）が
**残りの幅を全部もらう**（`--study-side-min` はその下限）。

⚠️ **「余りを全部もらう」のはバーを掴むまで**（2026-09-12）。掴んだ時点で列の幅は
**人が決めた値に固定される**（`--study-side-max`。下記「縦のスプリットバー」）。
そこから先は**盤にも列にも属さない幅ができうる**。

⚠️ **その余りは「盤の左右の auto マージン」が取ること**（2026-09-12 に踏んだ）。
**列は右端に貼り付いたまま、盤だけが余りの真ん中に座る。**
⚠️ **`justify-content` で寄せようとしないこと** —— あれは行の中身**全体**の寄せ方
なので、**列まで一緒に盤の側へ寄ってきて、窓の右端に何も無い帯が残る**（実際にそうなった）。
auto マージンは `justify-content` より**先に**余りを取るので、盤だけを動かせる。

⚠️ **窓の左端の 8px は `.board-area` の `padding-left` へ移してある。** 盤の
`margin-left` を `auto` にすると消えてしまうため（**量は変えていない** ——
`--board-size` の横の定数 86px はこの 8px を見込んでいる）。

⚠️ **列が出ていないとき（畳んだ / 切り離した）は auto マージンを効かせないこと。**
あちらの寄せ方は `justify-content: center` ＋ `margin-left: 12px` が持っており、
**畳む 0.3s の `margin-left` のトランジションは `auto` とのあいだでは補間できない。**

**重ねたグリッドは `ResizeObserver` が追う**（`study.ts`）ので、盤が横へ動いても
ずれない —— **あの監視を外さないこと。**

- ⚠️ **`--board-max` は使っていない**（`:root` の既定 560px は訂正タブ用）。
  上限を付けないので、**盤に `fluid` が付いていることが前提**（core/web。上の ⚠️）
- 盤は正方形なので**縦と横の両方から決まる**。縦＝ウィンドウの高さ −（タブの行・
  盤の上段・勝率バー・**評価値グラフ**・余白）、横＝ウィンドウの幅 −（右の列・駒台 2 つ）
- ⚠️ **駒台の幅は盤に比例させてある**（0.2 倍）ので、横の見積もりは盤 1 つぶんではなく
  **1.4 倍で割る**。**片方だけ変えると、広げたときに盤が横にはみ出す**
- **右の列は残りの幅をもらう**（下限 `--study-side-min`）。窓を横に広げたぶんは
  **この列が広くなる**（盤の大きさはウィンドウの高さで決まっているため）

##### 縦のスプリットバー（**2026-08-13**）

**盤と解析の列の境目をドラッグして、盤の大きさを変えられる**（`#study-split`）。
書き換えるのは **`--study-side-min`**（＋掴んだあとは `--study-side-max`。下記）で、
盤はその式から付いてくる。

###### ⚠️ 掴んだら列の幅を固定する（**2026-09-12**）

**列は既定で `flex: 1 1 auto`、つまり余りを全部もらう。** これは
⚠️ **「列の実幅は `窓幅 − 盤` で決まっていて、`--study-side-min` は盤の式の
引き算としてしか効かない」**ということで、**盤が高さで頭打ちになった時点から先は
列が 1px も動かせなくなる**（1600×900 の窓で**列が 635px より狭くならなかった**）。

そこで⚠️ **バーを掴んだ瞬間に `--study-side-max` を実幅で入れて固定する**
（`lockSide`）。以後は**1px 引けば 1px 動く**。

- ⚠️ **固定する値は「画面に出ている幅」を測って決めること**（2026-09-12 に踏んだ）。
  `.study-side` は **`min-width: 0`**（宣言が 2 つあり後のほうが勝つ）なので、
  **`--study-side-min` は盤の式の引き算としてしか効かず、列の実幅は「余り」で
  決まっている** —— つまり `settleStudySide` が式から逆算した値と実幅は
  一致するとは限らない。逆算値で固定すると、**その差のぶん掴んだ瞬間に列が飛ぶ**
  （固定後は一致するので、**1 回目のドラッグだけ見た目とずれる**という形で出る）
- ⚠️ **掴むまでは固定しないこと。** 幅は**設定に持っていない**ので、最初から
  固定すると**起動のたびに列が下限（300px）で始まる**
- ⚠️ **`settleStudySide` のあとに固定すること** —— 先に固定すると、遊びを消す前の
  （今の見た目より広い）値で固まるので、**掴んだ瞬間に列が太る**
- ⚠️ **固定したら `settleStudySide` は何もしないこと。** あれは「盤が上限に
  張り付いたまま取れる最大の幅まで詰める」処理なので、**人が決めた幅を
  その最大値へ押し戻す**（狭めた直後に元へ戻る）
- ⚠️ **一度決めたら戻さないこと。** 窓を広げたぶんは**盤の側**が受け取る
  （固定したのに列が太るのは、幅を決めたあとの振る舞いとしては裏切り）
- ⚠️ **キーボード（←/→）でも同じ順にすること** —— 固定しないと
  **右キーで狭めたつもりが 1px も動かない**
- ⚠️ **畳む / 切り離すほうが強いこと**（`is-side-collapsed` の `max-width: 0`）。
  詳細度で勝っているので、`.study-side` 側を `!important` にしないこと

**残っている制限は 2 つだけ**: 列の下限 `STUDY_SIDE_MIN`（300px。解析の行が
読める幅）と、盤の下限 `STUDY_BOARD_MIN`（240px。これ以上は列を広げられない）。

⚠️ **「盤がこれ以上大きくならないところより先へは詰めない」は外した**（2026-09-12）。
あれは列が余りをもらう作りが前提の歯止めで、**上のとおり壁そのものになっていた**。

⚠️ **判定は「実際の盤の幅を測って」行う。式の定数を JS に写さないこと。**
`--board-size` の式（`110px` や `1.4`）を写すと、CSS を直したときに**黙って食い違う**
（画面では気づけない）。測れば式が変わっても付いてくる。

- ⚠️ **掴む前に遊びを消す**（`settleStudySide`。二分探索で「盤が上限に張り付いた
  まま取れる最大の幅」を求める）。**見た目は 1px も動かない**が、これが無いと
  **ドラッグし始めても最初のうち盤の右端が動かない**（遊びのぶん空振りする）
- ⚠️ **既に盤が縮んでいるときは詰め直さないこと** —— それはユーザーが自分で列を
  広げた状態なので、勝手に戻すと設定を奪う
- ⚠️ **上限を「幅 0 のときの盤」で測らないこと。** 窓が狭いと盤は横で決まるので、
  0 まで詰めた大きさを上限にすると**解析の列を潰し切るまで詰めてしまう**。
  測るのは**列の下限（300px）まで詰めたときの盤**
- ⚠️ **評価値グラフの高さを変えたら詰め直すこと**（`setEvalGraphH` から呼ぶ）。
  グラフを畳むと盤は縦に大きくなれるので、**横の下限も下がる**
- ⚠️ **タブを開いた瞬間にも詰め直すこと。** 盤を測って決めるので、
  **隠れているあいだは決められない**（測ると 0）
- 盤は 240px、解析の列は 300px を下限にする（どちらも読めなくなる手前）
- **その場かぎりの値**（`config.json` には持たない。視点・グラフの高さと同じ扱い）

##### 解析の列も畳める（**2026-08-13**）

**縦のスプリットバーの上に載せたトグル**（`#study-split-toggle`）で、
右の列ごと畳める。**畳むと盤が中央に来る。**

⚠️ **トグルをバーの上に置いてあるのが要点。** 畳むと**列ごと消える**ので、
列の中に置いたら戻す手段が無くなる。**評価値グラフ側のトグルも同じ形に揃えてある**
（`.split-toggle`。向きだけ入れ替える）。⚠️ **押してもドラッグが始まらないよう
`pointerdown` を止めること** —— 止めないと「掴んだ」と解釈されて、
離すまで幅が動き続ける。

⚠️ **状態は幅 1 つ**（`studySideW === 0` が「畳んでいる」）。真偽値を別に持たない
のはグラフの高さと同じ理由。**ドラッグの下限は 300px なので、0 になるのは
畳んだときだけ**。

- ⚠️ **畳んだら盤を中央に寄せる。** 左上を起点にしているのは**右に列があるから**で、
  列が無くなれば寄せる理由も無くなる（盤だけの画面で左に寄っていると、
  右の余白が「何かあるはず」に見える）
- ⚠️ **スプリットバーを流れから外して右端へ逃がすこと**（`position: absolute`）。
  流れに残すと中央寄せの対象が「盤 + gap + バー」になり、**盤が 10px 左へずれる**。
  盤の `margin-left: 8px` も同じ理由で 0 にする
- ⚠️ **`.study-side` を `hidden` で消さないこと。** あの属性は「局面があるか」を
  表しており（持ち主は `showStudy`）、2 つの意味を載せるとどちらが今の話か
  分からなくなる。畳むほうは `#panel-study.is-side-collapsed` の class で消す
- ⚠️ **畳んでいるあいだはドラッグしない**（`settleStudySide` / `setStudySideW` の
  入口で弾く）。幅は 0 と 300px のあいだが飛んでいるので、ドラッグの続きにならない。
  **戻すのはトグルの仕事**
- ⚠️ **窓のリサイズで勝手に開かないこと**（「盤が潰れたら幅を取り直す」経路が
  0 を上書きしうる）
- **畳む前の幅に戻す**（`studySideOpenW`）。既定に戻すと、広げたのが失われる

##### 折り畳みのアニメーション（**0.3s**。2026-08-13）

**畳む/開くときだけ**トランジションを付ける（`#panel-study.is-animating`）。
⚠️ **常時付けないこと** —— スプリットバーの**ドラッグが 0.3s 遅れて追ってくる**
（掴んでいる位置と盤がずれる）。⚠️ **掴んだら即座に終わらせること**
（`cancelAnimation`）—— 畳んだ直後にバーを掴むと残りの時間だけ遅れる。

⚠️ **後始末（遊びの取り直し・測り直し）は終わってから。** 途中で測ると
動いている最中の値を掴むので、**`settleStudySide` はアニメーション中は何もしない**
（二分探索がでたらめな幅で確定する）。

- ⚠️ **解析の列は `display: none` にしない**（幅 0 へ縮める）。
  ⚠️ **起点の幅は JS が inline の `max-width` で入れること** —— 初期値の `none` は
  補間できないし、`100%` からだと**畳み始めの 7 割が空振りする**（列の実幅は
  箱の 3 割ほどしかない）。**開くときは「いったん最終状態にして測り、見た目だけ
  畳んだ状態へ戻してから動かす」**（同じタスクの中なので途中は描かれない）
- ⚠️ **`justify-content` は補間できない**ので、`#panel-study .board-area` は
  **常に `center`** にしてある。開いているあいだは `.study-side` が余りを全部
  もらうので**寄せる余白がそもそも無く、`flex-start` と同じ見え方**になる。
  切り替える作りにすると、畳んだ瞬間に盤が飛ぶ
- ⚠️ **畳んだらスプリットバーは窓の右端へ逃がす**（`position: absolute`）。
  流れに残すと**盤のすぐ右（画面の真ん中あたり）に線とトグルが残って目障り**。
  ⚠️ **`position` は補間できないので位置だけは一瞬で飛ぶ。フェードで隠すこと**
  （`split-fade`。0.3s）—— 消えて出るぶんには、どこから来たのかを目が追わない。
  **フェードを外すと飛んで見える**
- ⚠️ **中央寄せは盤の左の余白（12px）で釣り合わせる。** これは**盤の後ろに残る
  flex の gap** そのもの（バーは流れから外れているが、幅 0 の列との gap は残る）。
  **`.board-area` の gap を変えたら計算し直すこと**
- **重ねたグリッドは `ResizeObserver` が毎フレーム追いかける**ので、
  盤が伸び縮みしている最中もずれない（`.board-stage` の `width` も 0.3s で動かす）
- ⚠️ **エンジンごとの結果の枠（`.analyze-engines`）は横に流さないこと**
  （`overflow-x: hidden`）。読み筋は行の幅で切って `title` で読ませる作りなので、
  横スクロールバーが出ても得るものが無いうえ、**出た横バーが高さを食って縦バーまで出る**
- ⚠️ **解析タブだけパネルの余白を持たない**（2026-08-13。`#panel-study { padding: 0 }`）。
  そのぶん盤が大きくなる（実測で +22px）。**盤だけは窓の端に貼り付かないよう
  `#study-board-with-hands` に `margin-left: 8px`** を残してある。
  ⚠️ **上だけ 12px 残してある**（2026-08-13。対局者名を 24px にしたので、
  タブの行に文字が貼り付くと窮屈）。⚠️ **外した/残した余白は `--board-size` の
  定数に反映してある**（縦 92px → 60px → **72px**、横 110px → **86px**）。
  **片方だけ直すと盤がはみ出す**
- ⚠️ **`.panel` の `gap`（10px）も 0 にしてある**（2026-08-13）。**縦のスプリット
  バーの下端と、横のスプリットバーを繋げるため** —— あいだが空いていると 2 本が

  ⚠️ **この 10px も縦の定数から引いてある**（70px → 60px）
- ⚠️ **盤の下に積むものを増やしたら、縦の式からも引くこと**（積んだぶんだけ盤が

  **横に長いほうが読める**（右の細い列に入れると潰れる）
- **エンジンごとの結果は右の列**（`--analyze-engines-h` はもう `--board-size` を

- ⚠️ **盤の大きさは式で決まる。DOM から自動では決まらない。** 行を減らしても、
  **`--board-size` の式から引く量を減らさない限り盤は大きくならない**
  （減らした行のぶんが余白として残るだけ）。**行を増やしたら足すこと**
- ⚠️ **右の列の高さの頭打ちは `.board-area` そのもの（`max-height: 100%`）**

  **盤の高さで止めないこと** —— この列が受け持つのは `.board-area` の縦いっぱいで、
  **盤の列はその中で「勝率バー + 盤 + SFEN」を積んでいる**。盤の高さで止めると
  **勝率バーと SFEN と gap のぶん（60px 弱）が下に遊びとして残る**。
  盤の実寸（`--board-size`）で止めるのは更に悪く、盤は**縦と横の小さいほう**で
  決まるので、**盤が横で決まっているとき**——**縦のスプリットバーでこの列を
  広げたとき**や窓が横に狭いとき——**縦は空いているのに手順まで一緒に縮む**

- ⚠️ **右の列（`.study-side`）の中の高さの取り合いに注意。** エンジンの結果は
  **先に高さを取り**（`--analyze-engines-h`）、手順のリストが**余りをもらう**
  （`flex: 1 1 0`）。手順を `1 1 auto` にすると中身の高さが基準になり、
  **エンジンの枠を最低高さまで押し潰す**（2 つ目のエンジンが見えなくなる。実際に踏んだ）
- 列そのものも `overflow-y: auto`。**窓が低いと全部は置けない**ので、そのときは
  列ごと流す（普通の高さでは出ない）
- ⚠️ **読み筋は列が細いぶん省略される。** 溢れたぶんを読む手段が
  ツールチップしかないので、**日本語の読み筋も `title` に入れること**

**エンジンごとの結果**は `.analyze-engines` の中に `.analyze-engine` が縦に並ぶ
（見出し＝エンジン名 + 深さ/ノード数/経過/起動時間、その下が候補手の一覧
`.analyze-lines`）。

⚠️ **盤の下に駒台の行は無い**（2026-08-12 に外した）。駒台は盤の脇に駒そのものが
出ているので、文字の要約は要らない。

⚠️ **SFEN は盤の下に戻した**（2026-08-14。`.study-sfen-row`。2026-08-12 から
手順の列の下に置いていた）。「今どの局面を見ているか」の値なので、盤のすぐ下に
あるほうが結び付く。**盤は小さくしていない**:

- ⚠️ **収める先は「評価値グラフの箱を 38px 詰めたぶんの空き」**（同日の変更）。
  `.board-area` は `align-items: center` なので、**そこは元から遊んでいる**。
  `--board-size` の式は**触っていない**
- ⚠️ **1 行に収めること**（グリッドの 4 行目 + `gap` 6px で 23px ほど）。
  折り返させたり `border` / `padding` を足したりすると、**空きを食い潰したぶんだけ
  盤が押し出される**。溢れたぶんは省略して `title` に出す（`mainscreen.ts` が
  **SFEN そのものを `title` に入れている** —— 切れた末尾を読む手段がそれしかない）
- ⚠️ **幅を `--board-size` に固定すること。** grid の `auto` の列なので、
  **指定しないと SFEN の長さで列が広がって盤ごと押し出される**（折り返さないので
  max-content が数百 px になる）
- ⚠️ **盤と同じグリッドの列（2 列目）に入れること**（勝率バーと同じ理由）。
  `.board-area` の直下に置くと、右の列のぶん盤が左に寄っているので**左右がずれる**

⚠️ **候補手の行は「評価値 + 次の 1 手」を同じ大きさで出す**（2026-08-11）。
読むのはほぼ**「今この評価値が付いているのはどの手か」**なので、そこだけ大きく拾えれば
足りる。**その先の読み筋は手順の裏付け**として小さいまま並べる（読み筋が長くても
場所を取らない）。評価値は**右寄せ** —— 数字なので、桁が変わっても一の位が揃って
いるほうが読み比べやすい。

⚠️ **評価値と「次の 1 手」の幅は px で固定する**（`--analyze-score-w` /
`--analyze-first-w`）。手の表記は「▲同　銀」から「▲２二角不成」まで長さが違うので、
固定しないと**読み筋の始まり（2 手目）が行ごとにずれ**、候補を縦に読み比べられない。
⚠️ **em にしないこと** —— 2 番手以降は文字が小さいので、同じ指定でも幅が変わって
同じずれが起きる。**次の 1 手は中央寄せ**（余りを左右に振り分ける。左寄せだと
短い手のときに右が大きく空いて、評価値との間だけが詰まって見える）。

⚠️ **2 番手以降は一段小さく出す**（`.analyze-line.is-sub`）。同じ大きさで並べると、
どれが最善手なのかが順番でしか分からない。**小さくするのは評価値と次の 1 手だけ** ——
その先の読み筋はもともと小さいので、そちらまで変えると 1 番手の行と揃わなくなる。

⚠️ **高さは固定する**（`--analyze-line-h` / `--analyze-lines-h`。2026-08-11）。
**連続モードでは 1 手指すたびに「消す → 起こす → 結果が届く」を繰り返す**ので、
中身の有無や候補の本数で伸び縮みすると**盤ごと画面が上下に跳ねる**
（駒を掴んでいる最中に動くのが一番困る。訂正タブの `.board-head` を固定したのと同じ話）。

- **枠を畳まないこと。** 局面があるあいだは `.analyze-engines` を出しっぱなしにし、
  中身を空にするだけにする（`min-height` でエンジン 1 つぶんを確保してある）
- **`.analyze-lines` は `max-height` ではなく `height`。** 空でも畳まない
- ⚠️ **候補の本数ぶん全部を確保しないこと。** MultiPV を上げると候補は何本にもなるので、
  そのぶん盤の下が伸びる。**4 本ぶんで頭打ち**にして、溢れたら中でスクロールさせる
  （実際の値は `mainscreen.ts` の `reserveLines` が入れる）
- ⚠️ **枠全体（`.analyze-engines`）の頭打ちを定数にしないこと**（2026-08-12 に
  220px から直した）。候補手の本数でカードの高さが変わるので、定数だと
  **本数を増やしたとたんにエンジン 2 つでもスクロールバーが出る**
  （候補 3 本 × 2 つで中身は 240px なのに 220px で止めていた）。今は
  `--analyze-engines-h`（＝ `--analyze-card-h` × 2 + 8px、上限 300px）で
  **エンジン 2 つはそのまま見え、3 つ目からスクロール**する
- ⚠️ **`--analyze-card-h` の 29px は実測値**（一覧 + padding 8 + 見出し 19 + gap 2）。
  見出しの文字サイズを変えたら測り直すこと —— 2〜3px ずれるだけで
  **エンジン 2 つでスクロールバーが出る**（実際にそうなっていた）
- ⚠️ **`--analyze-lines-h` は `:root`（`documentElement`）に入れること。**
  枠の高さも `#panel-study` の `--board-size` もこれを引いており、
  **カスタムプロパティは下へしか継承しない**（`--eval-graph-h` / `--winrate-h` と
  同じ話）。⚠️ **枠が伸びたぶんは `--board-size` からも引くこと**
  （260px の中に 220px ぶんを見込んであるので、そこからの差を引く）

#### 勝率バー — **入っている**（2026-08-12）

**盤の真上・盤と同じ幅**で「どちらがどれくらい良いか」を横棒で出す（`.winrate-row`）。
**左が後手（青）・右が先手（赤）。** 真ん中（互角）に点線を引く。

```
勝率(先手) = 1 / (1 + exp(-評価値 / ポナンザ定数))     定数は設定タブ。既定 1500
```

- ⚠️ **計算は Go 側**（`analyze.WinRate` → `Score.WinRate`）。**フロントで `cp` から
  計算し直さないこと** —— 定数は設定で変えられるので、式を 2 か所に持つと
  **片方だけ古い定数で描く**（`Score.Label` を Go 側で組み立てているのと同じ理由）。
  既定値（1500）の解決も `analyze.PonanzaConstantOr` の 1 か所
- ⚠️ **バーは 1 本だけ。押すと別のエンジンに切り替わる**（2026-08-12）。
  **並べないこと** —— 盤の上に段を積むとそのぶん盤が小さくなるし、
  **形勢を一目で見るための帯**なので読む対象が増えると意味が薄れる。
  食い違いを読むのは下の一覧（そちらは全部出る）。
  ⚠️ **切り替えても合成ではない**（平均も多数決も取らない。どれか 1 つの値そのもの）
- ⚠️ **値はエンジンごとに覚えること**（`EngineCard.best`）。押した瞬間に
  そのエンジンの今の値が出るのが期待どおりで、**次の更新まで空**では比べられない
- ⚠️ **選んだエンジンは解析をまたいで残すこと。** 連続モードでは 1 手ごとに
  `buildEngineCards` を通るので、毎回 1 つ目へ戻ると切り替えた意味が無い
  （居なくなっていたら先頭に戻す）
- ⚠️ **数字（%）もエンジン名も画面に出さない**（2026-08-12）。盤の上に文字を積むと
  そのぶん盤が小さくなる。**カーソルを当てたときに `title` で出す**
  （後手/先手の % ・評価値・エンジン名・押すと切り替わること）
- ⚠️ **盤と同じグリッドの列に入れること**（`#study-board-with-hands` の 1 行目）。
  `.board-area` の直下に置くと、**右の列のぶん盤が左に寄っている**ので
  盤と左右がずれる。列に入れれば幅も位置も盤とそのまま揃う
  （解析タブの grid だけ 3 行になり、盤は 2〜3 行目・駒台も 1 つずつ下へずれる）
- ⚠️ **左右は盤の余白ぶん詰めること**（`padding: 0 5%`）。`<shogi-board>` の SVG には
  筋・段を書く余白（core/web の `MARGIN=28` / `size=560` なので左右 5% ずつ）が
  含まれるので、箱いっぱいに引くと**盤の格子より広い帯**になる。
  **盤が大きいほど目立つ**（720px なら片側 36px）
- ⚠️ **符号も向きもここで触らない。** 逆に伸びると「エンジンが間違えている」と
  しか読めない壊れ方になる（画面からは区別が付かない）
- **上下に 6px ずつ余白を持たせてある**（2026-08-13）。⚠️ **この余白は
  `--winrate-h` に入っている**ので、変えたらあちらも直すこと（`--board-size` が
  これを引いており、**引き忘れると盤が縦にはみ出す**）。
  ⚠️ **上下を非対称にしないこと** —— 対局者名は同じ行に `align-self: center` で
  置いているので、**帯と名前の高さが揃わなくなる**。タブの行との間を空けたい
  ときは `#panel-study` の `padding-top`（12px）で取る
##### 隠せる（2026-09-10）

**解析タブの黒地（盤・駒台・帯・右の列のどれでもないところ）を右クリックすると
「評価値バー」「対局者名」の 2 つのチェックが出て、外したほうが消える**
（`mainscreen.ts` の `isStudyBackdrop` → `openBoardMenu` → `applyStudyTopRow`）。
**中継を観ながら使うので「評価値を見たくない」場面がある**のに、盤の真上の帯は
目に入るのを避けようが無い、というのが理由。

- ⚠️ **チェックは 2 つに分ける**（1 つにまとめない）。**帯だけ消して名前は残す**
  （誰の対局かは見ていたい）も、**両方消す**（盤を大きくしたい）も、
  どちらも普通の使い方
- ⚠️ **解析は止めない。** 消えるのは帯だけで、候補手も評価値も右の列には
  今までどおり出る（**見たくないものだけを消す**）
- ⚠️ **盤の取り分（`--winrate-h`）を返すのは、行が空になったときだけ**
  （`#panel-study.is-toprow-empty`。両方消したときで、盤が 34px 大きくなる）。
  **片方でも出ているなら返さないこと** —— 対局者名は 24px あって行の高さ（34px）と
  ほとんど変わらないので、**帯を消しただけで引き算を減らすと盤が縦にはみ出す**
- ⚠️ **出す条件は `applyStudyTopRow` の 1 か所にまとめること**（`syncStudyChrome`
  からもここを呼ぶ）。「局面がある」と「隠していない」の掛け算を 2 か所に書くと、
  **隠したまま別の局面を読み込んだ瞬間に戻る**
- ⚠️ **設定に残すこと**（`Config.HideWinRateBar` / `HidePlayerNames`。**2 つとも
  別の項目**）。**画面の組み方の好み**なので
  次の起動でも同じ形で始める（切り離しと同じ扱い）。
  ⚠️ **「隠しているか」で持つ** —— `Show...` にすると bool のゼロ値が「隠す」に
  なり、**この項目を知らない設定ファイルで開いたときに帯が消えたまま始まる**
- ⚠️ **盤と駒台の上では出さないこと。** あちらの右クリックは**掴んだ駒を離す**
  操作（2026-08-29。`_docs/ui/moves.md`）で、指す先を探している最中にメニューが
  出ると**やめる操作がメニューを閉じる操作に化ける**
- ⚠️ **判定は「押した先が入れ物そのものか」で行う。除外リストを持たないこと** ——
  盤・駒台・帯・ボタン・右の列・幕はどれも**中身の要素が受ける**ので、入れ物
  （`#panel-study` / `.board-area` / `#study-board-with-hands`）まで抜けてくるのは
  何も置いていないところを押したときだけ。除外リストにすると、**行を足すたびに
  書き足すことになり、書き忘れた場所でだけメニューが出る**
- **設定タブには置いていない。** 見えているものを消す操作は、その画面で
  切り替えるほうが素直（切り離しのトグルと同じ判断）

- **対局者は「グリッドの左右の列」に出す**（2026-08-13。`△後手 ｜ バー ｜ ▲先手`）。
  帯は盤と同じ幅のまま**真ん中の列**に居るので、**駒台の上（1 行目の左右の列）が
  ちょうど空いている**。⚠️ **帯の中に入れないこと** —— 名前のぶん帯が短くなり、
  **形勢を一目で読むという帯の役目が痩せる**。
  - **左が後手・右が先手**（帯の左右と同じ並び）
  - **名前は棋譜を読んだときだけ埋まる**（`StudyState.Black` / `.White`。
    `StudyService` が `position.Game` を持つ）。⚠️ **撮った局面と新規対局では
    空に戻すこと** —— 残ると**別の対局の名前を今の盤に出す**
  - ⚠️ **Go 側で空を「先手」「後手」に埋めないこと。** 名前が分かっているのか
    既定を出しているだけなのかが区別できなくなる。**既定の文言は表示側が持つ**
  - ⚠️ **▲△ は名前があっても付ける**（名前だけだとどちらか分からない）
  - ⚠️ **色は付けない。** 先後は ▲△ が示しており、盤の上の狭い帯の周りに色を
    増やすと**帯そのものの赤青が読みにくくなる**
  - ⚠️ **視点を反転しても左右を入れ替えないこと。** 帯そのものが反転しないので、
    名前だけ動くと帯との対応が壊れる（駒台とは揃わなくなるが、名前が並んでいる
    のは帯の行なので、そちらに合わせる）
  - ⚠️ **幅は駒台と同じ `--board-size * 0.2` で頭打ち**にすること。グリッドの列は
    `auto`（中身で決まる）なので、**長い名前を入れると列が広がって盤が押し出される**。
    ⚠️ **`%` は効かない**（中身で決まる列に対する `%` は循環する）。
    係数は `.hand-zone.is-readonly` と同じなので、**片方を変えたら両方直す**
  - **字は 24px**（2026-08-13）。⚠️ **1 行目の高さ（`--winrate-h` = 34px）に
    収まる範囲にすること** —— 超えると行ごと高くなって**盤が小さくなる**
    （24px × line-height 1.2 = 28.8px なので今は収まっている）。
    ⚠️ **そのぶん入る字数は減る**（頭打ちの 0.2 倍で、盤 668px なら約 5 文字）。
    長い名前は省略されるので、**全文は `title`**。字数を稼ぐなら係数を上げるが、
    **駒台の列ごと広がって盤が小さくなる**ことと引き換え
- **盤の上に置いてあるのは、評価値の数字より先に目に入るから**（数字は下の
  候補手の行にある）。⚠️ **そのぶん高さの固定が効く** —— 連続モードでは 1 手ごとに
  消えて出るので、伸び縮みすると**盤ごと下へ押される**。高さは `--winrate-h`
  （`--winrate-rows` を `reserveWinrate` が入れる）で、⚠️ **`--eval-graph-h` と
  同じく `:root` に置き、`#panel-study` の `--board-size` から引くこと**
  （引き忘れると盤が縦にはみ出す）
- **まだ結果が届いていないあいだは中立の色にする**（バーは動かさない）。
  ⚠️ **50% と言い切らないこと** ——「互角」と「まだ分からない」は別物
- **詰みは 100% / 0% に振り切る**（詰みスコアの生値をシグモイドに通すと、
  詰みの手数で勝率が変わって見える）
- **更新は候補手の一覧と同じ 1 か所**（`showAnalyzeProgress`。順位 1 の評価値）。
  別々に更新すると、バーと数字が食い違う
- ⚠️ **局面が変わったら消すこと**（`clearAnalyzeResult`）。別の局面の勝率が
  盤の上に残っていると、**今の盤の形勢として読まれる**

  `AnalyzeService.Start` が読む）。⚠️ **`setoption` と違って繋ぎ直しは要らない**

##### ⚠️ ホバーで点くのが遅いのは意図的（**バグではない**）

スプリットバーの色は **0.5s・`ease-in`** で点く。**遅いのを「直さない」こと。**

盤とグラフ（および盤と解析の列）の境目は**カーソルの通り道**でもあるので、
横切るたびに光ると鬱陶しい。立ち上がりを寝かせておくと、**通り過ぎるだけでは
点かず、掴もうとして留まったときにだけ光って見える** —— ＝「サイズを変えるときだけ
光っている」ように見える。**実際に条件で分けているわけではなく、速さだけで
そう見せている**（実測: 50ms 留まって 1.7%、100ms で 6%、200ms で 21%、
0.5s で 100%）。

⚠️ **2s → 1s → 0.5s と縮めてある**（2026-08-13。長いと、掴もうとしてから
点くまでが待たされる感じになる）。**効いているのは長さではなく
立ち上がりの寝かせ方（`ease-in`）のほう**なので、⚠️ **更に縮めるとしても
`ease-in` は外さないこと** —— `linear` にすると 0.5s でも 100ms で 20% 点いて
しまい、**通り道で光り始める**（この節の狙いが消える）。

- ⚠️ **戻りは速いまま**（0.15s。base 側に置いてある）。離したのにいつまでも
  光っていると、今どこを掴んでいるのか分からなくなる
- ⚠️ **掴んでいるあいだ（`.is-dragging`）は即座に光らせる。** そこはもう
  「サイズを変えている」ので、待たせる意味が無い（掴んだ手応えが要る）。
  ⚠️ **`:hover` より後に書くこと**（詳細度が同じなので順番で勝たせている）。
  ⚠️ **pointer capture を取っているとバーの外へ出ても掴んだままなので、
  `:hover` では代用できない**

**これから**: 分岐ツリーが入ったら、**枝ごとの折れ線を並べる**のが自然な続き
（今は一直線なので 1 本ずつ）。
